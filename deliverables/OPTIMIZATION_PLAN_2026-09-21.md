## 1. 优化目标

### 1.1 三层目标（按可验证性排序）

| 层级 | 目标 | 判据 |
| :--- | :--- | :--- |
| **T1 消除确定性浪费** | 增量导入的代价与"实际变更量"成正比，而不是与历史数据总量成正比 | 新增 1 天数据时，夜表阶段与 GPX 阶段的输入规模应可测地降到 O(变更量) |
| **T2 补上缺失的工程护栏** | 队列可区分轻重任务；崩溃任务不会无限重放；备份恢复能保证跨库一致 | 各自有可突变到红的断言，而不是"读代码看着对" |
| **T3 消除口径硬编码** | 时区、效率指标从"写死"变成"显式传入 + 单一入口" | 全仓检索不再出现散落的默认值；或明确声明"暂不支持"并写进文档 |

### 1.2 明确非目标（本次不做）

- **不改评分口径的数值结果**，除非该项单独走完数据口径评审 + 全量重算 + 门禁（见 OPT-8）。
- **不动冻结区**（`AGENTS.md` 列的 `mobileNavigation` / `.mobile-nav-links` / `.workout-mobile-list` / <1024px 媒体查询）。
- **不恢复已删除的 Shadow 全重放比对**（见第 4 章）。
- **不新增写端点**，避免触碰 `metadataOnlyMutationRoutes` / `databaseRequiredMutationRoutes` 登记规则。

### 1.3 收益基线：本机真库实测规模

所有收益估算都基于本机 `var/rai.sqlite`（325 MB，只读查询，2026-09-17 快照）：

| 对象 | 实测 |
| :--- | :--- |
| 睡眠原始记录 | **5,693 条**，覆盖 201 个 UTC 日 |
| 夜表输出 | `canonical_nights` **189 行**（`wake_date` 2024-06-13 → 2026-09-04，**跨度 814 天**） |
| HRV | 原始 772 条 → `canonical_hrv_days` **184 行** |
| 路线点 | `route_points` **204,284 点**（92 个 GPX 文件，指纹表记录 52.7 MB） |
| 前端产物体积（09-19 构建） | charts 409,047 B / 预算 450 KiB = **88.7%**；index 183,411 B；styles 81,014 B |

🔴 **814 天 vs 189 行的落差本身就是问题**：夜表按日期逐日循环，跨越 814 天，但只有 189 天真正产出结果 —— 中间大量空档日也在全表扫描。

## 3. 逐项方案

### OPT-1 时区 formatter 复用 · P0

**现状**（`packages/health-export-parser/src/utils.ts:54-56`、`:43`）
构造国际化格式化对象发生在循环体第一句；`localDateAt` 每次调用也重新构造。而这两个函数在夜表重建里被高频调用：日期窗口起止与午睡窗口起止每天各 1 次（`canonicalize-nights.ts:159`、`:160`、`:196`、`:197`），`localDateAt` 则按 segment 逐条调（`:154`）。

**改动要点**
把格式化对象从"每次调用构造"提升为"按'时区 + 字段组合'缓存复用"，并考虑把 `localDateTimeAt` 的线性探测改为先用便宜的方式算出候选偏移、只在必要时才做精确校验。注意 `localDateAt`（只到日）与 `localDateTimeAt`（到秒）字段集不同，应缓存为两个不同键，不要共用一个对象。

**预期收益**
按本机实测规模：814 天 × 4 次/天 = 3,256 次调用 × 129 次循环 ≈ **42 万次**格式化对象构造，加上按 segment 的 5,693 次，合计约 **42.6 万次 → 个位数**。这是纯 CPU 消耗，改完夜表阶段的耗时应当有肉眼可见下降。

**风险与注意事项**
- 🟡 **缓存键必须含时区**。当前默认值时区只有 `Asia/Shanghai`，一旦 OPT-9 把时区做成可传入，按"单例"缓存会串时区 —— 请直接按 key 缓存，不要图快用全局单例。
- 🟡 `Intl` 的 `hour` 可能出现 `24` 这种表示（现代码有归一化），复用后不要把这个边界丢掉。
- ⚠️ 该函数同时服务于 **GPX/XML 解析之外**的场景，改前先确认所有调用方都接受"同一时区返回同一对象"的语义（`Intl.DateTimeFormat` 的 `formatToParts` 是纯函数，复用安全）。

**验收标准**
- 等价性：对同一批输入，改动前后 `localDateTimeAt` / `localDateAt` 的输出序列**逐条完全相同**（含夏令时边界，需覆盖一个非固定偏移时区做对照）。
- 夜表产出与改动前逐行一致（行数、每行主键、入睡/在床/各分期分钟数）。
- 回归门禁见第 5 章。

**回滚**：单文件改动，直接 revert。

### OPT-2 GPX 元数据先验跳过哈希 · P0

**现状**（`packages/health-export-parser/src/gpx-parser.ts:285`）
在缓存比对（`:286-301`）之前就无条件对磁盘文件做全量读取并计算 SHA-256；指纹表里已有的 `size_bytes` / `modified_at_ms`（`:267-280`）只被查出来、**没有参与"要不要读盘"的判定**。

**改动要点**
在算哈希之前，先比对该文件的**大小 + 修改时间**与指纹表记录：两者都一致时，直接用指纹表里存的历史 SHA-256，跳过读盘与哈希计算；任一不一致才走完整流程。

🔴 **这一条有一个必须守住的约束**：校验用的哈希值同时被累加进"bundle 哈希"、最终决定 `dataset_version`（`gpx-parser.ts:294-297` 命中时用的是 `cached.sha256`；`:367-369` 把它写进 import manifest）。所以跳过的**只能是"读盘重算"这个动作**，喂给 bundle 哈希的值**必须仍然来自指纹表的历史 SHA-256** —— 否则每次增量同步生成的 `dataset_version` 都会变，进而触发不必要的全量重算与模型版本变动。当前代码在命中分支已经是这么做的，按此实现即可保持 `dataset_version` 不变。

**预期收益**
本机规模：**92 个文件 / 52.7 MB**，每次增量同步都在为"没变过的文件"读盘并算哈希。命中后降为 **0 字节读盘、0 次哈希**。这是 P0 里收益最直接的一条（磁盘 IO 而非 CPU）。

**风险与注意事项**
- 🟡 **漏更新的窗口**：内容变了但大小与修改时间都没变（人为回填时间戳、或同尺寸覆盖）会漏判。概率极低，但要给出兜底：保留一个"强制全量重算哈希"的开关，或让 `replaceAbsent` / 全量导入路径强制走完整流程。
- 🟡 **双哈希残留**：缓存未命中的文件存在两次哈希 —— TS 侧先算一次，Rust 侧解析时还会再算一次（`crates/rai-data-worker/src/main.rs:380` 返回输入文件的哈希）。本轮**不处理**这一点（只影响变更文件，量小），但要在方案里记一笔，避免以后重复发现。
- 🟡 文件系统时间戳精度：跨平台的 `mtime` 精度不同，比较时应容忍亚秒级抖动，避免永远判定为"已变更"而退回全量哈希（此时表现为优化无效，不表现为错误）。
- ⚠️ 改动落在 **Rust 引擎已接管的那条链路的入口**。改完必须在启用 Rust 与回退 TypeScript 两种配置下各跑一次导入，确认结果一致（判定方式见第 5 章第 5 条）。

**验收标准**
- 连续两次增量导入（第二次不做任何文件变更）：第二次的 GPX 阶段**零重解析**，且 `dataset_version` 与第一次**完全相同**。
- 改动单个 GPX 文件（改大小）后导入：仅该文件被重新解析，其余跳过，`dataset_version` 变化。
- Rust 与 TypeScript 两种引擎下上述两条结果一致。

**回滚**：单文件改动，revert 即可。

### OPT-3 夜表增量化 · P1

**现状**（`packages/health-export-parser/src/canonicalize-nights.ts:148-206`）
无条件清空两张恢复表（`:152`）后从最小日期逐日重算到最大日期；每个日期做两次全表扫描（`:161` 主夜窗口、`:199-206` 午睡窗口）。调用点唯一但覆盖两条入口：CLI（`cli.ts:320`），而 API 的导入 worker 是以子进程方式跑**同一套 CLI 流水线**（`apps/api/src/import-worker.ts:1455-1463`，其阶段统计白名单里就有 `canonicalize_nights`，见 `:1484-1487`）。也就是说 **iOS 增量上传同样触发全量重建**。

对比同段代码：`canonicalizeRunningWorkouts`（`cli.ts:316-319`）**已经有** `dirtyWorkoutTimes` 增量参数，夜表没有。

**改动要点**
1. 引入"脏日期集合"入参，语义与跑步侧对齐：只清理并重算受变更影响的日期窗口。
2. 窗口归属规则要显式定义并写进注释：主夜窗口跨越"前一日 18:00 → 当日 14:00"，午睡窗口是"当日 14:00 → 18:00"。因此**一条落在 18:00 之后的睡眠记录会同时影响相邻两天**，脏日期必须按窗口边界外扩，不能只取记录自身所在日。
3. 把两次全表扫描收敛为"按日建索引后取窗口"，消除 O(D×N)。
4. HRV 天表与夜表通过 `night_id` 关联，重算脏日期时必须同批处理两者的删除与写入，避免出现"夜在、HRV 不在"的中间态。

**预期收益**
本机规模：814 天 × 2 次全扫 × 5,693 行 ≈ **927 万次谓词求值**，而这一切只为同步"昨天 1 条"睡眠记录。增量化后约为"2 天 × 5,693 ≈ 1.1 万次"，**约 800 倍减少**；同时 `canonical_nights` 的 189 行产出不需要被整体重建。收益随历史长度线性放大（每天都会变得更值钱）。

**风险与注意事项**
- 🔴 **等价性是唯一验收标准**：抓取本机真库的**只读副本**，对同一份数据分别跑"现有全量"与"新增量"，要求两张表的**逐行完全相同**（行数、主键、入睡/醒来时间、在睡/在床/清醒分钟、分期 JSON、segment 计数、provenance）。不要用"耗时下降"当验收标准，也不要用拍定的效率阈值当验收标准。
- 🔴 **只在本机只读副本上做实验**，不要在 `var/rai.sqlite` 真库上跑新逻辑。
- 🟡 **状态标签的语义要一起看**：算法版本号会写进 `provenance`（`:142`）。增量与全量产出的算法版本号必须一致，否则历史行会与新行不可比。
- 🟡 **用户的批注/覆盖不能丢**：跑步侧增量明确要求保留人工标注，夜表侧目前没有类似机制 —— 实施前先确认夜表是否有下游人工输入，避免清空重算时误删。
- ⚠️ **不要顺手加"空表回填"**：设计文档（`docs/SLEEP_HRV_DESIGN.md:746`）声称服务端启动时有"夜表为空则回填"的路径，但当前代码中唯一的调用点就是 CLI，`apps/api/src` 内没有任何调用。这是"文档有、代码无"的既有落差，**属独立议题**：它有可能会被加在 API 启动路径上（`server.ts` 里那条带 `migrationPolicy: "refuse"` 的打开逻辑附近，`:481` 起），一旦失败会牵动启动可用性。本项不处理。
- 🟡 该改动会让"历史全量"与"新增增量"两条路径长期并存，建议补一条**等价性回归**常驻在测试里（而不是一次性人工比对），否则以后任何一次算法调整都可能悄悄让两者分叉。

**验收标准**
- 上述逐行等价性断言通过（建议做成自动化断言，不是人工看）。
- 增量场景下 `canonicalize_nights` 阶段耗时相对全量有可测下降 —— 用**既有的阶段计时管道取数**（阶段统计已在 `import-worker.ts:1484-1489` 与 CLI 的 `timedStage` 里收集，不需要新插桩）。
- 跨日边界用例：18:00 之后入睡、跨 00:00、纯午睡、只有 InBed 无 Asleep（该日应计入拒绝计数）四类都必须有断言。

**回滚**：`cli.ts:320` 改回不传脏集合即退回全量语义；夜表本身可由下一次导入重建，无需备份回滚脚本。

### OPT-4 打包体积腾出预算空间 · P1

**现状**（`apps/web/scripts/check-bundle.mjs:6-12`，`apps/web/vite.config.ts:11-15`）
预算为 charts 450 KiB / index 250 KiB / css 100 KiB。charts 是**手动分块**（把整个图表库固定成一个 chunk），实测 409,047 B = **88.7%**。

🔴 **先纠正一个被文档误导的方向**：外部文档建议"对 `RoutePlot`、趋势图做动态 import 切分"。但 `RoutePlot` **已经是**独立懒加载 chunk（产物里是 `RoutePlot-*.js`，仅约 2.9 KB），且它是手写 SVG、**不依赖图表库**。所以按文档的建议做，动的是一块本来就不占预算的产物。真正吃掉预算的是那一个整包图表库 chunk。

**改动要点**（按性价比排序，先做前两步）
1. **先判定这是"首屏问题"还是"预算余量问题"**：核对该 chunk 是否进入初始加载路径，还是只被懒加载页面引用。若全部消费者都是懒加载，则 88.7% 属**未来余量告警**，不是当前用户体验回归 —— 这会直接决定后面该投入多少。
2. **压缩实际用量**：审查图表库的引入方式（是否整包引入、是否可用更细的具名引入、次要页面能否改用更轻的渲染方式）。
3. **再谈拆分**：若确需拆分，注意手动分块规则会把依赖强制打包在一起，拆得不合适反而造成重复代码或引入新的共享 chunk。
4. **最后才考虑调预算**，且必须在同一次变更里给出理由与新的上限依据。

**预期收益**
目标是把 charts 占用从 88.7% 降到 80% 以下（约再腾出 45 KiB），恢复后续功能扩展的空间。注意：当前 `dist/` 是 **09-19 的产物**，做之前必须先重跑构建取当期数值，别拿旧数据下结论。

**风险与注意事项**
- 🟡 **改分块规则会让预算脚本"匹配不到产物"而直接失败**：预算按文件名正则匹配，若产物命名或拆分方式变化导致某个正则匹配为空，检查脚本会报"没有匹配到任何产物"并中断构建。改分块时必须同批更新预算规则。
- 🟡 动态 import 会改变首屏加载瀑布与 chunk 数量，需要确认没有把关键路径推到二次往返。
- 🟡 必须与桌面回归一起做（`e2e:web`），涉及 1024–1180px 的布局规则属桌面依赖段，改动共享 Web 代码时要保住它。

**验收标准**
- 类型检查、构建、桌面 E2E 通过；预算检查通过且 charts 有可陈述的下降。
- 首屏请求数与总体积不得恶化（用构建产物的引用关系核对，而不是只看单个 chunk 体积）。

**回滚**：`vite.config.ts` 与预算脚本同批 revert。

### OPT-5 + OPT-6 队列重试上限与优先级 · P2（合并一个 v23 迁移）

两项都往 `recompute_jobs` 加列，必须合并成一次 schema 发布。

**现状**
- 队列表结构见 `packages/storage-sqlite/src/database.ts:446-462`，**无优先级列、无重试计数字段**。
- 取任务按"创建时间 + 行号"排序（`packages/storage-sqlite/src/recompute-job-repository.ts:48-53`），单 worker 串行消费。
- 崩溃恢复（同一文件 `:105-162`）会把未请求取消的中断任务重新排队（`:137`），且**没有任何次数上限**；恢复时会先把关联的 feature/model run 统一标记失败（`:128`）。
- 轻量刷新任务确实走同一张队列（`packages/application/src/service.ts:77-79`）。

**改动要点**
1. 追加迁移 **v23**：为队列表加"重试次数"与"优先级"两个可空/带默认值的列。
2. 取任务时按"优先级优先、其次原有顺序"排序，保证原有行为在默认优先级下**完全不变**。
3. 恢复中断任务时递增重试次数，超过上限（建议 3）转终态失败并记录原因；异常信息应能区分"被外部中断"与"反复崩溃"。
4. 明确哪些任务类型配高优先级（例如只追加当日快照的轻量刷新），并在注释里写清理由，避免以后被随意调高。

**预期收益**
- 重试上限：把"崩溃 → 重启 → 重新拉起同一个必崩任务"的死循环变成"三次后停在失败态"。当前没有任何上限，这是**可用性级别的护栏**，不是性能优化。
- 优先级：交互式的轻量刷新不再被长全量重算堵在后面，用户改一条训练标注后的等待从"等全量跑完"变成"插队执行"。

**风险与注意事项**
- 🔴 **迁移铁律**：只能**追加** v23，**绝对不能改动历史迁移的建表语句**（改了会让所有既有库永久打不开）。新列必须对既有库幂等（带默认值，允许旧行不填）。
- 🔴 **迁移不在启动时执行**：API 与 worker 以"拒绝迁移"策略打开主库，存在待执行迁移时进程会以 **78** 退出。发布顺序必须是"先在位（代码兼容新旧两种表结构）→ 再跑迁移 → 再启用新行为"。部署闸门 = 迁移命令报出空待执行列表。
- 🟡 **重试上限的副作用**：真实的"可恢复中断"（例如内存不足导致的中断）在第二次可能就成功。上限设 3 且只在"无进展"时累计，比"任何中断都计数"更稳。同时注意恢复流程会先把关联 run 标失败，重试时需要重新建立关联记录，别复用脏 id。
- 🟡 **优先级会引入饥饿反转**：持续到达的高优先级任务会把长任务永久压在队尾。要么给长任务也留一条通道，要么设"等待时长超过阈值即升权"，并在方案里写明选哪种。
- 🟡 取任务逻辑在一个立即事务里（`BEGIN IMMEDIATE`），加排序字段后要确认索引仍能命中，避免退化为全表排序 —— 现有索引是"状态 + 创建时间"，新增排序维度需评估是否补索引（补索引也走同一次迁移）。
- ⚠️ 默认优先级与默认重试次数必须让**现有测试的全绿基线保持不变**；任何需要改既有测试预期的改动都说明语义被动过了，需要重新评审。

**验收标准**
- 迁移后：既有库可以正常打开、旧任务行可读、`data:migrate` 报空待执行列表。
- 重试：构造一个必然失败的任务，确认三次后停在失败态，且事件表里每次重试都有记录 —— 用**突变测试**验证（去掉上限应立即复现无限排队）。
- 优先级：同一时刻插入轻重两类任务，确认轻任务先被取走；把排序里的优先级去掉，对应断言必须变红。
- 既有 node 侧与 web 侧门禁分别保持全绿（报数方式见第 5 章）。

**回滚**：代码 revert 即可；新增列对旧代码不可见，可容忍。**不要**为回滚写删除列的迁移。

### OPT-7 控制库并入备份束 · P3

**现状**
备份/恢复组件只拿到主库路径（`apps/api/src/server.ts:442-451`），控制库是另一个文件（`server.ts:99`），由移动目标存储独占管理（`apps/api/src/mobile-goals.ts:175`）。备份组件里处理"成组"的函数处理的是数据库的 **预写日志附属文件**，**不是**第二个数据库（`apps/api/src/maintenance.ts:467`）。项目自己的文档也承认这条没做完（`docs/IOS_CLOUD_REVIEW_PLAN_2026-09-07.md:5`），部署手册只把它写成人工提醒（`deploy/n100/README.md:172`）。

**改动要点**
把两个库作为**一个备份单元**处理：命名上可配对，恢复时作为一组校验与置换；恢复完成前不得让读取方看到"主库已换、控制库未换"的中间态。要考虑控制库路径可由环境变量指向不同目录的情况，备份目录策略需要覆盖这点。

**预期收益**
消除"还原历史备份后，控制库里锁定的训练 Session 指向主库不存在的记录"这一类不一致。本机控制库仅 24 KB，体积不是问题，**一致性才是目标**。

**风险与注意事项**
- 🔴 **这是本方案里唯一触碰"恢复语义"的项**，风险最高。恢复链路包含预检、试运行迁移、外键校验、自动前置备份、读租约排空与原子置换等多步（`maintenance.ts:257-383`），扩展它时**每一步都要同时覆盖两个库**，漏一步就会产生新的不一致。
- 🔴 **一致性边界要显式设计**：两个库无法在同一瞬间被快照（除非先停写）。要么接受"先主后控"的微小窗口并在文档里写明，要么走停写窗口。不要假设"反正是本地单用户就没事"。
- 🟡 **不要顺手改 `/v1/mobile/today` 的四态语义**。控制库里的目标/锁课会参与移动端"今日"聚合（同步态、覆盖态、恢复评估、建议四态互不替代），改动备份恢复时容易顺手碰这些字段解读。本项只做备份与恢复，不碰端点语义。
- 🟡 若为了暴露"联合快照"而新增写端点，必须同步登记到写端点白名单（两条名单互斥，纯读端点不登记）。**建议不新增端点**，复用既有备份/恢复入口。
- ⚠️ 需要一次真实的恢复演练作为验收，不能只读代码。演练必须在副本环境做。

**验收标准**
- 备份 → 改变控制库内容 → 恢复 → 控制库内容回到备份时点，且主库与控制库之间无悬挂引用（锁定的 Session 在主库中存在）。
- 恢复失败注入：在置换阶段人为失败，确认两个库都回到恢复前状态（或都停在明确可恢复的状态），不出现"一新一旧"。
- 演练记录写入交付物，含明确的回滚脚本路径。

**回滚**：本项改动前后都要保留原有单库备份/恢复路径可用，回滚 = 停用联合模式。

### OPT-8 效率指标口径（心率漂移） · P3

**现状**
效率指标用的是整段平均心率（`packages/features/src/index.ts:557-558`），包内无任何漂移补偿逻辑。外部文档指出的生理学问题成立：稳态长跑后半段因脱水与体温上升，心率自然上浮，整段平均会低估这类课次的效率。

**改动要点**
引入"前半程稳态段"作为效率基准，或把漂移率作为稳定性质检因子（漂移过大时降低该次课次的证据权重，而不是直接惩罚效率值）。**建议优先做后者**——质检因子只影响权重、不改效率数值本身，冲击面小一个数量级。

**预期收益**
减少长距离稳态跑被误判为"效率偏低"的情况，改善长距离训练者的现时跑力曲线平滑度（这类误判会集中出现在每周长课附近）。

**风险与注意事项**
- 🔴 **这会改数值口径**：效率是现时跑力的输入维度之一，改它等于改 CA 序列，进而触发模型重算与模型版本门禁（`recompute-pipeline.ts:217-222`，8 项失败判据见 `model-run-repository.ts:235-242`）。所以本项**不是纯技术改动，而是数据口径变更**，必须先过口径评审再动手。
- 🔴 **必须准备好门禁结果预期**：CA 均值偏差、P95 偏差、终态真实跑力差值、状态变化率等都有阈值拦截。改完若门禁失败，是"该改法不对"还是"阈值需要按新口径重定"——这个问题必须在动手前回答，否则会被卡在中间态。
- 🔴 **门禁阈值只能当参数，不能当验收标准**。验收标准应是"长距离稳态课次的效率值不再系统性低于同配速的短课次"这类**可复现的业务判据**，阈值只是运行参数。
- 🟡 漂移本身也受气温、湿度、坡度影响，而这些已有惩罚项在用。新增漂移因子时要确认不与既有环境惩罚**重复惩罚**同一现象（这是"两个都对但叠加起来就错"的经典陷阱）。
- 🟡 历史数据不可重算到"当时没有漂移修正"的状态，一旦改口径，**历史曲线会出现一次阶跃**。需要决定并记录：是接受阶跃，还是保留旧口径的历史段。这个决定要写进文档，否则以后没人说得清曲线为什么断了一截。

**验收标准**
- 长距离（>20 km）稳态课次的效率分布与同配速短课次的差异显著收窄，且该结论在**全量重算后的真库**上验证（不是抽样估算）。
- 模型版本门禁通过，且门禁的 8 项指标逐项留档，含改动前后对照。
- 历史阶跃的处理方式在文档里明确写出。

**回滚**：revert 代码 + 恢复到变更前的模型版本（旧模型 run 仍可回放）。

### OPT-9 时区入口收敛 · P3（分两步，第一步零行为变化）

**现状**
默认值与硬编码散布至少 9 处：两个包的函数默认参数（`packages/training-load/src/index.ts:326`、`packages/health-export-parser/src/canonicalize-nights.ts:148`）、API 层写死（`apps/api/src/server.ts:632`、`mobile-read.ts:628`、`data.ts:85`）、前端写死（`apps/web/src/format.ts:55` 与 `:64`、`apps/web/src/ios/shared.tsx:55`）、以及**一处 SQL 里写死的固定偏移**（`packages/storage-sqlite/src/read/trends-read-repository.ts:106`）。

🔴 **关键事实**：全仓检索**没有任何时区环境变量出口**（此前设计文档里提过的方案从未落地）。所以这不是"默认值可被覆盖"，而是**真硬编码**。

**改动要点（严格分两步，不要合并）**
- **第一步（零行为变化）**：统一入口 + 显式传递。默认值仍然是上海，所有调用点显式传入，消除"靠默认参数生效"的隐式路径，并把那处 SQL 固定偏移改为按记录自身时区字段关联或参数化。此步**不改变任何输出**。
- **第二步（真正可配置）**：引入环境变量出口，并处理"换时区意味着日历切分点改变"的全部后果。

**预期收益**
第一步的收益是**可维护性与可测性**：消除隐式默认，让夏令时/跨时区用例可以在测试里被构造；同时消掉 SQL 层的固定偏移（这是唯一无法通过传参绕开的一处）。第二步的收益只在真有非上海用户时才兑现。

**风险与注意事项**
- 🔴 **第二步的影响被严重低估**：时区决定日历天归属，而日历天是夜表、日度训练指标、快照、恢复评估的共同主键维度。换时区会让同一份原始数据重排到不同的日期上，等于**全量数据重新归属** + 全量模型重算。因此第二步必须当成一次数据迁移来规划，附带回滚脚本与前置备份。
- 🔴 **第一步必须做到"输出零变化"**：验收方式是改动前后对同一份输入的关键输出**逐字节一致**（夜表、日度指标、趋势切分都要覆盖）。做不到就说明有调用点被漏掉，或者某处传入的值与默认值不等价。
- 🟡 **夏令时**：上海无夏令时，现有测试覆盖不到。第一步就该补一个使用夏令时地区的对照用例（这不影响生产行为，只是让第二步有地基）。
- 🟡 前端也硬编码了时区（`format.ts` 与 iOS 共用形状的 `shared.tsx`）。若只改后端，会出现"后端按新时区切分、前端按上海展示"的错位，必须同批处理。
- 🟡 第二步会牵动移动端的"数据截至某日"与陈旧度提示语义，属移动端聚合端点的既有约定，改动要单独评估。

**验收标准**
- 第一步：关键输出与改动前逐字节一致；全仓检索不再出现"靠默认参数生效"的调用路径；SQL 层固定偏移消失。
- 第二步：单独立项，需要"换时区后全量重算 + 门禁 + 历史阶跃处理"三件事一起给方案。

**回滚**：第一步 revert 即可；第二步需回滚脚本 + 备份（同数据迁移规格）。

### OPT-10 轨迹渲染节点 · P3（不推荐按文档的前提做）

不是"加抽稀"（已经抽过了），而是减少渲染元素数量。注意一个现有功能约束：**线段按速度着色**，把多段合并成单条路径会**丢掉速度色带**。所以可选的做法只有两类：把相邻同色段归并成少量路径（保住色带、减少节点），或者维持现状。

**风险与注意事项**
- 🟡 **不要动公里标记的输入**：公里标记是基于原始点列累计算出来的（`RoutePlot.tsx:43-69`），若在渲染前对点列抽稀，标记落点会漂移。任何改动都要保证标记仍基于原始序列。
- 🟡 与 OPT-4 无关：该组件已是独立懒加载产物且不依赖图表库，别把它和打包预算混在一起。
- ⚠️ 综合判断：**本项建议只做"加断言 + 加注释"，不做渲染重构**，除非有实测的性能问题。

**验收标准**
- 若只加断言：改动一个固定的上限常量应导致断言失败（突变测试）。
- 若做归并：轨迹视觉与色带在 ≥3 条真实路线上目视一致，公里标记数量与位置不变。

**回滚**：单组件改动，revert。

## 5. 实施纪律（改之前先过一遍）

1. **迁移只增不改**：只能追加 v23；**绝不改动历史迁移的建表语句**（改动会让所有既有库永久打不开）。新列必须带默认值、对旧行幂等。
2. **迁移不在启动时执行**：API 与 worker 以"拒绝迁移"策略打开主库，有未执行迁移时进程直接退出。发布顺序 = 代码先兼容新旧结构 → 跑迁移 → 再启用新行为；部署闸门是迁移命令报出空待执行列表。
3. **门禁分开报**：node 侧与 web 侧必须分开陈述，web 侧单独跑。合并脚本当前以非零码退出是**本机既有的资源问题**（web 侧 worker 起不来），**不得当作代码回归的判据**。现行基线：node 侧 740 / 736 通过 / 0 失败 / 4 跳过；web 侧单跑 13 个文件 / 84 个用例。跨次比较用例总数没有意义。
4. **实验只在只读副本上做**：本机 `var/rai.sqlite` 是 325 MB 的真实健康库。OPT-3、OPT-8、OPT-9 第二步都必须先在副本上跑通并准备回滚脚本。
5. **Rust 引擎要双配置各跑一次**：涉及导入链路的改动（OPT-2、OPT-3）必须在启用 Rust 与回退 TypeScript 两种配置下各跑一次导入，比对结果一致。观察口是数据摘要端点的 issues 列表与运行时写路径不变量；注意不变量里"墓碑计数必须为 0"这类断言**不成立**（正常导入会有墓碑），违规定义以文档为准。另注意"API 起来了"不等于"引擎生效了"，判据是读运行中进程的环境变量。
6. **断言必须能突变到红**：OPT-3 的等价性、OPT-5 的重试上限、OPT-6 的排序、OPT-10 的上限常量，都要实际把它改坏、确认对应断言变红，排掉"恒红"与"改坏后其实编译不过"两种假绿。拿界面回归当证据时源码必须冻结。
7. **阈值不是验收标准**：门禁阈值、效率阈值、内存上限都只是参数。验收标准必须是可复现的业务判据（例如"增量与全量逐行等价"），否则等于把参数当结论。
8. **改完对齐文档**：`docs/SLEEP_HRV_DESIGN.md`（含那条"接受浪费的全量重算"的结论）、`docs/DATABASE_DESIGN.md`（迁移到 v23）、`README.md` 的相关描述需同批更新，否则下一轮审查还会拿旧结论当依据。
