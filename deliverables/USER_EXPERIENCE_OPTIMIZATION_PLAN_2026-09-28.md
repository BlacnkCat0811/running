# RAI 用户体验优化实施方案

> 日期：2026-09-28
> 性质：待实施方案，不代表功能已交付。本次只新增本文档，不修改产品代码。
> 核验基线：本地 `main @ eb5965d`；实施开始时须重新检查 HEAD、工作区与实际部署版本。
> 产品方向：日常训练在原生 iOS 完成，深度分析与管理在桌面 Web 完成。
> 核心修订：首页不是同步监控面板。正常时不打扰，影响用户当前任务时就地提示，诊断细节按需查看。

## 1. 决策摘要

### 1.1 本轮明确采用的原则

1. 首页不常驻最近同步时间、数据截至日期、任务队列、缓存时间或同步阶段。
2. 正常后台同步保持安静；正常完成不弹窗、不常驻成功卡。
3. 异常先判断是否影响当前任务，再决定提示位置，不能把所有后台失败升级为首页警报。
4. 不隐藏会误导用户的限制：离线旧建议不能伪装成今日实时建议，未保存不能显示已保存。
5. 数据明细进入“设置 → Apple 健康 → 数据与同步详情”；训练建议的依据进入建议详情。
6. 优先完成训练反馈闭环；预测、导出、通知分阶段交付。
7. 不为了功能对齐，把 Web 管理能力全部搬到手机。
8. 不新增手机端评分算法，不修改冻结的窄屏 Web，不新增独立 Watch App。

### 1.2 对上一版方案的纠正

- “透明”不等于把技术状态摆在首页；透明应体现为结果可信、错误可理解、必要时可追溯。
- 现有首页已经以 `TechSyncStatus(showsHistory: false)` 隐藏正常历史状态，并非完全没有降噪设计；应在此基础上收敛，而不是重建状态系统。
- 现有 `TechFreshnessBanner` 仍会在首页因离线、同步异常或恢复缺测出现，且包含数据明细展开项，这是本轮应调整的重点。
- “缺少恢复数据”不等于“同步失败”；没有新跑步也不等于数据过期。
- `waiting_engine` 不应一律翻译为“完成后会自动更新”：只有确有可恢复任务和重试机制时才可承诺，否则应说明更新暂不可用并提供检查入口。
- WorkoutKit 调度回读成功不应直接宣称“实体手表已收到”；应使用与实际证据一致的文案。
- 测试通过不能证明预测准确、实机后台可靠或线上服务健康。

## 3. 产品信息架构

### 3.1 iOS：以用户任务组织

| 页面 | 主任务 | 不承担的职责 |
|---|---|---|
| 今日 | 看懂今天安排、进入训练计划、查看跑后摘要 | 同步监控、原始数据审计、模型管理 |
| 训练 | 找到一次训练、看详情、填反馈、纠正记录 | 大量高级模型参数 |
| 统计/趋势 | 看进步与训练结构，进入预测摘要 | 模型训练/激活 |
| 训练计划（二级） | 预览、确认、调整未来计划、发送系统训练日程 | 用未同步推断漏课 |
| 设置 | 服务连接、Apple 健康、同步详情、缓存、隐私导出 | 替代日常训练首页 |

本期不改五个一级入口，不做大规模导航重构。先把主流程完成率和理解成本验证清楚。

### 3.2 桌面 Web

保留深度分析、数据审计、导入备份、模型管理、高级筛选与完整编辑。核心事实及写入结果与 iOS 同源，但页面无须同构。

Web 历史 iOS 壳与窄屏兼容范围冻结：不重新设计、不删除、不作为新原生体验的对齐对象。桌面验证 1440×900，并覆盖 1024px 最小支持宽度；不新增移动 Web 回归。

## 4. 核心修订：安静、可信的数据体验

### 4.1 四层信息分配

| 层级 | 呈现内容 | 触发条件 |
|---|---|---|
| 首页正常态 | 训练与恢复业务内容，不出现同步时间和覆盖日期 | 有可展示内容且无阻断 |
| 相关卡片/当前操作 | 一句影响说明 + 最多一个主要动作 | 异常确实影响这张卡或这次操作 |
| 设置 → Apple 健康 | 连接状态、可重试同步、是否需要用户处理 | 用户主动查看；必要时设置入口加轻量标记 |
| 数据与同步详情 / 建议依据 | 精确时间、覆盖、阶段、结果及诊断 | 用户主动展开 |

全局只在“整个页面没有可用内容”时显示连接/首次导入引导。不能因一个恢复指标缺失而给整个首页加警告。

### 4.2 逐状态展示矩阵

| 场景 | 首页 | 操作反馈 | 详情/设置 |
|---|---|---|---|
| 正常、有新或无新数据 | 无同步横幅，无时间戳 | 无 | 保留最近成功记录 |
| 后台正在同步 | 不新增大卡，不打断阅读 | 用户未发起则静默 | 显示进行中 |
| 用户主动点击同步 | 原按钮转进行中，不另叠状态卡 | 完成显示一次短反馈；无变化用“已检查，没有新记录” | 记录此次结果 |
| 下拉刷新 | 使用原生刷新反馈 | 保持当前“刷新服务端页面”的行为；不偷偷启动全量健康导出 | 需要同步健康数据时给明确入口 |
| 短暂断网，有缓存 | 保留数据；涉及动态建议的卡片标“离线参考” | 写操作就地提示“连接后才能保存” | 网络详情 |
| 跨日旧建议 | 不冒充今日建议；相关卡显示“连接后查看今天的安排” | 不允许以旧快照确认今日计划 | 可查看历史内容与时间 |
| 一次后台失败，但现有内容可用 | 不全局警报，不抢占首页 | 无 | 在设置保留失败记录和重试入口 |
| 失败阻止确认计划/保存 | 在对应按钮或弹层说明原因 | “暂时无法确认，请连接后重试”；草稿保留 | 可进入连接检查 |
| 凭证失效且有确定证据 | 不弹模态拦截所有阅读 | 受影响处提示“服务连接已失效，请重新连接” | 定位服务连接设置 |
| 今日无睡眠/HRV | 恢复卡显示“今日暂无恢复记录” | 不报同步故障、不禁用所有训练操作 | 解释本次建议未使用哪些指标 |
| 首次使用、没有任何内容 | 简单引导“连接 Apple 健康，查看你的训练” | 用户主动授权/同步 | 提供只读权限说明 |
| 用户取消同步 | 不保留警告卡 | 原操作处一次性提示“已取消” | 保留可继续入口 |
| 服务端任务等待引擎 | 无关页面不提示 | 相关结果显示“更新暂未完成”；可恢复时说明稍后继续 | 暴露确切原因与下一步，不无限假进度 |
| 未找到刚跑完的记录 | 不推断用户没跑 | 训练页提供“找不到刚完成的训练？”帮助入口 | 检查记录、同步与读取权限 |

### 4.3 明细中的日期语义

“数据覆盖到哪一天”不作为一个笼统结论。改为各事实独立展示：

- 最近一次健康同步成功时间：来自已确认成功的同步状态。
- 最近一条已导入训练日期：不是所有历史训练完整的证明。
- 最近可用睡眠、HRV、静息心率日期：分别标明，不用一个最大日期代替。
- 当前建议生成时间与使用的业务日期：进入“为什么这样安排”。
- 缓存更新时间：只在离线/诊断详情使用，不冒充同步时间。
- 未知即显示未知，不用当前时间或 0 补齐。

### 4.4 展示策略实施方式

新增纯展示决策层（建议名 `UserDataNoticePolicy`，最终命名由实施 PR 确定）：

输入：现有同步阶段、网络/接口结果、是否用户主动发起、缓存业务日期、当前页面与操作、可恢复任务证据。

输出：`hidden / inline / blockingEmptyState`、展示位置、用户文案 key、主动作、可选详情入口、事件去重 key。

约束：

- 不新增第二套同步状态机，不改变 HealthKit 水位提交和重试规则。
- 网络失败、认证失败、接口部分失败分别处理；不把训练列表请求失败直接解释成所有数据都过期。
- 同一事件仅有一个主要提示，避免 `TechSyncStatus` 与 `TechFreshnessBanner` 重复。
- 后台状态变化不得自动弹窗或抢夺 VoiceOver 焦点；用户主动操作的结果可适当播报。
- 不仅用颜色表达错误。详情入口可发现，提示消失不等于诊断记录被删除。
- 不通过“距上次跑步超过 N 天”推断同步异常。
- 读取不到 HealthKit 数据不直接断言权限被撤销；只在有可靠证据时使用权限失效文案，否则用“暂未读取到记录，请检查”。

### 4.5 首页验收标准

1. 正常进入首页看不到同步时间、覆盖日期、缓存时间、任务阶段和常驻同步成功卡。
2. 后台同步从开始到结束，不增加或移除大块内容，不改变用户当前阅读位置。
3. 恢复缺测只影响恢复卡和建议依据，不产生全局故障条。
4. 同一异常最多一个主要提示，且能定位到有效操作。
5. 断网和跨日缓存不把昨天的动态建议标成今天可确认的安排。
6. 主动同步/刷新有明确结束状态；失败保留可用内容，不变成空白页。
7. 从设置中的 Apple 健康页能一步打开数据与同步详情。

## 5. 训练反馈闭环（优先交付）

### 5.1 用户流程

训练详情 → “记录感受” → 可选 RPE、备注 → 保存 → “反馈已保存”。

首页跑后摘要仅提供一个轻量入口，不弹出强制问卷。每次训练允许稍后填写、再次编辑、清空反馈。未填写不是负面状态。

首期只收集现有字段：RPE 1–10 整数、备注；类型纠正在“编辑训练”中提供。状态标签继续复用既有语义，不自行新增一套枚举。

不把“轻松/正常/吃力”等描述偷偷换算为精确 RPE；如果提供文字辅助，仍由用户确认数值。

### 5.2 技术前置：安全保存

当前 override 是整组字段写入，且服务端追加 revision 不等于已具备并发冲突检测。因此不能只加一张 iOS 表单就交付。

实施顺序：

1. 确认训练详情返回当前 override revision；无反馈时定义初始版本。
2. 扩展契约支持 expectedRevision，在业务事务内比对当前版本，冲突返回稳定 409 code。
3. Web、iOS、持久化命令执行路径使用同一校验；队列入队后真正执行时再次校验，不能只在提交时检查。
4. iOS 编辑部分字段时保留其他字段，包括 Web 已设置的模型参与、统计参与、协议与标签。
5. 优先复用现有 `/v1/commands` 与幂等键；重试同一次提交用原 key，用户再次修改用新 key。
6. 确认旧客户端兼容窗口：先后端增量发布、再两端更新；窗口内旧客户端仍可能覆盖，必须明确残余风险，不宣布全端冲突保护已完成。
7. 若采用命令队列，202 只显示“正在保存”；命令成功后才显示已保存，重算任务完成后才更新分析结果。
8. 保存后刷新训练详情、列表、相关统计；保存成功但分析未刷新显示“反馈已保存，分析稍后更新”，不重复提交。

### 5.3 离线和异常

- 本期不建离线业务写队列。允许保留编辑草稿，但不得显示已提交。
- 如持久化草稿，按 serverId/athleteId/datasetEpoch/训练 ID 隔离，复用受保护的本地存储；清缓存和切换账户规则明确。
- 响应丢失用幂等命令查询确认，不盲目再次追加 revision。
- 冲突保留输入，提示读取新版本；不后台静默覆盖另一端修改。
- 记录不存在时说明“这条训练已不可用”，不得自动创建同名训练。

### 5.4 编辑与排除

“排除模型评估”和“排除统计”是两个选择，必须解释影响，不能合并为含糊的“删除记录”。允许恢复自动判定；原始健康记录不因覆盖操作被删除。

### 5.5 验收

- 正常完成一次 RPE/备注填写无需离开训练详情；可用性试验目标为 20 秒内完成。
- 清空 RPE 与填写 0 不混淆；拒绝非整数和越界输入。
- iOS 保存不清除 Web 其他覆盖字段；双端冲突可被识别。
- 重试不重复落库；命令失败、重算失败和展示刷新失败分别呈现。
- 明确解释反馈的用途，不宣称每条备注都会改变明天的计划。

## 6. 计划—执行—设备闭环

### 6.1 观测结果的行动入口

沿用 observed/pending/unknown，不自动引入 missed，不用距离比例判定完整完成。

| 事实 | 用户文案方向 | 动作 |
|---|---|---|
| 已导入当天训练 | 已记录训练 | 查看当天训练、填反馈 |
| 有历史计划，暂未观察到训练 | 暂未找到对应训练 | 查看记录、检查同步 |
| 缺少历史计划快照 | 无法与当时计划比较 | 查看训练；不要求重生成过去计划 |
| 已导入部分跑量 | 已记录 X km | 看详情，不自动判断偷懒或训练质量 |

“是否按计划完成”的主动确认另立小项：现有 RPE/备注表单并不等于结构化完成回执。确需上线时增加计划 revision、训练关联、用户确认时间及可撤销状态，再接入展示；先不让它影响评分。

### 6.2 Watch 状态

分开呈现：计划已保存、已提交系统日程、调度回读已核验、尚需更新、设备不支持、未授权、失败。

- 调度回读只能证明对应调度结果，不能未经实机证据声称实体手表已收到或已执行。
- 今日记录到一次跑步不等于该处方逐段完成。
- 修改处方后提示“需要重新发送”，不要自动覆盖用户未确认的计划。
- 保留 preview/confirm 机制；打开预览不写库、不发手表。

验收：取消预览零副作用；确认失败不变更计划；无手表不引导无意义授权；同日期相似处方不会被误标成已核验的新版本。

## 7. 预测、导出与通知（后续批次）

### 7.1 iOS 预测摘要

入口放在比赛目标卡/跑步能力详情，不增加一级 Tab。复用服务端预测 DTO，展示目标距离、预测区间（接口提供时）、可信度/局限和依据。无区间时不自行伪造。

区分“目标成绩”与“预测成绩”；没有足够依据时显示暂不可估计，不补 0，不把估计当承诺。不做本地重新计算。模型准确性需要独立评估，不能由 UI 测试替代。

### 7.2 用户导出

首期：选定日期的训练摘要 CSV + 不含坐标的分享摘要；PDF、GPX 后置。

- 显式预览包含哪些字段；备注和健康指标不默认分享。
- 导出端点鉴权、日期范围和大小限制明确，不复用管理员整库备份作为用户导出。
- 默认无坐标、设备标识、令牌、内部日志；CSV 对公式型文本做安全处理。
- 分享仅用户主动触发；临时文件有清理策略，失败不留下公开链接。
- GPX 后续单独确认隐私规则；仅裁剪起终点不能宣称完全匿名。

### 7.3 通知

不是首期验收项。先完成 App 内的就地提示，再小范围验证通知价值。

第一批只考虑用户显式开启的训练提醒；同步异常默认在 App 内处理。若后续通知异常，必须持续阻断且确需用户操作，不因一次短暂后台失败推送。

要求：按场景授权、安静时段、去重、完成/撤销计划后取消过期提醒、时区变化处理。拒绝权限不妨碍核心功能。不承诺后台准点触达；远程推送和新后台机制需单独确认范围。

## 8. 数据隐私与生产可靠性

这是发布前核验，不是借体验优化重写后端。

- 检查线上匿名读取是否实际开放训练轨迹；默认方向为个人健康与路线私有，若需要公开展示，应使用单独的脱敏数据面。
- 改动鉴权前验证桌面 Web 的连接入口，避免关闭匿名读后正常用户无法访问。
- 查验当前部署版本、资源限制、引擎实际执行记录、失败及回退原因；环境变量仅证明配置意图，不足以证明每次任务实际使用 Rust。
- 全量恢复演练包含主库、控制库、运行时库、模型 artifact、必要导入资产与身份配置；检查旧锁课、目标和任务是否一致。
- 不在生产现场通过清库、重导入或重启来“顺便验证”；破坏性操作需独立批准。
- 性能先量测冷启动到可读内容、训练详情加载、保存响应和导入期间读取可用性，再定指标；不先承诺无证据的毫秒目标。

## 9. 实施工作包与依赖

以下时间仅用于排期，按一名熟悉仓库的开发者估算，包含基础测试，不含等待真机和业务确认的时间。发现契约/兼容性问题应重估。

| A1 首页降噪 | 展示决策层、就地异常、移除首页技术明细 | A0 | 2–4 人日 |

### 9.1 推荐 PR 拆分

1. PR-A：展示策略纯函数与状态测试，不改同步引擎。
2. PR-B：首页/设置接线、文案、无障碍与视觉验收，和 PR-A 配套发布。
3. PR-C：反馈契约及服务端并发/幂等保护，兼容旧客户端。
4. PR-D：Web 写入适配 + iOS 反馈入口及冲突处理。
5. PR-E：计划观测行动入口与 Watch 文案、实机证据。
6. 预测、导出、通知各自独立 PR 与验收，不阻塞前两阶段。

### 9.2 预计改动范围（仅规划，当前未修改）

- iOS 展示：`TechViews.swift`、`TechSyncStatus.swift`，按需要拆出同步详情和反馈组件。
- iOS 数据接线：`NativeAppModel.swift`、`APIClient.swift`、`APIModels.swift`。
- 反馈契约与写入：`packages/api-contracts`、`packages/application`、`apps/api/src/schemas.ts`、直接路由及命令队列。
- Web：`OverrideDrawer.tsx` 和桌面相关数据刷新/冲突提示。
- 测试：iOS 展示/模型门禁、API 契约/队列/运行测试、Web 组件测试。
- 默认不改 HealthKit 导出、水位提交、发布机制、评分核心、历史迁移、冻结移动 Web。
- 真需新增存储字段时追加迁移，禁止修改既有冻结 checksum 的迁移。

## 10. 验证与发布

### 10.1 自动化

按实际变更选择：

- `npm run typecheck`
- `npm test`
- `npm run build`
- iOS 变更必须 `npm run test:ios`
- 涉及 Web 桌面流程时 `npm run test:e2e:web`
- 不运行响应式或完整移动 Web E2E。

不要简单删除与旧首页结构相关的门禁。把断言改为新产品要求：正常态无时间戳、明细在详情可达、缺测不当成失败、重复提示被合并、旧建议不能确认。

### 10.2 关键集成用例

| 用例 | 必须结果 |
|---|---|
| 正常后台同步、无数据变化 | 首页不出现新状态卡、不滚动跳动 |
| 睡眠缺失但训练数据可用 | 无全局故障，可查看建议依据 |
| 断网跨日后打开 App | 不冒充今日实时建议，已缓存训练仍可读 |
| 认证失效 | 当前写操作阻止，草稿保留，可直达连接设置 |
| API 部分请求失败 | 未失败模块不被清空，不笼统显示全部离线 |
| 命令提交后断网重连 | 同一操作只落库一次，能恢复结果 |
| Web/iOS 同时改反馈 | 冲突可见，未编辑字段不丢失 |
| 反馈保存成功但重算失败 | 不回滚为“未保存”，说明分析状态 |
| 计划确认后刷新失败 | 明确已保存，不诱导重复确认 |
| Watch 未配对/拒绝权限/回读不符 | 三种可辨别结果，不虚报成功 |
| 切换服务/身份/数据 epoch | 无跨用户草稿、缓存或结果串用 |
| 导出含恶意公式备注 | CSV 打开不执行公式，不泄漏敏感字段 |

### 10.3 手工验收

- iOS 真机：HealthKit 首次授权、无数据、增量、后台后恢复、网络中断；不以模拟器门禁代替。
- Apple Watch 真机：实际可见日程与处方；对比 App 文案能证明的范围。
- 动态字体、VoiceOver、长中文错误消息；提示不依赖颜色、不抢焦点。
- 桌面 Chrome/Edge：1440×900 和 1024px；不扩展窄屏范围。
- 生产核验与本地测试结果分开记录。

### 10.4 发布与回退

1. 先后端兼容变更，再客户端；老版本仍存在时保留兼容窗口说明。
2. 第一阶段尽量仅改变展示，不动业务状态；保留同步详情的错误定位能力。
3. 单独记录每次发布的 commit、契约变化、手工验收和已知限制。
4. UI 可回退旧展示，但不能通过回退恢复“不安全覆盖”或虚假成功状态。
5. 数据变更只做向前兼容迁移；不可盲目回退数据库或清除用户反馈。
6. 若关键流程出现误判、丢反馈、错误成功提示，暂停扩大发布范围，先修复再继续。

## 11. 成功标准：以用户任务，而非功能数量衡量

这些是验收目标，不是已测得结果：

- 用户正常打开首页，能直接找到今日安排，不需要先理解同步系统。
- 用户能解释为什么暂时不能保存，并在一次跳转内找到处理入口。
- 用户填写反馈后能确认“是否保存”和“分析是否更新”，不必重复提交。
- 未同步、未跑、缺数据、计划不匹配不再混为一谈。
- 开启/关闭通知不影响训练主流程。
- 问题可追溯，但诊断信息不占据日常首页。

验证方式：先做覆盖首次使用、日常训练、离线和冲突的任务演练，记录完成时间、错误理解和重复操作次数；小范围真实使用后再决定是否投入通知或更多图表。默认不新增第三方行为采集；如需遥测，应先说明采集字段与隐私边界，不上传路线、健康原始值或备注。

## 12. 当前不做

- 不做首页常驻“最后同步 / 数据截至 / 队列 / 缓存”面板。
- 不做强制训练打卡、不默认判断漏课、不设置羞辱式提醒。
- 不重新实现评分、不因为页面对齐重构全部后台、不提前拆微服务。
- 不把新增标签或备注自动宣称为模型已消费的信号。
- 不把缺少历史计划的问题用“重新生成计划”假装修复。
- 不把队列接收成功、调度回读成功、备份存在分别当成业务完成、实体手表到达和恢复成功。
