审查日期：2026-09-25。基线提交：`49c9ef9`。

## 一、结论与边界

本轮将“App 端”按仓库当前产品边界解释为 `apps/ios` 的 SwiftUI 原生应用，追踪其依赖的 API、训练建议、周计划生成、控制数据库和既有 WorkoutKit 桥接。没有修改业务代码、真实健康数据库、Web 响应式区域或设备排期；仅新增本报告。仓库已有的未跟踪文件 `deliverables/PROJECT_AUDIT_2026-09-24.md` 保持不动。

**总体判断：基础设施比较完整，但“比赛目标 → 周计划 → 今日执行 → 手表同步 → 实际训练反馈”的业务闭环尚未贯通。当前优先级应是统一执行规则与状态一致性，而不是先做视觉重设计或扩展赛事类型。**

值得保留的基础：

- 业务计算留在 TypeScript 服务端，原生端负责展示、交互和设备能力，没有必要在 Swift 重写评分核心。
- 比赛目标已有新增、编辑、清除、版本冲突检查；只改比赛目标不替换周计划，是明确且合理的现有策略。
- 课表生成有结构校验、部分训练约束和确定性回退；结构化处方与距离重算已有较多回归。
- 手表同步已做本地调度器回读，并只登记确认过的日期；不应退回“调用返回就算成功”。不过，调度器回读不等于本轮已在真实手表端验证到达。
- 准备度已经明确声明“不等于目标成绩达成概率”；缺恢复记录也不被直接当成恢复不良。优化必须保留这些语义。

下文 P1 表示应先修的执行/数据一致性问题，P2 表示随后修复的交互、可解释性或测试问题；不是对真实用户伤害发生率的判断。

## 三、P1：优先解决执行与一致性

### P1-01：保存的逐日计划不是今日推荐的底稿

**事实与影响**

`decideNextSession` 根据负荷、恢复判断、剩余周量等重新选课，不读取当天 `storedWeekPlan`；`buildWeekPlan` 又把“今天”直接替换成该推荐。于是未来某天在计划页/手表里是休息、长跑或特定分段，到了当天即使没有恢复否决，也可能变成另一堂课。

这不是“恢复闸门按需调整原计划”，而是原计划没有进入今日选课输入链。它也解释了为什么当前编辑器干脆不让用户编辑今天。

**合成复现**：保持其他输入和 yellow 判定不变，当天存储为 `rest` 时，今日推荐仍是 `easy / 5 km`；将存储改为 `long_run / 12 km` 后，推荐完全相同。

**证据**

- `/Users/ta/running/apps/api/src/mobile-coach.ts:818–903`：今日选课。
- `/Users/ta/running/apps/api/src/mobile-coach.ts:1174–1235`：今天与未来日期采用不同处方来源。
- `/Users/ta/running/apps/api/src/mobile-read.ts:290–294`：先计算，再套用锁课快照。
- `/Users/ta/running/apps/ios/RAI/Skins/Technology/TechViews.swift:1940–1956`：今天不开放编辑。

**优化**：先明确产品语义。建议采用“当天已存处方 → 服务端负荷/恢复/比赛规则校验 → 保留或带原因调整 → 当天有效处方”。无已存处方时才走临时建议。保留原计划和调整后计划两份语义，不允许缺测本身触发降级。如果产品坚持每天完全重算，则应明确叫“未来参考安排”，不能让用户把它理解为承诺执行的周计划。

**验收**：无调整条件时，休息日、长跑和自定义间歇结构跨日后保持；发生调整时，首页、详情、手表使用同一有效处方，并给出具体调整原因。

### P1-02：比赛目标没有成为周计划的确定性约束

**事实与影响**

比赛信息会进入 LLM 提示词，也会改变今日倒计时、减量标记及部分今日建议；但周计划验证器没有比赛日期输入，回退模板也没有比赛参数。修改比赛目标保留既有周计划本身不是 bug；问题是连显式重新生成时也没有统一的比赛约束。

**合成复现**：以 2026-09-25 为生成日，目标为 2026-09-27 半马、周目标 40 km、质量课上限 2、不配置 LLM。设比赛与不设比赛生成的课表完全相同，**2026-09-27 比赛日被安排 interval / 7.9 km**；同一目标的比赛卡却显示 `taper: true` 和现有减量文案。这是两个输出路径不一致，不是本报告对个人训练量的建议。

**证据**

- `/Users/ta/running/apps/api/src/weekly-plan-prompt.ts:93`：提示词已有赛事信息。
- `/Users/ta/running/apps/api/src/weekly-plan-service.ts:110–119,147–157`：验证器、回退模板未收到比赛参数。
- `/Users/ta/running/apps/api/src/weekly-plan-validate.ts:103–113`：约束输入没有比赛日期/阶段。
- `/Users/ta/running/apps/api/src/mobile-coach.ts:1137–1169`：比赛卡及减量标记。

**优化**：建立服务端统一赛事上下文，覆盖备赛、临赛、比赛当天、赛后、已过期状态；由确定性政策决定允许的训练类型、量和日期安排，LLM 只在这些边界内组织处方，回退模板同样受约束。具体训练政策与阈值另行评审，不在 UI 或提示词中临时硬编码。比赛保存后提示“哪些日期受到影响”，让用户预览、确认重排，不静默覆盖周计划。

**验收**：同一目标下模型生成、模板回退、手工编辑和设备导出遵循同一比赛政策；覆盖赛前、比赛日、赛后、修改/清除目标及目标已过期。

### P1-03：手工编辑绕过周计划约束

**事实与影响**

生成接口会执行质量课上限、轻松占比及周量约束；`PUT /v1/mobile/goals` 直接进入存储归一化，主要保证单日结构/范围，没有同等的整周校验。用户设置“质量课上限 0”后，仍可把未来日期改成质量课，并正常保存。

**合成复现**：周目标 10 km、质量课上限 0，提交 7 个 tempo 日期；保存成功，返回 **7 堂质量课、合计 67.9 km**。这是隔离存储路径复现，不是对真实用户数据或 App 点击流程的实测。

**证据**

- `/Users/ta/running/apps/api/src/server.ts:1126–1141`：手工保存路径。
- `/Users/ta/running/apps/api/src/mobile-goals.ts:186–222,661`：写入与逐日归一化。
- `/Users/ta/running/apps/api/src/weekly-plan-validate.ts:517–548`：生成路径才应用的强度约束。
- `/Users/ta/running/apps/ios/RAI/Skins/Technology/TechViews.swift:1985–1999`：任意未来行均可选择质量课。

**优化**：抽取可复用的领域校验，覆盖生成、手工变更和设备导出。先区分“硬限制”和“用户可确认超出的软目标”；对于允许覆盖的软约束明确警告并记录原因，禁止悄悄忽略或悄悄改写。校验窗口需与下文的自然周/滚动周定义统一。

**验收**：同一非法课表从不同入口提交得到同等处置；上限为 0 的语义在保存后仍成立，或必须经过产品定义的显式覆盖流程。

### P1-04：已确认的保存可被较早发起的刷新覆盖

**事实与影响**

`refreshAll` 只有“已经在刷新就返回”的布尔门控。保存成功后先写入新 goals，再请求刷新；若此时有旧刷新在途，新刷新直接跳过，而旧刷新随后无版本比较地覆盖新状态和缓存。

**生产模型 + 网络替身复现**：旧 GET 返回 revision 12，延迟 300 ms；PUT 立即确认 revision 13。输出为：

```text
saveAcknowledged=true
immediatelyAfterSaveRevision=13
finalRevision=12
raceDisappeared=true
```

服务端新目标没有因此被删除，但 App 在提示保存成功后显示旧目标，缓存也可能被写回旧版本。重新生成成功后的刷新同样使用这条机制，需一并处理。

**证据**

- `/Users/ta/running/apps/ios/RAI/NativeAppModel.swift:139–181,202–213`：刷新门控及应用返回值。
- `/Users/ta/running/apps/ios/RAI/NativeAppModel.swift:461–483`：保存确认和后续刷新。
- `/Users/ta/running/apps/ios/RAI/NativeAppModel.swift:620–630`：生成后的刷新。
- 复现日志：`/tmp/rai-plan-race-audit.jSAVPW/model-repro.log`。

**优化**：同一服务/数据域内，goals 版本不得倒退；引入 mutation epoch 或相应请求所有权，写入成功使写入前的读结果失效。对于没有可比较 goals revision 的 today/workoutPlan，用统一快照标记或写后必达的合并刷新；不能只比较时间字符串。重排中收到刷新请求应排队合并，而不是永久丢弃。

**验收**：慢 GET/快 PUT、慢 GET/快生成、连续保存、切服务器、取消请求及局部刷新失败；已确认目标不得回退。保留现有 configuration/cache scope 隔离。

### P1-05：旧锁课需要调整时，App 没有可达的重锁入口

**事实与影响**

服务端会保留今天的锁课快照；当原判断为 green、新判断为 red 时返回 `relockSuggested=true`。原生 DTO 解码了该字段，但界面没有消费它，所有入口在 `lock.present` 时禁用；模型支持 `relock: true`，没有 UI 调用。

**合成复现**：最新计算结果是 `rest`，原快照为 `interval`；服务端返回 `relockSuggested=true`，有效课程仍为 `interval`。保留锁定是一种既有设计，缺陷是需要重新确认时用户没有可达操作。

**证据**

- `/Users/ta/running/apps/api/src/mobile-coach.ts:1251–1288,1305–1316`。
- `/Users/ta/running/apps/ios/RAI/Skins/Technology/TechViews.swift:400–405,1608–1611`。
- `/Users/ta/running/apps/ios/RAI/Skins/Technology/TechLockSheet.swift:43–47`。
- `/Users/ta/running/apps/ios/RAI/NativeAppModel.swift:497–518`。

**优化**：显式区分“已锁定且仍适用”和“已锁定但需重新确认”；展示旧课与最新建议的差异，接通现有重锁 API。服务端可补充新的候选处方和调整理由，避免 UI 只能再次展示旧 `nextSession`。重锁后同步更新可执行周计划，并提示手表需要同步。

**验收**：锁课后判断变化可在 App 内完成预览、确认、刷新；不要求用户清库、改日期或去其他客户端操作。

### P1-06：零项可下发时，手表旧课表无法从当前界面撤回

**事实与影响**

桥接层已经实现“可执行集合为空时，移除本 App 原有排期并回读”的逻辑；但 UI 在 `schedulableCount == 0` 时直接禁用唯一同步按钮。原来有排期、后来全改休息/失效时，必要的空集合同步无法从页面触发。

**证据**

- `/Users/ta/running/apps/ios/RAI/Skins/Technology/TechViews.swift:1839–1845`。
- `/Users/ta/running/apps/ios/RAI/WorkoutKitBridge.swift:210–234`。

**优化**：把同步定义为“让设备排期与当前有效计划一致”，而不只是“新增 N 项”。区分新增、更新、撤回，零项时仍应有明确的撤回操作与结果。保留调度器回读机制，避免把清空失败描述成已撤回。

**验收**：先同步有课表，再把全部未来日改为休息，App 可撤回并验证空排期。此项是确定的代码路径缺口，实际 Watch 效果需真机验收。

### P2-01：自然周展示与未来七天生成/同步混用

- **复现**：2026-09-25 生成和设备导出包含 09-25 至 10-01；页面“7 天训练安排 / 本周”展示 09-21 至 09-27，未来四天不在该总览里。
- **证据**：`/Users/ta/running/apps/api/src/weekly-plan-service.ts:17–24,80`；`/Users/ta/running/apps/api/src/mobile-read.ts:367–421`；`/Users/ta/running/apps/ios/RAI/Skins/Technology/TechViews.swift:1683–1708`。
- **优化**：保留自然周作为进度统计口径；把可执行计划明确叫“未来 7 天”，支持跨周查看。服务端返回窗口起止日期，App 不自行猜测。同步确认页列出将变化的所有日期。
- **验收**：周五生成、周日进入、周一跨周及跨月时，展示窗口、生成结果、可编辑范围和设备变更列表一致；“周目标”与“滚动窗口合计”不能混算。

### P2-02：距离输入可编辑，但部分训练类型不会按输入保存

- **复现**：tempo 距离由 9.7 km 改为 12 km，服务端仍返回 9.7 km；这是固定剂量处方的既有规则，API 测试甚至明确要求忽略该距离输入。App 却对所有类型提供相同输入框，最后统一显示保存成功。
- **证据**：`/Users/ta/running/apps/ios/RAI/Skins/Technology/TechViews.swift:1985–1999,2054–2071`；`/Users/ta/running/apps/api/test/mobile.test.ts:1088–1133`。
- **优化**：easy/recovery/long_run 才显示距离编辑；rest 不提供距离输入；tempo/interval 显示由结构计算的只读总量。后续如开放结构编辑，应编辑组数、工作段/恢复段等真正被服务端接受的参数，并预览重算结果，不伪造一个可编辑的总距离。
- **验收**：所有可编辑字段都实际生效；服务端调整了结果时有差异提示，不能只说“已保存”。

### P2-03：刷新和冲突会无条件重置正在编辑的周计划

- **事实**：`native.goals.revision` 变化就调用 `loadDraft()`，没有 `editing/isDirty` 保护；健康同步完成会触发全量刷新。并发冲突时模型自动载入最新 goals，也会触发该草稿覆盖。比赛编辑器已有开窗版本快照，而周计划保存读取的是保存时的当前版本，两者不一致。
- **证据**：`/Users/ta/running/apps/ios/RAI/Skins/Technology/TechViews.swift:1653,2045–2069`；`/Users/ta/running/apps/ios/RAI/NativeViews.swift:62–65`；`/Users/ta/running/apps/ios/RAI/NativeAppModel.swift:431–445,487–490`。
- **优化**：建立带 `baseRevision`、原始值、草稿和 dirty 状态的编辑上下文。外部变更时保留草稿，展示冲突差异；用户明确选择重载、保留或合并。保存中的编辑、取消、导航离开也需要统一规则，避免出现“取消”被理解为取消已提交写入。
- **验收**：编辑过程中健康刷新、另一客户端更新、409 返回都不丢草稿；保存必须携带开窗时的基线版本。

### P2-04：重新生成直接覆盖，只在事后说明损失

- **事实**：点击立即发起生成并写入，覆盖已有结构/说明的警告在成功响应里才出现。生成、编辑与手表同步也没有共用操作状态，可能同时针对不同快照工作。
- **证据**：`/Users/ta/running/apps/ios/RAI/Skins/Technology/TechViews.swift:1839–1866`；`/Users/ta/running/apps/api/src/server.ts:1055–1075`；`/Users/ta/running/apps/api/src/weekly-plan-service.ts:29–60`。
- **优化**：近期先增加覆盖前确认和互斥操作状态；随后拆成“生成候选 → 差异预览 → 带 revision 确认”。可扩展“仅重排未开始日期/保留指定日”，但不要默认破坏手工处方、已执行历史和已同步版本。
- **验收**：取消候选不写入；确认时重新校验版本；生成过程中不能误把旧计划同步并呈现为新计划已同步。

### P2-05：计划执行反馈未接入，字段覆盖门禁出现假绿

- **事实**：服务端已有 `recentPlanExecution`，原生 `MobileTodayResponse` 没有解码。视图只有一条包含 `data.recentPlanExecution` 的注释，却让检查源码子串的门禁报告“已有展示位”。最近训练反馈不能替代“计划与执行对照”。
- **附带表现**：已完成日的结构为 null，日详情会进入“还没有结构化处方；生成课表后显示”的通用空态，而不是引导查看已完成训练。过去无训练的格子又统一写为休息，不能据此推断用户按计划休息或漏跑。
- **证据**：`/Users/ta/running/apps/ios/RAI/APIModels.swift:328–358`；`/Users/ta/running/apps/ios/RAI/Skins/Technology/TechViews.swift:345,2124–2128`；`/Users/ta/running/apps/ios/tests/run-tech-presentation-tests.sh:185,238–242`；`/Users/ta/running/packages/api-contracts/src/index.ts:941–942`。
- **优化**：接入已有执行 DTO，显示原计划、已观测训练、来源及数据未齐状态；完成日链接训练详情。不要把 pending/unknown 记作漏跑，也不要用距离比例冒充强度完成率。字段门禁至少排除注释，并增加 JSON 解码、状态映射和 UI 元素断言。
- **验收**：删除真实展示时测试失败；只留注释不能通过。覆盖匹配、未匹配、数据未齐、计划历史缺失与一天多条训练。

## 五、产品优化方案

### 1. 训练计划页：围绕“今天做什么、接下来做什么、是否已同步”组织

建议顺序：

1. **今日执行卡**：原计划、有效计划、调整理由、锁课/重锁状态。只有实际发生调整时展示差异。
2. **周目标与执行进度**：分别标识周目标、已完成、剩余计划、预计合计；“轻松占比下限”和“质量课上限”明确是约束而非完成进度。
3. **未来七天**：跨周完整展示，点开看真实结构与来源；编辑能力与处方类型一致。
4. **设备同步状态**：当前计划版本、上次同步版本、待更新/待撤回日期、明确的错误与重试。
5. **执行回顾**：最近已完成日期的计划/实际对照，不把缺数据推断为执行失败。

手表是执行渠道，不应成为唯一“生成训练计划”的概念入口；无手表用户也应能直接生成、查看和执行计划。

### 2. 比赛目标：从静态表单升级为可解释的备赛入口

- **输入**：日期、现有三类距离，支持目标完赛时间与目标配速互算；二者使用同一规范值，不保存两份可矛盾的目标。先不扩大全马等服务端尚未支持的赛事类型。
- **时间状态**：区分未设置、备赛中、临赛、比赛当天、已过期/待归档；历史目标不要无提示地继续当活跃目标。新建过去日期应提示，历史归档另走明确语义。
- **解释**：展示已有 `volumeFraction`、`longRunFraction` 及准备度数据依据；目前 DTO 已有这两个字段，但未在 Technology 视图展示。不要先新造一个总分。
- **能力对照**：复用已有预测接口中的区间与 confidence，比较目标完赛时间和当前估计；数据不足时明确说明。准备度、预测成绩和达标概率必须保持区分。
- **计划影响**：保存后提示当前周计划不会自动重排，提供“查看影响 → 预览重排 → 确认”，并在确认后告知设备是否需要更新。

### 3. 架构：小范围解耦，不做大重写

- 从 `/Users/ta/running/apps/ios/RAI/Skins/Technology/TechViews.swift` 拆出计划总览、日详情、周编辑器、比赛摘要和设备同步面板；该文件当前 2,688 行。这是可维护性建议，不是已测得性能问题。
- 周计划编辑和比赛编辑共用草稿/版本/冲突策略，但各自保留必要的业务语义。
- 用功能级状态表达读取、提交、已保存但局部刷新失败、冲突等，不用全局字符串或文本前缀决定成功/失败颜色。
- 建立计划相关定向刷新与合并机制。现在保存目标会等待 today/statistics/trends/goals，再请求 workout-plan 和 workouts；与该操作无关的面板不应决定保存反馈时机。
- 保持配置、身份与缓存隔离；不新增 HealthKit 写入、后台机制或独立 Watch 产品。

## 六、实施顺序与验收里程碑

| 批次 | 交付内容 | 完成标准 |
| --- | --- | --- |
| A：一致性止损 | 修复旧读覆盖新写；保护编辑草稿；质量课距离改只读；开放旧排期撤回；接通重锁 | 保存不回退、不丢草稿；每个可编辑值真实生效；锁课和设备存在完整更新/撤回路径 |
| B：执行规则统一 | 明确每日计划优先级；统一比赛/整周约束；自然周与滚动七天口径拆清；生成改预览确认 | 计划、今日、详情与设备遵循同一有效处方，所有写入入口执行统一规则 |
| C：闭环与产品体验 | 比赛成绩目标与解释；执行回顾；版本/同步状态；按功能拆分页面和状态 | 用户能解释“为什么改课、目标影响什么、执行了什么、设备是哪一版” |

顺序按依赖划分，不是工时承诺。B 中改变今日选课优先级及赛事训练规则属于产品行为变化，应先评审规则，再实现，不以修 UI 的名义偷偷改变训练策略。

### 建议补齐的验收矩阵

| 层次 | 必补场景 |
| --- | --- |
| 服务端 | 原计划跨日保留；比赛日/临赛/赛后；LLM 与 fallback 同政策；手工编辑约束；自然周剩余额度与滚动窗口；生成候选确认时的版本冲突 |
| 原生模型 | 旧 GET 晚于新 PUT；生成期间刷新；草稿遇外部更新；取消和切服务；写入已成功但 today/workout-plan 刷新失败 |
| 原生 UI | 比赛新增/修改/清除/冲突/离线；锁课需重锁；质量课只读量；未来跨周日期可见；完成日进入记录；生成取消不落库 |
| 设备手工验收 | 新增/修改/撤回排期；零项目同步；授权拒绝/不支持设备；调度器未回读；登记回执失败与实际排期分开反馈 |
| 质量门禁 | 注释不能充当展示覆盖；执行反馈 DTO 解码与状态呈现；保留现有结构、距离、缓存隔离和缺测语义回归 |

**建议先实施 A，不先改整体视觉，也不先加更复杂的 LLM 功能。** 当前最有价值的优化，是让“保存成功”“今天按计划做”“已同步到设备”这些用户能感知的承诺与实际行为一致。
