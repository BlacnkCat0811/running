## 1. 前置项 P-1：v22 迁移安全化（用户指定，必须在 P0 之前完成）

### 1.1 问题定性

`RaiDatabase.open` **无条件**调用 `migrate`（`database.ts:1649-1662`）。线上 API 启动路径 `server.ts:338`（`recoverDatabaseJobs`）与 `server.ts:399-412`（`openMainDatabase`）都会触发。v22 会重写 `health_records` 的 id 并去重，**本地 160k 行实测 44.3 秒**。

**最危险的组合不是"慢"，而是"静默降级"**：
- `server.ts:351-356` 把启动迁移异常 **try/catch 吞掉**（仅记日志），进程继续启动，`databaseReadyAtStartup=false`
- 此后**每一个写请求**都会经 `openMainDatabase` 重新跑一遍 44s 迁移再失败 ⇒ 表现为"服务活着但什么都干不了，每次请求卡 44 秒" `[未验证：来自只读侦察，行号未逐条复核]`

另有三个已确认的缺口：
- **备份无磁盘预检**：`createBackup`（:1707-1717）在 `migrate` 内被调用（:1755-1757），失败即抛，没有 `ensureBackupCapacity` 那样的空间检查 `[未验证]`
- **迁移期无信号处理**：`SIGTERM/SIGINT` 处理器在 `server.ts:1558-1559` 注册，**晚于** :338 的迁移 ⇒ 迁移中重启会立刻打断（**库安全**，单事务回滚，但操作者会误判）
- **备份落点文档与代码不一致**：代码为 `<dbdir>/backups`（`database.ts:1709`）；`deploy/README-UBUNTU.md:71` 写的是 `/var/lib/rai/backups/` ⇒ **需线上确认** `[未验证]`

🔴 **为什么不能改 v22 的 `up` 函数**：`migrationChecksum = sha256("version:name:up.toString()")`（:1607-1611），`migrate` 对已应用迁移做**强校验**（:1747-1752）⇒ 改函数体 = **所有既有库（含线上）永久无法打开**。这直接否决了"把 v22 改成分批可续跑"的方案 C。

### 1.2 推荐方案：显式执行 + 启动拒绝

| 方案 | 做法 | 裁决 |
|---|---|---|
| **A 显式执行 + 启动校验** | `open` 增 `migrationPolicy`；API 两处传 `refuse`；新增迁移 CLI；pending 时以退出码 78 拒绝启动 | ✅ **采用** |
| B 自动执行 + 加固 | 保留自动跑，加磁盘预检 + 503 健康门禁 + 失败不吞 | ✅ 取其"加固"部分并入 A |
| C 分批/可续跑 | 重写 v22 为可中断 | ❌ **否决**：必须改 `up`，checksum 违约 |
| D 副本迁移 + 原子换入 | 用 `publishDatabaseFile` 在副本上迁移后换入 | ⏸ 留作未来选项：换入前仍须停 API，省的是"阻塞启动"而非停机 |

**推荐 A 的理由**：① 匹配"个人自用 + 一台机器 + 可 SSH"的现实；② 把 44s 从**不可观测的启动阻塞**变成**人工可观察的独立命令**；③ 失败从"静默降级 + 每请求重跑"变成**启动即拒绝**（宁可起不来，也不要半挂）；④ **不触碰 `up`，checksum 安全**；⑤ 默认行为不变，100+ 处 CLI/测试调用零改动。

**关键代码依据**：`up.toString()` 的哈希**不含其它属性** ⇒ 可以安全地新增与 `up` 同级的元数据字段而不破坏 checksum。

## 2. P0-1：跨源/分段记录归并（**形态已修正**）

### 2.1 实测结论：问题不是 120 秒窗

**[亲验]** 真库只读复制后实测：

```
271 条跑步 ｜ connect 148(146 canonical) / apple_watch 46(46) / huawei 41(40) / coros 36(36)
canonical 总里程 1769.48 km ｜ 全部里程 1799.46 km
```

跨组对（起跑差 ≤1800s 且不在同一 canonical group）共 **16 对**，其中：
- **跨来源只有 1 对**：`apple_watch` ↔ `connect`，起跑差 **1 秒**，2024-08-16
- 其余 15 对全部**同源**，且多数起跑差 >700s、时长差异大（很可能是真实的一天两练/热身+正课）

⇒ **"Garmin+Watch 起跑差 >2 分钟被双计"这个假设在真实数据里不成立。** 放宽 120s 窗不但修不了那一对（它本就在窗内），还会误并 15 对真实双课。**方案必须改向。**

### 2.2 真正的缺陷：截断/分段记录不归并

**[亲验]** 2024-08-16 三条记录：

| id | 来源 | 时段 | 时长 | 距离 |
|---|---|---|---|---|
| `workout_20c974…` | apple_watch | 10:58:08–11:25:32 | 1644s | **4.3796 km** |
| `workout_5408da…` | connect | 10:58:09–11:52:13 | 3245s | **9.0344 km** |
| `workout_ee2e19…` | apple_watch | 11:53:12–12:23:47 | 1835s | **4.7189 km** |

**4.3796 + 4.7189 = 9.0985 ≈ Connect 的 9.0344 km** ⇒ 这三条是**同一次跑步**：Watch 记录被切成两段，Garmin 记录了完整段。

而现有 `overlapsAsDuplicate`（`canonicalize.ts:73-100`）：
- :81 `if (startDifferenceSeconds > 120) return false;` —— 三段中第一段与第二段相差 3284s，**天然合不上**
- :88-93 两端都有距离时要求 `|Δd| ≤ max(0.2km, 3%)` —— 4.38 vs 9.03 差 51%，**直接被否决**
- `canonicalRank`（:117-125）= `sourceRank + routeCount*100 + hrCount*40 + …`，`routeCount*100` 权重压倒一切 ⇒ **被截断的短记录因为带轨迹而被选为代表**，长记录反而成为非 canonical

**后果**：那次跑步在系统里是 3 条记录，该周里程虚高约 4.38 km（若不合并），且 TRIMP/五维/EWMA 全部基于被截断的代表。

### 2.3 改动方案

**（a）`canonicalize.ts:73-100` 重写为分级证据判定**（禁止简单的窗口放宽）

```
硬边界（防早晚双课）：起跑差 > 900s ⇒ 永不合并
高置信自动合并：
  · 起跑差 ≤300s 且 时长比 ≥0.85 且（距离比 ≥0.85 或 距离缺失）        → MERGE
  · 起跑差 ≤900s 且 时长比 ≥0.85 且 距离比 ≥0.85                      → MERGE
前缀截断（本库实况）：
  · 起跑差 ≤300s 且 距离比 ∈ [0.35, 0.85) 且 配速差 ≤0.5 min/km       → REVIEW（进人工清单，不自动并）
分段接续（新增，处理 2024-08-16 那类）：
  · A 段结束时间 ≈ B 段开始时间（±120s）且 同源或跨源
    且 合并后时长与另一来源的完整记录吻合（±5%）                       → MERGE（标记 segment_join）
轨迹重叠：仅 apple_watch 有轨迹 ⇒ 只能作同类加分项，不能跨来源使用
```

⚠️ **分段接续规则要保守**：一天两练（上午/下午）也可能"结束接着开始"。必须要求**存在第三条记录佐证合并后总时长**（本库正好有），否则一律走 REVIEW。宁可漏并，不可误并。

**（b）`canonicalize.ts:117-125` 改 canonical 选择**
先按「完整度」分级（时长与距离都落在组内最大值 2% 内为一等），再在同级内比 `sourceRank + 数据丰富度`。**避免 `routeCount*100` 让截断记录当代表。**

**（c）常量化与版本化**
`canonicalize.ts:81/141/242/285` 的 120 魔法数抽成 `const DEDUP_WINDOW_SECONDS` / `AUTO_MERGE_WINDOW_SECONDS`；新增 `CANONICAL_WORKOUT_ALGORITHM_VERSION`（对齐 `canonicalize-nights.ts` 的 `CANONICAL_NIGHT_ALGORITHM_VERSION`，`index.ts:23`）写入 `import_manifest`。**这很重要：以后改算法能知道哪些数据是用哪版算法产的。**

**（d）REVIEW 清单落地**
REVIEW 对不合并，写入已有的 `import_issues` 表（`severity/code/object_id/message`），code = `SUSPECTED_DUPLICATE_REVIEW`；在 `audit.ts`（`buildAudit` :292、`renderAuditMarkdown` :514）新增段落，输出到 `docs/DATA_AUDIT.md` + `var/reports/data-audit.json`，**复用已有只读端点 `/v1/data-audit`（`server.ts:683`）自动可见，无需新路由**。

**（e）历史数据重算路径**（必须与代码改动同批执行）
1. `canonicalizeRunningWorkouts(db)` 不带 incremental 走全量重建（:312-318 会清 `workout_group_members`/`workout_groups` 并重置 `is_canonical`）
2. **在副本上执行再切换**：照抄 `cli.ts:115-127 prepareStagingDatabase` + `:138-187 activateStagingDatabase` 的 staged publish 模式
3. 下游重算：`npm run data:recompute -- --database var/rai.sqlite`（**必须全量，不能用 `--dirty-from`**——canonical 归属变化会影响任意会话）
4. 报告：`npm run data:audit`

需在 `packages/health-export-parser/src/cli.ts` 新增分支（现有只认 `import|incremental-import|audit`，见 :54-62）。

### 2.4 验收标准

| 判据 | 期望值 |
|---|---|
| 2024-08-16 那组 | 落成 **1 组 N 成员**（或按保守规则进 REVIEW 清单），canonical = 9.03km 的 Connect 记录 |

### 2.5 回滚与风险

- ⚠️ **回滚不能只回代码**：`workout_group.id` 由成员 id 排序后 `stableId` 生成（`utils.ts:14-20`，调用点 :359-362），成员集合一变 id 即变 ⇒ **必须同时恢复库文件**。重算前先 `POST /v1/backups` 留全量快照。

- 风险：TRIMP/五维/EWMA 的具体变化量**未实测**（未跑 recompute），需在验收时补数值。

### 3.2 判定规则

以 `Asia/Shanghai` 本地日为唯一时钟（`data.ts:79-86`）。**"已过当日截止" = 次日 00:00**（全仓无日切小时概念，已核实）。

| status | 条件 |
|---|---|
| `completed` | 有训练；无计划 或 实际 ≥ 计划×0.7 |
| `completed_short` | 有训练；有计划距离且实际 < 计划×0.7 |
| `missed` | 过去 + 有计划 + `planned.kind !== "rest"` + 无训练 + **数据已覆盖该日** |
| `rest` | 过去 +（无计划 或 计划就是 rest）+ 无训练 |
| `pending` | 过去但同步未覆盖该日 ⇒ **不计入分母** |
| `today` / `planned` | 今日 / 未来 |

**数据覆盖门**（防误报漏课）：`Shanghai(lastSyncedAt) >= today`（`data.ts:255-258`）或 `latestDataDate >= day.localDate`（`:251-254`）；否则 `pending`。**宁可漏报，不可误报。**

**adherence 定义**：
- **分子** = 窗口内 `completed` + `completed_short` 天数
- **分母** = 窗口内 `kind !== "rest"` 且有计划且非 `pending` 的天数（休息日与未排课日**不入分母**）
- **窗口 = 滚动 7 天 `[today-7, today-1]`**，**不用自然周**——因为 `ensureWeeklyPlan` 恰在周一早上跑，自然周的过去日恒为 0，LLM 拿不到任何信号

## 8. P3-A：Critical Speed 作「分区一致性校准器」

### 8.1 现状链路（已确认方向正确）

**[亲验]** `recompute-pipeline.ts:1235` 调 `estimateLactateThresholdFromPerformanceVdot` → prior 为 `estimateLactateThreshold`（VDOT→1h 配速，method `vdot_one_hour_proxy_v1`），再与实测片段融合（method `multi_evidence_threshold_v2`）→ 作为 `thresholdPace`（`ThresholdPaceCandidate`，`training-zones/src/index.ts:37-42`）喂给 `buildDailyZoneProfile`（:253-291）→ `daily_zone_profiles` 表。

⇒ **强度分区确实来自成绩反推，不是本人实测** —— 这是 CS 值得做的真实理由。且已有 `confidence`/`evidenceCount` 可用于门控（`training-zones/src/index.ts:268` 需 ≥0.35 才平滑更新）。

### 8.2 改动清单

| # | 文件 | 改法 |
|---|---|---|
| 1 | `packages/physiology/src/index.ts` | 新增纯函数 `estimateCriticalSpeed(spans: {durationSeconds, distanceMeters}[], config) → {criticalSpeedMps, dPrimeMeters, r2, reason} \| null`，线性回归 `D = CS·t + D′`（3/7/12 min 三点） |
| 2 | 🔴 **性能约束** | **不要塞进 recompute 全量重算**——CS 要逐课扫描速度样本，268 会话 × 每次 full recompute 太贵。结果算在读路径 `/v1/training-zones/current`（`data.ts:836 trainingZonesCurrent`），走既有 `cached()`（`data.ts:158-168`） |
| 3 | 采样 | 复用 `speedTrack`（:269-326），把私有 `metersAt`（:388-396）抽出为 `fastestWindowDistance(track, windowSeconds)` |
| 4 | 🔴 **明确不做** | **CS 不参与重算**；若实测 >300ms，改写进已有 `daily_zone_profiles.evidence_json`（已有 JSON 列，**无迁移**） |

### 8.3 校准器设计（**核心形态**）

CS **不与现有 `thresholdPace` 并列展示**，而是做一致性校验 —— 避免红队指出的"两个不一致的数 = 不可信"：

| 偏差 | 判定 | 文案 |
|---|---|---|
| CS 比阈配速 **快 >8%** | 分区偏保守 | "实测能力高于分区设定，可考虑上调阈值配速" |
| CS 比阈配速 **慢 >4%** | 分区偏激进 | "实测能力低于分区设定，分区可能偏高" |
| 其间 | 一致 | 不出提示 |

**阈值双侧不对称**是有意的：CS 生理上本就略快于乳酸阈，用单侧 5% 会误报。

**展示位置**：`DailyZoneProfile.evidence`（`packages/contracts:202-206`）加 `criticalSpeedPaceSecondsPerKm` 与 `divergenceFraction`；提示出现在训练分区页（`TrainingZonesPage.tsx:63/101`）一行 + 今日卡 coach 侧（`data.ts:344-364` 已把 `zones` 交给 `assembleMobileCoach`）。**不进告警系统。**

### 8.4 无硬跑门槛（防假精度）

近 42 天 ≥3 次跑 且 其中 ≥1 次含 ≥12 min 连续速度样本 且 三点 `r² ≥ 0.98`；否则 `reason: insufficient_hard_runs | low_r2`，**不出值**。

### 8.5 验收 / 回滚 / 风险

- 验收：**[未验证]** 真实库约 44 次会话满足 ≥12min 速度样本；断言 CS ∈ 2.5–6.0 m/s、D′ ∈ 0–400 m；偏差提示在构造用例下正确触发
- 🔴 **版本红线**：本方案**不让 CS 反向修改 `thresholdPace`**。一旦回写就成了改口径 —— 必须升 `MODEL_CONFIG_VERSION`（`packages/scoring/src/model.ts:16`）并全量重算（`recompute-pipeline.ts:463` configHash、:1651 校验）。**首版严禁回写。**
- 回滚：删函数与 `evidence` 字段（JSON 列旧值自然忽略），无迁移
