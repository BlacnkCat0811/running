## 1. P1：首次空库许可缺少历史数据集证据

### 1.1 现状、根因和可复现序列

`apps/api/src/runtime-state.ts` 的 `reserveFirstEmptyScope()` 在 `import_scope_evidence` 没有该 scope 行时直接插入 `first_empty_epoch=1`、两个时间戳为 `NULL`。`apps/api/src/import-worker.ts` 仅在入队时主库路径不存在才调用它；构造器没有在**已有主库存在时**登记该 scope 已建立。执行前的账本复核和 `markScopeWriterEntered()` 能挡住“同一批 A 写完、B 尚未运行”的已知序列，但不能追溯新账本建立以前的数据集。

可复现的另一序列：部署新版前同一 scope 已有事实库 → 新版尚未处理任何导入，因此账本没有该 scope 行 → 主库被暂时移走或挂载不可见 → 新任务入队，空行被当作“首次空库”预留 → 执行路径创建新库。若 `runtime.sqlite` 损坏后被隔离重建，缺失的历史账本也会形成同类“没有记录”的状态。`readDatasetEpoch()` 在主库缺失且无显式删除 sidecar 时回退到配置的 epoch，不能单独证明这是新数据集。

**安全不变量：**“账本没有记录”是**未知**，不能等同“历史上从未有数据库”。主库缺失时，只有来自可信初始化流程、持久化且与当前 scope 绑定的首空许可才能放行创建；任何未知、损坏、过期或互相矛盾的证据都进入 `recovery_required`。

### 1.2 推荐修复设计

1. **把状态语义写清楚。** 在现有 `runtime.sqlite` 内为 scope 维护单调状态，例如 `unknown → pristine → writer_entered → established`；`unknown` 不可自动转成 `pristine`。允许将 `writer_entered` 与 `established` 保持为已有的不可清空证据字段，但必须另有明确的 `pristine` 来源／创建依据。状态或依据缺失时拒绝首次空库许可。不要仅凭主库文件、账本行或运行目录“不存在”推断首次安装。
2. **升级时先登记旧库。** API 启动、构造和恢复导入 worker **之前**，在维护／单写者边界内只读确认当前主库及 scope：存在且可读的主库持久标记为 `established`；存在但不可读的主库标为未知并阻断自动建库；主库缺失且没有可信首空许可时保持 `unknown`。此登记要早于新任务可入队、`loadJobs()` 可放行和 `resume()` 可调度。
3. **首次安装需有可信引导动作。** 由受控的首次安装／数据集初始化流程，在确认要创建新数据集时为该 scope 持久写入 `pristine` 许可；显式删除成功并切换 dataset epoch 后，也只能为**新 scope**按既有维护合同建立许可。若安装流程无法提供可验证的首次引导证据，安全默认是停止自动首包并要求一次显式初始化。仅靠“主库和 runtime.sqlite 同时不见了”在逻辑上无法区分新安装与两份状态同时丢失，不能承诺两者都自动放行。
4. **所有建库路径共享同一证据。** 导入 worker 开始任何可能写主库的动作前，持久进入 `writer_entered`；观察到已有主库、worker 建库成功、维护恢复完成时，持久进入 `established`。写账本失败必须停止本次写入。`pristine` 一旦失效，不得因进程重启、文件暂时缺失或 `runtime.sqlite` 隔离重建而再次生效。保持当前的同一 scope 单写者准入，不新增主库或写者。
5. **重启恢复按事实裁决。** 主库可读时优先严格读取原持久回执；主库缺失且 scope 为 `unknown`、`writer_entered` 或 `established` 时，作业保持 queued/running、`phase=recovery_required`，不 finalize、不清理上传来源、不触发第二写者、不创建新库；恢复原库后按原回执或“确认不存在”收敛。旧作业没有新许可字段时一律按未知处理。
6. **迁移和回滚。** 老 `runtime.sqlite` 没有该表／该 scope 行属于未知；不能在迁移中补写“从未建库”。旧代码忽略新表的兼容性可以保留，但回滚后再升级必须重新核对主库和账本。显式删除、恢复、换 epoch 的状态转移与持久顺序应写进 `STATE_CONTRACT.md`；不要手工清空旧 scope 证据来获得首空许可。

### 1.3 必须新增的故障与迁移用例

| 场景 | 构造 | 必须观察到 |
|---|---|---|
| 旧库升级后正常启动 | 预置旧版主库，账本无当前 scope 行 | 启动时持久登记 `established`；主库和数据不变 |
| **旧库在首次登记前暂时缺失** | 预置有事实的旧库与旧版 runtime 状态，移走主库后首次启动新版并入队 | 不签发首空许可；作业 `recovery_required`；主库路径不被重建，来源保留；恢复旧库后按真实回执／任务状态收敛 |
| 启动后旧库消失 | 启动时已登记 `established`，再移走主库并新建作业 | 同上；不能因新作业 `attempts=0` 放行 |
| 账本损坏／隔离重建 | 先建立并写入数据集，再使 runtime 状态损坏，主库暂时缺失 | 新账本默认未知；不得因隔离后无行而重建空库 |
| 既有 A/B 排队序列 | 空库时入队 A、B，A 成功后移走主库 | B 仍阻断；恢复原库后只提交一次，A 数据仍在 |
| 真正首次安装 | 由可信初始化流程建立 `pristine`，主库为空、作业 queued/attempts=0 | 首包可创建 v47 主库并写回执；许可在写者进入前持久失效，第二包按已有库处理 |
| 证据持久化失败 | 在进入 `writer_entered` 前注入 runtime 写失败 | 不创建／修改主库，不发布终态，来源不清理，恢复诊断明确 |
| 显式删除／恢复 | 通过既有维护流程完成 epoch 切换或恢复旧库 | 旧 scope 许可不复活；新 scope 只按显式初始化规则放行；恢复旧库标为已建立 |

**P1 验收条件：** 以上用例在真实队列／重启路径通过；无法证明首次空库的任一序列中，主库路径无新建、无第二写者、无猜测终态、无上传来源清理；恢复原库后事实和回执不重复。原有首次空库及 A/B 双任务用例继续通过。

## 2. P2：F01 删除与 GPX 的提交前强杀证明

### 2.1 当前测试能证明什么、不能证明什么

`apps/api/test/direct-sync-http-acceptance.test.ts` 的新 GPX 用例使用 `syncManifest()` 默认值，`deletedSourceIds=[]`、`deletedRecords=[]`，且初始主库中没有待删除事实。它没有执行删除。强杀等待条件为 `job.status=running`、WAL 大小至少 256 KiB、回执尚未出现；4500 条 Record 可以先使 WAL 达标，而 GPX 导入位于 XML 解析之后。因而测试可能在路线点写入前杀死进程。杀后路线表为零与重启后路线可见，都不能反推“杀前路线写入已发生并被 SQLite 回滚”。

既有 `data-only-import.test.ts` 使用回执写入前的确定性屏障证明了**另一条** records＋删除路径的回滚；它与 GPX 用例可以分别支持局部结论，但不足以把“同一批删除＋GPX 已写入后的回滚”写为已验收。

### 2.2 推荐修复方法

1. **构造有真实删除目标的基线。** 先提交一条有稳定 UUID 的 Record（可再加一条不应删除的同来源事实作为保护对照）；记录批次前 `health_records`、墓碑／变更账本、路线及版本、generation、回执的精确快照。待强杀批次的 v2 manifest 必须显式删除该 UUID，同时提交一个带 `WorkoutRoute` 显式引用的 Workout 和 3 点 GPX；所有内容都走真实 HTTP 上传和导入 worker。
2. **使用确定性提交前屏障。** 在**删除与 GPX 写入已经执行、COMMIT 尚未发生**的位置暂停真实子进程。例如复用既有测试的“回执写入前 SQLite 触发器＋同连接测试函数”方法，或使用只由内部测试夹具注入的等价 IPC 屏障。屏障必须由实际导入事务触发，携带 job id；在同一事务连接上核实待删 UUID 已不可见、`route_versions/route_version_points` 已有本批版本和 3 点，外部只读连接仍看到批次前快照且无回执。只观察 WAL 大小、时间或 `running` 不算屏障。不要新增对外生产故障开关。
3. **屏障处强杀并重新开库。** 对真实服务子进程发送 SIGKILL，等待 OS 确认退出；重新打开主库并逐表比较批次前快照。原待删事实必须还在，新 Workout/路线/版本/点/指纹、墓碑、批次、任务、回执均无半批；`PRAGMA foreign_key_check` 为空。
4. **同一任务恢复与恰好一次。** 用同一 runtime 目录重启，由同一 job id 重试；最终原 UUID 被正确删除、未删的对照事实保留、Workout/路线版本/3 点和指纹各一份、批次与持久回执各一份。终态摘要等于持久回执，generation 只按合同推进一次；再次重放不改变事实。
5. **更新证据口径。** 屏障日志应明确 `jobId`、所处事务阶段、同连接删除／GPX 写入断言、杀前外部快照、杀后快照及重试结果。若不能建立屏障，应将 F01 标为 partial，而不以 WAL 阈值日志宣称 GPX 回滚已证明。

**F01 验收条件：** 同一个真实批次同时含有效删除与 GPX，且有确定性证据证明两者都在杀前写入未提交事务；SIGKILL 后数据库等于批次前快照（包括原删除目标），恢复后同 job 恰好提交一次。目标用例、相关 G1/G5 套件和完整 `npm test` 均通过，并在 `TEST_MATRIX.md` 对应 F01 行记录命令、并发、退出码和日志。

## 3. P3：T12 从实际导入到 readiness 发布的 A/B

### 3.1 当前证据边界

`packages/application/test/training-metric-domain-reuse.test.ts` 的 T12 双库用例直接 `INSERT/UPDATE canonical_nights`、`canonical_hrv_days`，再调用 dirty-range 规划与 `runAnalysis()`。它有效验证了**已有 canonical 事实进入分析后**的 readiness 完整产物等价、Fitness 隔离和中间期不变；没有在这同一用例中经过 v2 XML 接收、旧新夜局部重建、批次持久脏证据、任务登记、调度和发布。现有接收层单测分别验证部分前段，报告中的“端到端 A/B”应由一条贯通用例支持，或明确限定其含义。

### 3.2 推荐补充用例

1. 建立两个独立临时库 A/B，使用相同 70 天合成 Apple Health 睡眠／HRV 原始事实、父发布、配置、时区和 `evaluatedAt`；记录相同的初始 dataset version、代次、canonical 及业务投影。夹具用真实 v2 manifest 和稳定记录身份，不直接改 canonical 表。
2. 通过真实接收路径给 A/B 导入同一修订包：两个不相邻时期（沿用 day 5/day 50），每处均跨夜移动睡眠片段并修订 HRV。控制分析消费者的启动时点，使两库先完成同样的事实事务；核对批次回执、raw/dependency generation、两段独立的脏范围、旧新夜变化及中间区间 canonical 行逐字段不变。
3. A 使用事务登记并合并后的真实 partial 计划计算和发布；B 在同一父发布和相同最终事实之上禁用复用，执行完整计算并发布。不得以“空白库全量”替代同父发布对照。实际 executed plan、覆盖证据和复用计数必须留在日志中；A 预期安全前缀确实复用，readiness 自身仍可整域全量。
4. 使用现有 15 张表／投影比较器逐键逐字段核对 A/B：`training_sessions`、特征、负荷、分区、每日能力、readiness/fitness 五域封存、lineage、bundle、`evaluation_json`、active 指针、freshness 与输入绑定。readiness 必须因修订而变化且 A=B；中间期逐日 readiness/canonical 行不变。Fitness 的**业务指标与解释**应与修订前一致，并与 B 相等；真实导入会推进 dataset version，相关 lineage/version 字段应按合同变化，不能为了追求“原始 JSON 与修订前逐字相同”而抹掉版本差异。
5. 若贯通用例受夹具成本限制而暂不加入，则在 `TEST_MATRIX.md` 和 `PHASE3_REPORT.md` 把现有测试准确写成“接收层与应用层组合证据”，将“单条车道到发布端到端 A/B”标为未证明；不得沿用无条件的端到端称谓。

**T12 验收条件：** 真实 XML 修订产生两个不相邻的旧／新夜脏时期；中间 canonical 行和相应 readiness 业务值不变；A 的实际 partial 计划与 `reused>0` 有持久证据；readiness 更正后确实变化且与同父发布的 B 全量逐字段等价；Fitness 业务值不被睡眠／HRV 修订污染；发布及可读状态自洽。差分为零或每一项差异均有预先定义的执行身份／版本解释，不能事后放宽比较器。
