### 批次 2：OPT-5 + OPT-6 队列护栏（合并一次 v23）

**目标**：① 崩溃任务三次后停在失败态，不再无限重放；② 轻量刷新任务可插队长全量重算之前。

**必须先知道的三件事（都改变实施方式）**
1. 🔴 **v23 是单向门**。回退**不能**靠 revert 代码：库里出现了代码不认识的版本号会直接抛错（`database.ts:1698`、`:1808`）。回退只能"停服 → 还原迁移前自动备份 → 删 `-wal`/`-shm` → 启动"。
2. 🔴 **不存在"代码先兼容旧结构、再迁移"这个阶段**。含 v23 的代码打开 v22 的库会立刻退出（退出码 78，`migrationPolicy: "refuse"` 分布在 `server.ts:482`、`:554`、`recompute-thread.ts:7`、`command-queue.ts:179` 与 `prediction-worker.ts` 多处）。因此**迁移必须与代码在同一次停服发布里完成**。
3. 🔴 **校验和覆盖迁移函数体**（`database.ts:1622` 取 `version:name:up.toString()`）⇒ 连"改注释/空格"都算修改，历史迁移绝对不许碰。

**改动要点**
1. 追加 **v23**（只能追加，不得改动任何历史迁移）：加"重试次数"与"优先级"两个带默认值的列，**并在同一迁移里补排序所需索引**——否则取任务会退化为临时排序（审查员实测：不补索引会出现 `USE TEMP B-TREE FOR ORDER BY`）。
2. 取任务排序改为"优先级优先，其次维持原顺序"，保证默认优先级下行为与现在完全一致。
3. 重置上限：超过 3 次转终态失败，异常信息要能区分"被外部中断"与"反复崩溃"。
   - 🔴 **不要用进度字段判断"无进展"**：恢复流程会把进度归零，照字面实现拿不到进度。
   - 🔴 每次崩溃恢复会先把关联的 run 标记失败 ⇒ 重启一次就留一组垃圾，重试上限 3 意味着最多 3 组；要在方案里接受或清理。
4. **删除迁移里可能写出的删除列语句**：回滚靠备份，不靠反向迁移。

## 7. 实施纪律（修订版，取代原第 5 章）

1. **迁移只增不改**：校验和覆盖迁移函数体，改历史迁移（含注释）会让所有既有库打不开。这是被代码强制执行的，不是约定。
2. **迁移与代码同批停服发布**：不存在"先上兼容代码"的中间态；API/worker 遇到未执行迁移直接退出（78）。
3. **v23 之后只能靠备份回退**：先写好并演练回滚脚本（停服 → 还原主库 → 删 `-wal`/`-shm` → 启动）再发版。
4. **门禁分开报**：node 侧与 web 侧必须分开陈述。web 侧现在有**两条**不同的通道，别混：① 单元/组件（vitest，宜单跑）；② 桌面 E2E（`npm run test:e2e:web`，需 Chrome，已可跑）。合并脚本 `npm test` 以非零码退出有**本机既有原因**（vitest forks worker），不得当作回归判据。基线数字必须**在批次 0 之后重新取**——现有一切基线都是脏树数字。
5. 🔴 **E2E 基线要先在干净树上取，再拿脏树比 —— 但必须多采样**（本条已被今天的 5 样本结果修正）：昨天按单次样本把 3 个失败切成"1 个 HEAD 既有 + 2 个脏树引入"，**今天证明切错了**（10/11 是用例 9 的级联，不是回归）。手段仍是 `git worktree add --detach /tmp/<name> HEAD`（不碰工作区），但 🔴 **必须重建 `node_modules/@rai/*` 软链指向 worktree 自身**（否则 `packages/**` 仍指向脏工作区，见纪律 15）。**注意**：该测试会 spawn `apps/api/src/server.ts`（`web-flows.test.ts:61`，`cwd=项目根`）⇒ 它**吃的就是被改动的 API 源码**，所以"E2E 失败"完全可以由 `apps/api/**` 的改动引起 —— **这正是单次样本不够的原因**。
6. **断言必须能突变到红**：优先级排序、重试上限都要实际改坏确认变红；但**死循环那条必须强杀进程构造**，"去掉上限"式的写法会是恒绿假绿。
7. **判据不能用恒真式**：例如"跳哈希后 `dataset_version` 不变"在默认路径下永远成立（哈希取自指纹表），作废。
8. **阈值不是验收标准**：门禁阈值、效率阈值、性能上限都只是参数，验收必须是可复现的业务判据。
9. **"零命中"结论必须交叉复核，且要两种工具形态都防**：① 检索工具对某些 pattern 会静默返回空（已实锤 `timezone_identifier`）；② 🔴 **BSD grep 的 `\|` 交替也静默返回空**——当日三次踩中（`manualChunks`、skill 文件、`cli.ts` 里的 `canonicalizeNights`，而该文件 `:320` 明明存在）。**一律用 `grep -E` 或检索工具。**
10. 🔴 **性能收益必须区分"机器特性"与"算法改进"，而且不能用通说推算目标机器**（本条已被今天的实测两次修正）：同一改动本机省 39.7 s、云机省 18.9 s —— **两个都是实测**。错误做法有两种：① 拿本机数字宣称生产收益（把测试机当生产）；② 用"正常 Node 构造 10–30 µs"这种通说反推目标机器（今天实测云机 **73.4 µs/次**，同样不"正常"）。⇒ **报收益 = 在目标机器实测 + 同批给出等价性证据 + 标明数据口径。**
11. **只读实验**：`var/rai.sqlite` 是 325 MB 真实健康库，一切等价性实验在**副本**上做。
12. **改完对齐文档**：`docs/SLEEP_HRV_DESIGN.md`（含"接受浪费的 full recompute"那条结论）、`docs/DATABASE_DESIGN.md`（迁移到 v23）、`README.md` 同批更新。
13. 🔴 **「某失败是不是我改出来的」必须多采样，单次样本不足以定性**：同一棵树、同一份代码跑 **5 个完整 E2E 样本**得到 **1 fail 与 3 fail 两种结果**。判级联的关键是看**受害用例依赖的上游用例死在"破坏性操作"之前还是之后** —— 本例 `firstRunApi` 的空库只被用例 9 填充、又被用例 9 删掉，10/11 只是受害者。
14. 🟡 **测试间共享可变夹具时，破坏性用例必须保证恢复**：用例 9 删库后只有走完恢复流程才复原；一旦在中途失败，后续用例就被连带判死。凡"删库/改全局状态"的用例，恢复动作要放进 `finally`（或让下游用例自带前置自保）。
15. 🔴 **干净 worktree 对照要连 `node_modules/@rai/*` 一起重建**：`node_modules/@rai/*` 是指向 `../../packages/*` 的**相对软链**，直接软链整个 `node_modules` 会让 worktree 的 `packages/**` **仍指向原工作区（脏）**，只干净了 `apps/api` / `apps/web`。
16. 🟡 **临时探针的计数必须与数据规模对账**：探针报出的数若不能用手头数据解释（本例初看 25.0 万构造 vs 预期 40.9 万），**先怀疑探针、再怀疑数据**；对不上账就说明探针可能跑错了对象。（本例最终对上：见第 6.4 节。）
