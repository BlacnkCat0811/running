## 2. 关键设计选择

### 2.1 缺数据必须与"确实处于参考条件"分开（§5.3 的硬要求）

现有 `performanceConditionPenaltyFraction` 在缺数据时**返回 0** —— 与"测得平路、无热湿"**无法区分**。
§5.3 明确：`not_needed` 表示"有足够证据且处于参考条件"，**不是**"缺信息所以不修正"。

本包把这两件事拆成两个状态，并让缺数据的那一支**结构上不可能**被当成 `not_needed`：
`normalized = null`、`correctionFraction = null`、`comparability` 降到声明值、原因码点名缺哪个字段。

🔴 `correctionFraction` 用 `null` 而不是 `0`：**0 表示"算过且为零"**，用它表示"没算过"是同一字段承担两种语义
（本仓库纪律 16① 已吃过一次亏，127 处假警报）。

### 2.2 `applied` 对 identity 是**不可达**的，且被断言钉住

"identity 不施加修正"如果只写在注释里，一次重构就可能悄悄违约。断言直接覆盖四种上下文
（参考条件 / 全缺 / 全超域 / 边界值）都要满足 `status !== "applied"`。

### 2.3 `rawComparableFallback` 非空 **⟺** `normalized` 为空

不给调用方任何"两个都有值、该信哪个"的模糊地带。字段名本身即提醒：它是**原始值**，不是归一化结果
（§5.3：不能谎报"已归一化"）。

### 2.4 条件账本：把 §5.5 的禁令变成**构造即抛**

§5.5 禁止"同一历史热惩罚被 adapter 与 `performanceVdotEvidence` 各去一次"。
这是一句**要靠人记住**的话 —— 除非把它变成约束。`validateConditionLedger` 在模块加载时运行，拒绝：

- 同一 `(appliesTo, field)` 出现两次 ⇒ **这就是重复扣罚**，报错时点名两个冲突条目；
- `residual_input` 覆盖 `historical_evidence` / `target_scenario` 已处理的字段（§5.5：残差只学**剩余**偏差）；
- 空 id / 重复 id / 未知字段 / 同一条目内重复字段 / 缺 location。

同时**不能过度收紧**：`historical_evidence` 与 `target_scenario` 对同一字段各一次是 §5.5 **明确允许**的
（"过去热天去偏差 + 未来热天加情景"），有一条断言专门守着这个允许是真的。

账本的每条 `location` 都写成 `文件:函数`，并有一条断言**真的去读那个文件**确认函数存在 ——
防止账本指向已被删除或改名的代码。

### 2.5 纯哈希：为什么不用 `node:crypto`

`tsconfig.pure.json` 带 `"types": []`，纯包不得引用 node 内置模块（`contracts` / `features` / `readiness`
里 grep 不到任何 `node:` 导入）。而谱系指纹只需要**确定性**与**低碰撞率**，不需要密码学强度 ⇒ FNV-1a 64 位。

## 3. 验收证据

### 3.1 覆盖盘点（真实库，只读）

```
canonicalWorkouts: 268
contextStatus: { applied: 0, not_needed: 0, unavailable: 268, out_of_domain: 0 }
reasonHistogram: temperature_missing=268, humidity_missing=268, elevation_missing=267
```

`not_needed = 0` / `unavailable = 268` 是**预期**结果，不是缺陷：这份数据确实没有环境上下文，
而 adapter 的价值恰恰是**把它说出来**，而不是像现在这样静默地按"零惩罚"处理。

### 3.2 三次突变

| 突变 | 结果 |
|---|---|
| 缺数据那一支改成返回 `normalized = raw`、`status = not_needed`（即"缺数据伪装成参考条件"） | 测试 2 转红 ✅ |
| 指纹只哈希 `temperatureC`（丢弃湿度与爬升） | 🔴 **第一次没红** —— 见下 |
| 账本加入一条重复的 `historical_evidence: temperature_c` | 模块加载即抛，错误信息点名 `vdot-evidence-history-debias` 与 `mutation-probe-duplicate` ✅ |

**第二个突变暴露了我自己的一个真问题**：原测试只在**哈希函数本身**上断言"每个字段都改变指纹"，
只有最后一行经过 adapter。所以"**trace 真的带了全上下文指纹**"这件事**没有被验证**——
把 adapter 的调用改成只哈希一个字段，测试照样全绿。

修法：新增一条**逐字段走 trace** 的断言（缺失与改值两种情况都要让 `trace.sourceContextHash` 变）。
补完后该突变如期转红，测试 13 → 14 条。

> 这与本方案前面几批踩过的是同一类坑：**断言测的是"辅助函数对不对"，而不是"路径真的用了它"**。
> 判据：凡是"某个字段参与了计算"的断言，必须在**产物的那个字段**上断言，不能在中间函数上断言。

### 3.4 一处工程观察（不是缺陷）

只读打开活库 `var/rai.sqlite` 会更新它的 `-shm` 侧车（`mtime` 变为本次运行时间）。
这是 WAL 模式的正常行为，与"打开**备份**文件留下侧车"不同 —— 后者要清理，前者**不能删**
（删掉会伤正在读库的进程）。已核对：`-wal` 为空（0 字节），库本体未被写入。

同时发现 `var/` 下有 15 个 `rai.sqlite.import.lock.stale.*` 目录（2026-09-01 至 09-17，非本批产生）。
**本批未清理**：它们属项目数据，清理应当单独确认。
