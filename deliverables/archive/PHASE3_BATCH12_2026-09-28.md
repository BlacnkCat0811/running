### 🔴 先说清一件我一开始判断错的事

我最初的假设是：**这条 Coach 子句会推翻 `classifyTrainingStatus` 给出的 `recovery`**（停跑一周时按"高负荷"置红）。

**实测证伪。** 停跑 7 天后 acute 衰减比 chronic **快**，比值反而从 2.2 降到 **0.476** ——
休息把比值压下去，不是抬上去。

改做形态扫描后的结论是：该子句在 7 种负荷形态、13 个 red 日里 **0 个只靠它**，
并且可以**解析证明**：

> 比值 > 1.3 时，`classifyTrainingStatus` 的 `load_ratio_high` 分支在 `recovery` / `maintaining` /
> `effective_load_range` **之前**返回；能抢先的只有 `attention`（Coach 也判 high）或
> `insufficient_data`（Coach 的第一条分支先接管）。两者都使该子句**无法改变结果**。

⇒ 它**不是缺陷，是冗余**。这个区分很重要：**冗余可以安全删除，缺陷必须带测量才能删。**
若我按最初的假设写成"修了一个会误判休息周的缺陷"，那份报告就是错的。

## 2. 关键设计选择

### 2.1 §9.4 的"不得三票"做成**形状上的不可能**

§9.4：不得让 ATL、ACWR、超额值**三次分别投票**提高风险。

如果实现成 `{ acwrRisk: boolean, excessRisk: boolean, atlRisk: boolean }`，规则就只活在注释里。
本版的形状是：

```ts
interface LoadAssessment { risk: LoadRisk; basis: LoadRiskBasis; indicators: {...}; explanations: [...] }
```

`basis` 是**单值**（`"acwr" | "ramp_rate" | "strain_vs_p90" | "phys_state" | ...`），
`risk` 由分类器的**首次命中**决定。想投三票在类型上就做不到 —— 有断言专门守它
（改 `basis` 为"多信号取最严"会立刻转红，见 §3.2）。

### 2.2 本版**不重新分类**（兼容优先）

§9.5 第 1 条说"只有高 ACWR、历史充分、其他项正常：提高关注级别，**不自动认定身体疲劳或禁止训练**"——
这暗示孤立的 ACWR 升高应判 `elevated` 而非 `high`。那是一次**政策变更**，会改变 Coach 的对外判定
（red → yellow），必须带自己的测量。

本版 `risk` 与 `basis` 都是对现有判定的 **1:1 映射**（`attention`/`high_load` → `high`，
`insufficient_data` → `unknown`，其余 → `nominal`）。**该政策留给下一批，附回放对照。**

### 2.3 `acuteLoadExcess` 的未知值返回 `null`，不是 `0`

`0` 会被读成"算过，且没有超额"。输入缺失时返回 `null`，与 §9.4"它不是独立证据"的定位一致。
（与 §5.3 / §8.3 同一条原则：**不能让 0 冒充"算过且为零"**。）

### 2.4 `LOAD_RISK_BASIS` 的覆盖测试

`assessLoad` 用 `LOAD_RISK_BASIS[code] ?? "maintaining"` 兜底。这个 `??` 有风险：
分类器将来新增一条分支而这里没登记，就会**静默落到 `maintaining`** —— 把"没识别"说得像"正常"。

所以有一条断言：把子句的 **key 集合冻结成字面量**，并用 10 组探针把分类器实际吐出的 code 收集起来，
要求全部在表内。**新增分支必须同时改这张表，否则测试先红。**

## 3. 验收证据

### 3.1 形态扫描：那条子句的边际贡献（§9.5 的"离线比较"）

60 天、7 种负荷形态（恒定 / 3× 递增 / 10× 暴涨 / 锯齿 / 单次超大 / 递减 / 停跑一周）：

| 形态 | red 天数 | **仅靠子句判 red** | 最大 ACWR |
|---|---:|---:|---:|
| 恒定 | 0 | 0 | 1.000 |
| 前低后高（3×） | 6 | 0 | 1.517 |
| 前低后暴涨（10×） | 5 | 0 | 2.205 |
| 锯齿 | 0 | 0 | 0.844 |
| 单次超大 | 2 | 0 | 1.984 |
| 递减 | 0 | 0 | 0.875 |
| 停跑一周 | 0 | 0 | 1.000 |
| **合计** | **13** | **0** | |

分析边界的另一半：`loadRatio > 1.5` ⇒ 分类器判 `attention`，该行仍是 red
（例如 `{loadRatio: 1.6, trainingStatus: "attention"}`），语义未变。

**扫描本身写成了断言**，且带一条**非空检查**：

```ts
assert.ok(clauseTrue > 0, "the sweep must exercise rows where the clause is true, or it proves nothing");
assert.equal(clauseWouldChange, 0, "the clause could change a builder-produced verdict");
```

没有第一行，一个"从未触发"的扫描会**空过**——看起来全绿，其实什么都没验证。

## 4. 我在这一批犯的三个错（都记进分册）

### 4.1 探针用了**不存在的日期**，静默丢数据

第一版扫描把日期写成 `"2026-01-40"`（1 月只有 31 天）。暴涨恰好安排在第 36–40 天 ⇒
那几天的负荷**从未匹配到任何一天**，被静默丢弃。结果所有形态的 `max ratio` 都是 **1.000**，
我差点据此写下"该子句从不在高比值下触发"。

**判据**：造 fixture 时，任何"第 N 天"的日期都必须由**日期运算**推出来
（`new Date(Date.UTC(...) + n*86400000)`），不能手写字符串。

### 4.2 `Edit` 时把两行粘了起来

`old_string` 以 `{\n` 收尾、`new_string` 不以 `\n` 收尾 ⇒ 函数签名与下一行被拼成一行，
`buildDailyTrainingMetrics` 一度变成 `...(): DailyTrainingMetric[] {  if (loads.length === 0) return [];`。

**这条我记过，还是踩了。** 好在"改完立刻回读"抓住了。**删掉 `new_string` 末尾的换行就是删除下一行的开头。**

### 4.3 测试 28/28 全绿，**typecheck 却 3 个错**

`tsx` 只剥离类型不做检查，于是：

- `stimulusType: "aerobic"` —— 合法值是 `aerobic_base` 等，`aerobic` 不存在；
- `breakdown: null` —— 该字段不可为空；
- 探针对象缺 `recoveryEvidence`。

**老规矩（第四次了）：`npm test` 与 `npm run typecheck` 必须分开跑、分开报。**
一个绿不代表另一个绿。

### 4.4 三条现成测试依赖"手造的不一致输入"

`decideVerdict({...base(), loadRatio: 1.5})` 里 `base()` 的 `trainingStatus` 是 `effective_stimulus` ——
真机不可能出现（比值 1.5 会让分类器判 `attention`）。这些测试**借子句**表达"高比值必须 red"。

已按**原意**改为一致输入（`loadRatio: 1.5, trainingStatus: "high_load"`），
"恢复证据缺失不得掩盖高负荷"这条意图完整保留。

> 这也说明该子句此前**实际在服务的是一批构造出来的输入**，而不是生产数据 —— 与我扫描得到的结论一致。
