## 0. 结论先行

**RAI 的问题不是算法不够，而是「三件事同时成立」：上游数据有洞、中游有六份孤儿资产、下游日常闭环断裂。**

| 层级 | 核心问题 | 一句话证据 |
|---|---|---|
| 🔴 上游 | 跨源去重仅 **120 秒窗**，而小唐的数据正好是 connect/apple_watch/huawei **三源** | `canonicalize.ts:81,96,141`；`docs/DATA_AUDIT.md` 载 148/46/41 条 |
| 🔴 中游 | **6 份孤儿资产**：2 端点 + 2 表 + 2 算法导出，零生产调用方 | `server.ts:1432/679`；v10/v12 表；`physiology/src/ridge.ts:178` |
| 🔴 下游 | 漏课被**静默改写成休息**，计划-执行闭环是假的 | `mobile-coach.ts:1051-1062`；全仓 `missed\|adherence` 零命中 |

竞品调研给出的对照最刺眼：**Runalyze 官方定位"没有任何社交功能，纯粹的个人数据工具"，且没有 App、只做响应式网页；Intervals.icu 的官方定位是"分析平台优先于教练平台"。两者共同的成功法则只有三条：数据进入成本 ≈ 0、每周操作 ≤ 1 次、全靠减法立身。**

RAI 的算法层（五维评分 + HRR-TRIMP + EWMA + 恢复管线 + CatBoost 残差 + shadow gate）**已经超过了这两家的分析深度**。所以本次评审的主旋律不是"补算法"，而是**接通 + 收敛 + 减法**。

> 🔴 **裁决层最重要的一次否决**：科学派与红队都主张「下线 CatBoost ONNX 残差」，理由是其为孤儿能力、样本仅约 235 条、易过拟合。
> **该主张的事实基础是错的。[亲验]** `OnnxCatBoostResidualModel` 是**活的生产路径**：`packages/application/src/prediction-report.ts:19,467,509,707` 与 `prediction-training-runner.ts:22,556,685` 均在实时加载与推理；`applyRaceResidualRidge` 也在 `prediction-report.ts:279` 被调用。**唯一真孤儿是 `predictRaceResidual` 这个同包内部函数（`ridge.ts:178`，仅被 `ridge.ts:200` 调用）——它压根不该被当成"独立能力"来讨论。** 不予采纳。

## 2. 三派立场摘要（原话压缩）

### 2.1 产品体验派

> 核心判断：**RAI 不缺算法，缺"每天打开就有答案"**——能力都做完了，却散在孤儿端点、iOS-only 入口和被静默改写的计划里，跑者感受不到。

| 主张 | 优先级 | 验收标准（其自述） |
|---|---|---|
| 修漏课被改写成休息 | P0 | 漏 2 次课后，周计划显示 missed 与 adherence%，不再写成 rest |
| 打通"今日一屏" | P1 | 桌面不点二级菜单即可看到今日建议与恢复状态 |
| 主观数据最小录入（含 sRPE） | P2 | iOS/Web 都能 15 秒内提交一次 RPE，落库并进今日卡 |
| 修 120 秒去重窗 | P3 | 双设备起跑相差 >2min 只落一条，里程/TRIMP 不翻倍 |
| 至少一次后台触达 | P4 | app 未打开也能完成一次增量同步或收到一条本地通知 |

**它反驳红队最有力的一句**：*"我主张的是接通库存，不是新增算法。那 6 份孤儿资产——成本已付、收益未交付，接通边际成本≈0。"*
**它主动砍掉**：跑姿指标打分、ACWR 伤害告警、周计划自动调优（"adherence 数据都还没有"）。

### 2.2 运动科学派

> 核心判断：**RAI 能算负荷，却答不出"这个配速是 easy 还是 threshold"，也没有任何信号区分"变强了"和"只是练累了"。**

| 主张 | 算法要点 | 验收标准（其自述） |
|---|---|---|
| **Critical Speed** | D = CS·t + D′，取近平路段滚动最快 3/7/12 min 最小二乘（Hunter 2023，r=0.67）；**只出 CS 不出 D′ 点值** | CS 推得配速落在同人有效 VDOT 的 T 配速 ±10 s/km |
| **心率-配速解耦** | 剔前 10 min，按时间对半，Δ=(GAP₂/HR₂)/(GAP₁/HR₁)−1，>5% 提示有氧耐力不足/热应激 | ≥40 min 稳态跑，6 周块内 decoupling 中位数降 ≥2 个百分点 |
| **sRPE** | RPE(1–10) × 分钟；以个人 sRPE/TRIMP 中位数为基准，偏离 >1.5 IQR 标记 | sRPE–TRIMP Spearman ρ ≥ 0.7 |
| **Taper 规划器** | Bosquet 2007：8–14 天、减量 41–60%、强度不变、频率降 ≤20% | 赛前 14 天里程落峰值 40–59% |
| rTSS（可延后） | GAP 30s 滚动 + 四次方加权 | — |

**它反驳红队最有力的一句**：*"新增指标不改行为，只在指标不进入下一次训练时成立。CS 改配速、decoupling 改增量、sRPE 改明日上限、taper 改赛前课表——没有一条是图表。"*
**它主动砍掉（这是本次评审最有价值的一节）**：五维**点值分 → 降为趋势/个人分位**（Stability 底层是垂直振幅/触地时间、Recovery 底层含单日 HRV，证据弱）；**乳酸阈点值配速 → 改区间**；ACWR 降为负荷变化率描述；Monotony/Strain 降为趋势。

### 2.3 红队怀疑论者

> 核心判断：**"你们想加的东西，已经在这个仓库里孤儿化了六份。先证明新提案不会变成第七份。"**

**它对 11 条主张只批准 4 条，其中 3 条是复用已有资产：**

| 主张 | 判断 | 理由（其原话压缩） |
|---|---|---|
| 今日一个结论 | 做 | 这是**重排不是新建**，符合竞品"减法立身" |
| 补 RPE 录入 | 做 | `workout_overrides` 表 + 端点已存在，缺的只是原生入口；**采集端无入口＝永远没数据** |
| 修计划-执行对账 | 做 | 漏课静默变 rest 是**数据造假**，不是缺功能 |
| 解耦 | **做** | *"这是我唯一真心支持的科学派主张"*：八类同步时序 + GAP 已在代码里，纯函数、零新数据 |
| sRPE | 做 | 与产品派 RPE **是同一件事，两派重复立项**；复用同一字段 |
| 酸痛/睡眠质量 | 推迟 | 睡眠已进恢复权重，边际信息未验证 |
| iOS 全端功能对等 | **砍** | 每能力双端实现 + 双端验证，维护面直接翻倍 |
| 装备里程提醒 | 砍 | 要建 shoe 表 + 录入 + 通知子系统；不提升可信度 |
| Critical Speed | **砍** | 与已有 Riegel/VDOT/乳酸阈/成绩预测**定义域重叠**，会产出第二个阈值口径 ⇒ 用户看到两个不一致的数＝不可信 |
| rTSS | 砍 | 与 HRR-TRIMP 并行＝同一曲线两个值，趋势/门限/状态全要重标定 |
| Taper | 推迟 | 给一个对账都没修好的计划系统再加规则；一年用两三次 |

**它的判决书**：*"孤儿清单是判决书：2 个端点 + 2 张表 + 2 个算法导出同时零引用，而这恰好就是'新表/新端点/新算法/新入口'四个抽屉——两派提案的全部交付形态。历史不是失败一次，是四类资产同时烂尾。"*

## 3. 裁决层：逐条裁决表

**裁决原则（三条）**
1. **数据正确性 > 分析深度 > 交互体验**。上游脏了，下游所有置信区间无意义。
2. **能复用已有资产的，优先级高于新建子系统的**。孤儿资产 = 沉没成本，接通即净收益。
3. **判据是"是否改变下一次训练"，不是"是否能多画一张图"**。

| # | 主张 | 裁决 | 裁决理由（裁决层独立判断） |
|---|---|---|---|
| 1 | **修跨源 120 秒去重窗** | 🔴 **P0-1 立即做** | 三方罕见共识。科学派称其为"前置必修"，红队列为第 1 项，产品派列 P3。**我把它提到最高**：它是唯一会**污染全部下游指标**（TRIMP/EWMA/五维/预测/周计划 LLM 输入）的缺陷，且小唐的设备组合（connect+apple_watch+huawei 三源）正好命中。⚠️ 注意：**不能让 120s 变成 10min 了事**——需要按起跑时间聚类 + 输出"疑似重复待确认"清单，否则会误并真正的双课 |
| 2 | **修计划-执行对账** | 🔴 **P0-2 立即做** | "静默改写成 rest"是**数据造假**而非缺功能（红队措辞准确，我采纳）。更严重的是：它污染了周计划 LLM 的上下文——LLM 看到的历史全是"计划=已完成"，于是永远学不到小唐的真实执行率 |
| 3 | **今日一屏收敛** | 🟡 **P1 做（限定形态）** | 做，但采纳红队的边界："**重排不是新建**"——只改 `/v1/mobile/today` 的渲染与 Web 调用方，**不加端点、不加表**。同时采纳科学派的反对：**不许扩成多结论面板**，就一个结论 + 折叠依据 |
| 4 | **主观输入（RPE/sRPE 合并）** | 🟡 **P2 做（合并立项）** | 红队抓得准：**产品派的"RPE 录入"与科学派的"SRPE"是同一件事**，两派重复立项。合并形态：复用 `workout_overrides` 表与 `/v1/workouts/:id/override` 端点，**只在原生加一个 sheet**，零新表。RPE×时长是纯计算，另加一个函数即可 |
| 5 | **心率-配速解耦** | 🟡 **P3 做** | **本次评审唯一三方零争议的新增指标**：红队"唯一真心支持"、产品派未反对、科学派有 Hunter 2025 循证。关键优势是**零新数据、零新表、纯函数**（GAP 和八类时序都已在代码里）。采纳红队边界：**详情页一行百分比 + >5% 文案，不进告警系统** |
| 6 | **Critical Speed** | 🟢 **P4 做，但改形态：作校准器，不作新指标** | **这是裁决层对红队与科学派的双向否决。** 红队说"定义域重叠会产出第二口径"——风险真实；科学派说"现有分区是间接预测、CS 是实测"——[亲验] **该事实成立**：配速分区确实来自成绩反推（`recompute-pipeline.ts:1235` 调 `estimateLactateThresholdFromPerformanceVdot`，喂给 `thresholdPace`），而非本人实测。**调和方案：CS 不作为独立展示的第二个阈值，而是作为「分区一致性校验器」** —— 当 CS 推出的配速与 VDOT 推得的 T 配速偏差超阈值时，提示"你的分区可能偏离实测"，走项目已有的 shadow gate 思路。**这样既用上实测锚点，又不产生第二口径。** 科学派"无硬跑不出值"的要求予以保留 |
| 7 | **Taper 规划器** | 🟢 **P5 推迟，降级为 prompt 约束** | 采纳红队最小形态："塞进计划生成 prompt 一条约束，不建模块"。Bosquet 2007 证据虽强，但一年用 2–3 次、且当前计划对账尚未修好，**没有资格在坏地基上加规则** |
| 8 | **rTSS** | ⬜ **不做（记为设计债务）** | 采纳红队：与 HRR-TRIMP 并行会迫使趋势/门限/状态全量重标定。若将来 CS 落地且 HR 型负荷在短间歇上被证实系统性低估，再作为**替换**（而非并存）评估 |
| 9 | **孤儿清算** | 🟡 **P1 与今日一屏同期做** | 红队主推"删除或接通"、产品派主张"接通"——**两者不矛盾**：原则是**每个端点/导出必须有 ≥1 个生产调用方，否则删除**。`/v1/openapi.json` 无消费方（可保留但降为调试工具，不算孤儿）；`import_batch_files`/`import_entity_generations` 两表零读写路径 —— 需先判定 v22 迁移是否仍依赖，**不可盲删** |
| 10 | **iOS 全端功能对等** | 🔴 **明确不做** | 采纳红队的核心反对：双端实现 + 双端验证 = 维护面翻倍。**唯一例外原则**：**采集类入口必须上原生**（RPE、备注），因为"采集端无入口＝永远没数据"；**展示类不追求对等** |
| 11 | **通知系统** | 🟢 **推迟** | 全仓零命中意味着从零建子系统（含 entitlement、后台模式、权限引导）。而小唐的核心动机是"跑完看结论"，App 一打开就有答案已覆盖 90% 场景。**先做 P1 今日一屏，观察两周再决定** |
| 12 | **跑姿打分降级** | 🟡 **做减法** | 科学派与产品派一致、红队支持。垂直振幅/触地时间腕表误差大、与跑步经济性相关弱（Gómez-Molina 2022）⇒ **从打分区降为趋势异常区**。⚠️ 保留数据展示（小唐是数据控），只撤销"打分"这个**判断动作** |
| 13 | **乳酸阈点值 → 区间** | 🟡 **做减法** | 无气体交换/乳酸测试即无真值。同向处理"精确到秒的阈值配速" |
| 14 | **五维点值分降级** | ⬜ **部分采纳，需先验证** | 科学派主张降为趋势/个人分位。**我不全盘采纳**：五维是 RAI 的**招牌与差异化**，且点值有个人基线归一化（`createPersonalBaseline`）。但其中 **Stability（跑姿类）与 Recovery（含单日 HRV）两维的底层证据确实弱** ⇒ **先只降这两维，保留 Efficiency/Pace/Cardio 点值** |
| 15 | **CatBoost 下线** | 🔴 **否决** | 见第 0 节。[亲验] 事实基础错误，是活的生产路径 |
| 16 | **装备里程提醒** | ⬜ **不做** | 采纳红队：要建 shoe 表 + 录入 + 通知三个抽屉。**降级为审计页一行累计里程**即可满足实际需求 |

## 4. 裁决层补充：三派都没抓到的两件事

### 4.1 🔴 信息架构是"按数据源组织"，不是"按今天该做什么"组织

竞品调研给出的最锋利用对照：**Garmin 把 Training Readiness 0–100 收敛成唯一入口，下面挂 Target Exertion Zone** —— 用户早晨只回答一个问题："今天该练多重"。而 RAI 的现状是：

| 端 | 组织方式 | 证据 |
|---|---|---|
| Web | 8 个平级页面（概览/训练/分区/统计/趋势/预测/数据/设置） | `apps/web/src/App.tsx` 路由 |
| iOS 壳 | `/week`、`/body` **无底部 Tab 直达**，桌面端**完全无入口** | `apps/web/src/ios/App.tsx` |
| 移动端载荷 | `today` 一个端点返回 **17 个载荷字段** | `apps/api/src/mobile-coach.ts` |

**17 个字段返回给用户，等于没有结论。** 这与产品派的"今日一屏"是同一个诊断，但更深一层：**不是把已有内容挪到首屏，而是要决定首屏"只回答一个问题"。**

### 4.2 🟡 缺「明日负荷上限」这个单一数字（Runalyze 的 Easy TRIMP）

三方都没提，但这是**成本最低、行动性最强**的一条：

- RAI 已经有 EWMA 急慢性负荷与 TSB 类指标 —— 但它们是**描述**（"你现在是 -12"），不是**指令**。
- Runalyze 的招牌做法：把 TSB 反解成**一个数字** —— "明日建议 TRIMP ≤ X 可维持 TSB≈0；今日已超则建议休息 N 天"。
- **成本核算**：纯确定性计算，输入全部已有（`packages/training-load` 的 EWMA），**零新表、零新数据、零新端点**（塞进 `today` 载荷即可）。
- **为什么它比 CS/rTSS 更值得做**：它直接回答"明天最多练多少"，而 CS 回答的是"该跑多快"——**后者已有分区覆盖，前者是空白**。
- 且它天然与"周计划锁课"形成软约束闭环：锁课时若超出明日上限，给一句提示。

### 4.3 🟡 缺「预测值 × 训练结构」的折扣（Runalyze Marathon Shape）

RAI 有 5K/10K/半马预测**点值**，但**没有"你的训练结构撑不撑得起这个预测"**。Runalyze 的 Marathon Shape 用 6 个月窗口、周里程占 2/3 + 最长单次占 1/3，锚点 10K=17%、半马=42.5%、全马=100%。

**成本核算**：输入全是已有里程数据 + 已有预测值，纯计算，无新表。中等成本，可在 P3 之后插入。
**价值**：它正好补上"预测高估"这个已知偏差（Vickers & Vertosick 2016：5K→全马常高估 5–15%）——**给小唐一个"这个预测要打几折"的诚实修正**，契合他风控出身的思维。

## 6. 一句话给三派

- **给产品派**：你说得对——但"接通库存"要证明**接通后有人用**。`/v1/import-sources/recent` 接通了也可能没人点，所以先接通的是"每天必然被打开"的那个入口。
- **给科学派**：CS 的价值不在"多一个阈值"，而在"**校验现有阈值是不是错的**"。改形态之后，你的主张从"加指标"变成"修指标"，红队的反对随之失效。
- **给红队**：你的判决书成立，但**六份孤儿不等于第七份必然烂尾**——判据是"是否进入每日决策链"。解耦与明日负荷上限都在链条上，CS 以校准器形态进入链条，其余推迟项则确实该等。
