## 2 本轮目标：深度审查"架构"，不是复述缺陷

对每条结论都要能回答其中之一：

1. **结构与边界**：实际有哪些容器/进程/线程/包？依赖方向是否符合声明？有没有反向依赖、循环、越层调用、
   "文档里分层、代码里穿透"？
2. **职责与单一数据源**：同一业务规则是否只有一处实现？哪些规则在 API / application / storage / iOS 各有一份？
   写路径是否收敛到"单写者 + 发布"？退役接口是否真的没有消费者？
3. **一致性与并发模型**：读快照 / generation / datasetEpoch / 锁 / 租约 / 队列 / 事务边界，哪里是"设计上可接受"、
   哪里是"靠调用方自觉"？失败开放还是失败关闭？
4. **故障隔离与可伸缩性**：单进程、单写者、单 SQLite 文件在什么规模下失效？线程隔离、内存预算、超时、背压、
   重试与幂等是否形成闭环？iOS 侧后台/网络/缓存失效如何处理？
5. **可演进性**：契约（TS DTO ↔ OpenAPI ↔ Swift Codable）怎么版本化？迁移策略（46 个 migration、冻结规则）是否可长期维持？
   新功能应该加在哪一层？现有代码的**改动成本**（god file、重复实现、耦合）如何？
6. **质量系统架构**：门禁/测试/文档本身是否构成可信的反馈系统（假绿、孤儿门禁、文档漂移、跳过语义）。
7. **安全与运维边界**：鉴权、上传、备份、部署拓扑、密钥、日志可观测性是否与架构假设一致。

**不要求**：重跑所有测试、复现所有 P2 缺陷、给每个历史问题编号。要求：**结构层面的判断有证据、有规模感、有优先级**。

## 3 证据纪律

- 严重度沿用仓库惯例：P0 数据丢失/安全漏洞/生产不可用；P1 发布阻断或硬架构不变量被破坏；P2 用户可见错误或
  高概率结构性风险；P3 低影响/防御性/可维护性/文档。
- 证据等级：**E1** 代码/配置逐行阅读（静态确认）；**E2** 已实跑命令、测试或探针（附输出）；**E3** 合成夹具/推断（写明前提）。
- 每条发现必须给 `文件:行号`（对齐 HEAD `9db450f`）或可重跑命令；**逐条核对行号**，不要抄文档里的旧行号。
- 文档承诺不能当实现证据；"测试绿"不能当断言有效证据（写明是哪个命令、什么输出）。
- 允许在 `/tmp` 建合成 SQLite/XML 探针；**禁止读写 `var/` 下的真实库/备份/健康数据**，禁止迁移、导入、部署、`git add/commit/push`。
- 不跑全量 `npm test`、`npm run test:ios`、`npm run smoke:api`（Lead 统一跑并在最终报告里给统一基线）；
  lane 可跑**定向**测试文件（`node --import tsx --test --test-name-pattern ...`）与 `node -e`/`tsx -e` 小探针。
- 不 `npm install`，不改 `package.json`/锁文件，不改任何被跟踪文件。
- 写盘只允许：本 lane 报告 `deliverables/architecture-review-2026-10-20/<你的文件>.md`，以及 `/tmp` 下探针。
