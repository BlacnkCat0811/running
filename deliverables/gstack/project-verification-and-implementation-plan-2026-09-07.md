## 1. 结论与边界

**项目存在实际的数据解析、存储、计算、API 和 Web 展示链路，具有真实工程实现；不能据此证明评分在运动科学上的准确性，也不能证明当前部署已通过验收。原评审有真实问题线索，但不宜直接作为实施清单。**

本次将“真实性”分为三个层面：

| 层面 | 核验结论 | 证据边界 |
|---|---|---|
| 项目是否只是界面演示 | 已核对到解析器、SQLite 迁移与仓库、回放流水线、真实 API 请求和测试资产；不是仅凭截图描述功能 | 未启动服务、未导入个人健康数据，未验证当前端到端运行成功 |
| 原报告的问题是否属实 | 部分属实，部分已被后续实现改变，部分推断或评级不成立 | 当前代码比旧基线多 3 次提交，比较涉及 46 个文件；旧行号不能直接当当前证据 |
| 输出是否可当作真实跑力/生理真值 | 目前不能作此保证；CA/TA、生理与赛事结果属于模型估计 | 未重跑当前数据回测；历史文档中的样本量、预测值不是本次复测结果 |

主要更正：

1. 激活逻辑确有重复，但 `EXISTS failed` 与 `WHERE status='failed' ORDER BY ... LIMIT 1` 在判断“是否存在失败”时等价，不能据排序差异宣称存在门禁绕过。
2. 实际服务已把目标写入 `rai-control.sqlite`，旧 JSON 作为迁移来源和兼容路径存在。应处理“业务库、控制库、运行时库的生命周期”，而非仍以 JSON 为生产主路径设计修复。
3. 导入入口已有互斥锁且直到任务终态才释放，也检查模型任务忙碌状态。“无显式互锁”不符合 HTTP 主路径现状；跨进程和异常恢复仍需专门验证。
4. `StatusBadge` 显示文字，不是仅颜色编码。CA 圆点本身无键盘操作，但图表已提供可展开的等价训练链接，不能描述成整条操作链路键盘不可达。
5. 无暗色模式、多个绿色、文件较长属于体验或维护问题，不应与数据丢失风险并列为最高严重度。
6. 当前开发边界已明确为桌面 Web。无需先把 iOS 升格主力产品，也不应把移动页面、原生壳或小屏优化纳入本次实施范围。

## 4. 本次补充发现

### 4.1 恢复趋势在中国时区早晨可能漏掉“今天”

证据：`apps/api/src/data.ts:642` 先 `new Date().toISOString().slice(0, 10)` 取得 UTC 日，再拿该日期查询 `Asia/Shanghai` 的 canonical 事实。

例如上海 2026-09-07 07:30 对应 UTC 2026-09-06 23:30，最后查询日期会是 09-06。即使今天睡眠已导入，端点也可能未查今天。属于代码可推导的边界缺陷，本次未运行复现。

同一路由没有 querystring Schema，`days=abc` 会转换为 NaN 并可能返回空列表，`days=1.5` 没有清晰整数语义。应补合法整数和日期参数校验，再接前端。

### 4.2 首页“同一量纲”文案与真实图表不符

证据：`DashboardPage.tsx:132` 描述“同一量纲”；`DashboardPerformanceChart.tsx:117` 起使用评分轴和独立负荷轴，负荷轴上限会按数据变化。三条曲线高度不具有直接可比性。

建议先修正名称、单位和说明；评分和负荷分图或明确双轴。不要为了统一曲线外观再把负荷任意归一化为能力分。

### 4.3 控制库已经引入，但可靠性验收没有同步体现

证据：生产实例传入 `controlDatabasePath`；`apps/api/test/mobile.test.ts:291` 起的目标存储测试仍实例化不带控制库路径的旧 JSON 分支。在已检查文件中未见针对控制库迁移及并发 revision 的专门测试。

生产迁移中复制备份、写迁移标记发生在首次插入完成之前，初始目标与历史记录插入也未包在同一个事务内。若第二次写入失败，可能出现目标已有、历史缺失，而后续启动按“目标存在”跳过初始化。需要故障注入确认影响，按幂等迁移设计补齐。

### 4.4 “模型门禁存在”不等于“模型准确”

现有 shadow gate 比较候选与原模型的差异，主要用于回归保护，不是独立科学真值验证。两份模型输出相近，也可能一起偏离实际能力。

`docs/MODEL_VALIDATION_PLAN.md` 明确反对拿自身输出验证自身，历史样本只能支持有限原型验证；`docs/PHYSIOLOGY_PREDICTION_BASELINE.md` 也明确预测非医学检测结果。当前应建立持续的外部标签回测证据，并在用户界面保留估计性质、样本和时效信息。

### A. 多库生命周期

推荐保留现有控制库隔离，暂不把 goals 搬回会被导入替换的业务库。若直接入主库，staging 在旧时间点克隆后，用户后来修改的目标可能随换库回退，反而引入新风险。

拟定资产政策：

| 资产 | 备份政策 | 恢复政策 | 删除政策 |
|---|---|---|---|
| 业务 SQLite | 在线一致性快照，含 schema/dataset/model 元信息 | 必要表、外键、版本校验后发布 | 现有“删除分析库”保留安全快照，文案明确范围 |
| 控制 SQLite | goals、history、revision 纳入完整备份 | 完整恢复时配套恢复；分析库单独恢复时保留目标并重新验证锁定建议 | 不随分析库删除静默清空；完整个人数据清除单列动作 |
| runtime SQLite | 明确区分可重建任务与导入来源记录 | 导入旧任务不得自动当作仍在运行；失效来源重新发现 | 按保留策略清理任务、来源路径和上传记录 |
| 模型 artifact | 完整恢复需含正在引用的 artifact 或可验证重建策略 | 校验 hash、基线；缺失时明确回退公式预测，不保留虚假的激活状态 | 明确清理范围 |
| 原始导出/上传/迁移 JSON 副本 | 标注是否包含，避免用户误认为全量归档 | 缺失时仍可浏览已恢复分析，但不可宣称可重新解析 | 完整清除需要独立显式确认；普通分析库删除不波及原始文件 |

完整备份方案应带 manifest、各文件 checksum、创建时间、版本、包含与排除清单。SQLite 使用在线 backup API，不能复制活跃主文件后忽略 WAL。若需要跨库同一时点，短时冻结相关写入后逐库快照，成功后才发布 bundle。

多个文件不能靠多次 rename 宣称整体原子。短期实现需维护恢复事务日志及全组回退路径；长期可评估版本目录加单一指针切换，另行核对 Windows/部署环境文件语义。备份内容不得包含 API 密钥。

控制库迁移调整为幂等事务：读取与校验旧文件，保存原始副本，在事务内创建目标及对应历史，提交成功后再写完成标记；损坏不能自动伪装成默认值。增加控制库关闭、重开、并发保存冲突和重试能力。

### B. 时间和恢复口径

制定字段字典，至少包括 `asOf`、`timezone`、`latestDataDate`、`generatedAt`、`evidenceDate`、`status`、`missingReasons`。其中时钟时间和数据最新日不可混用。

先固定兼容策略为 Asia/Shanghai，并修复 UTC 与本地日混用；跨时区功能另分阶段。运行时环境变量不能直接改写历史分组语义，历史 Run 必须能追溯当时使用的时区。未来支持 IANA 时区时，夏令时不能靠固定 SQL `+8 hours` 参数替换解决。

恢复保留不同概念：训练内恢复维度用于该次评分；每日睡眠/RHR/HRV/负荷事实用于当日状态；赛事预测修正用于明确场景。共同复用 canonical 事实与基线，不强制同一个数值输出。未知数据保持 null，显示原因，不能补成 0 或默认“恢复良好”。

先移除桌面中退役 `recoveryEvidence` 的展示依赖，维持旧 DTO 兼容；服务端读取结果的有效性、样本数、基线不足、时效都应明确。移动死代码仅记录为后续事项，本轮不修改 mobile-only 实现。

### C. 模型激活

建立一个应用层激活入口，HTTP 负责入参和错误映射，仓库负责查询/写入。事务必须覆盖“验证候选、切 active 指针、清除旧预测激活状态”全过程；流水线已有外层事务时要明确所有权，避免嵌套 BEGIN。

显式保留和测试：候选不存在、状态未完成、统计缺失、gate failed、gate skipped、无 gate 的历史兼容、已有预测模型、数据库正忙、写入失败。当前是拒绝任何失败 gate；若将来改成“当前门禁版本有效通过”，必须作为单独政策变更，不能藏在去重重构中。

缺 gate/skipped 不应一律禁用，否则可能破坏首次导入和历史数据兼容。先规定首次模型、历史模型和普通候选分别允许什么，再考虑更严格门禁。

### D. 桌面信息架构与首页

第一屏用紧凑汇总展示“跑力估计 TA”、快照日期、7 日变化、最新 CA 与置信度；只展示后端已有并有定义的值。7 日变化必须来自同一可比模型口径，换模型时标记不可直接比较。

最近训练区使用“最近训练均配”“训练稳定性”“近 7 日负荷”“该次恢复维度”等准确名称，分别带数据日期和单位。恢复趋势先提供睡眠与 HRV 实际已有字段，RHR/综合状态必须先扩充契约再展示。能力趋势与训练负荷分开或清楚标注双轴，不将不同量纲称作同量纲。

首屏必须处理首次导入、旧数据、无有效训练、部分健康缺失、读取失败与后台重算。重算期间保持旧结果可用并显示状态，不能先清空结果。恢复趋势优先放趋势页，概览仅摘要，避免首页承载全部分析。

### E/F/G/H. 维护与体验

契约先覆盖恢复趋势、目标、模型激活、备份四类关键端点；词表由常量推导类型和 Schema；区分公共 DTO 与内部存储输入。谨慎开启 response schema，验证序列化不会丢字段。只在 SQLite 行映射和 JSON 边界检查关键字段及有限数值，不增加每层重复验证。

桌面颜色和尺寸先在桌面容器内定义语义 token；保留冻结样式取值。逐组件替换颜色，完成视觉比对后再删被替代规则。保留现有图标库和像素风，建立当前 DESIGN 文档，注明哪些旧稿为历史参考。

可访问性以任务为准：键盘可进入详情、焦点可见、状态有文字、表单错误关联、200% 缩放可读。保留 AbilityChart 等价链接；需要点本身可聚焦时用合适 SVG 语义/键盘处理或明确等价交互，避免无效 HTML/SVG 嵌套。无需为达标强加装饰图标。

数据页以导入、任务进度、备份/恢复、重算为主操作，模型 hash、Run 和门禁放可展开高级区。桌面导航保持现有链接和深链兼容，明确提供审计入口；不改 mobileNavigation 和小屏导航。

架构按顺序局部拆：激活服务、控制库仓库、ImportWriter、流水线准备/计算/发布、各 worker。每个改动保留事务、取消、checkpoint 和 active 不变性，避免同时改 schema、算法、样式和任务调度。

## 7. 验收矩阵与发布控制

| 场景 | 必须证明的结果 | 建议验证层 |
|---|---|---|
| 激活失败 | 原 TA/CA 运行与预测激活指针均不变，无半提交 | 仓库+应用集成+HTTP |
| 激活成功 | 训练统计对应正确，旧预测失效可见，新 active 一致 | 应用+HTTP |
| 首次模型/旧模型 | skipped/no-gate 依明确政策处理，首次导入可用 | 应用 |
| 导入与重算竞争 | HTTP 拒绝冲突；异常重试、CLI/跨进程受发布约束 | server-runtime+独立进程故障测试 |
| 备份中断/磁盘不足 | 无不完整“成功备份”；已有备份仍可读取 | 临时目录文件故障注入 |
| 完整恢复中断 | 主库/控制库不留混合半状态，原版本可恢复 | maintenance 集成 |
| 目标旧 JSON 迁移 | 有效迁移一次；损坏保留原文并报错；中途崩溃可重试 | 控制库专门测试 |
| 两次旧 revision 保存 | 一次成功，另一次冲突；历史与当前版本一致 | 两个连接/实例集成 |
| 当地日边界 | 上海 00:00/07:59/08:00 日期一致；跨午夜睡眠按规定归属 | 固定时钟黄金用例 |
| 参数与缺失 | 非法 days 拒绝；无睡眠/HRV 保持缺失，不生成正常状态 | API 契约 |
| 无数据/陈旧/重算 | 用户能导入和重试；历史结果带日期；重算不清空旧结果 | 桌面页面与 E2E |
| 图表与键盘 | 单位正确，详情可键盘访问，200% 缩放可读 | 桌面浏览器 |

未来默认检查为 `npm run typecheck`、`npm test`、`npm run build`；涉及桌面流程时再运行 `npm run test:e2e:web`。当前脚本虽与 responsive 指向同一个测试文件，但文件通过 `npm_lifecycle_event` 选择桌面/响应式用例，不能误判为必然运行 390px 测试。

主验收视口 1440×900，另检查 1024 宽桌面边界；Chrome 和 Edge。不得运行响应式全套或修改 390px 基线。本轮不加入手机截图、原生壳变更和小屏重新设计。

涉及迁移和恢复必须先对隔离副本演练。已发布迁移保持不可变；需要新 schema 时只新增版本并验证旧库升级。部署前保存当前代码版本、完整可用备份及恢复步骤；先完成读写与恢复冒烟，再允许例行导入。

## 8. 模型真实性后续验证方案

另设持续评估轨道，不以增加模型复杂度为先：

1. 冻结数据区间、来源、标签定义、代码/配置版本，保存不可混淆的评估 manifest。
2. 按时间 walk-forward，杜绝未来恢复基线进入历史预测；禁止用同一评分公式生成的标签证明自身准确。
3. 优先使用实际比赛、标准化测试跑和记录时点明确的主观 RPE；设备 VO₂max 标注为设备估计，不作唯一真值。
4. 对比分数稳定性、异常输入敏感度、来源差异；赛事预测统计 MAE/中位绝对误差及有效标签数，有区间时再验证区间覆盖率。
5. 单独报告 5K/10K/半马、室内/室外、稀疏/充分数据；样本不足直接报告不足，不发布全局“准确率”。
6. 模型候选需同时通过软件回归门禁和独立效果评估；无法证明优于简单基线时保持公式回退或现有模型。

评估基础设施与报告整理可预留 3–5 人日；有效标签积累时间取决于实际训练，不能承诺一周内完成科学验证。当前没有足够新证据给项目打“8–9 分”或宣称模型已验证准确。

## 9. 不建议现在做的事情

不调整主力产品为 iOS，不重写原生评分，不扩展移动端教练页面。不要为消除多个恢复概念重写所有公式；不要为视觉统一重排全站；不要一次替换全部 CSS、迁移 hash、强制类型转换或 worker 架构。未证明发生的问题先补验证，再决定是否修复。

本方案建议的实施顺序为：**可恢复的数据资产 → 准确的日期与指标含义 → 一致的模型切换 → 桌面价值闭环 → 渐进维护治理。**

本次仅完成核验与计划编制，未执行上述任何实施阶段。
