# RAI 数据模型、产品功能与 iOS UI 审查及实施方案

审查日期：2026-09-07。对象：当前工作区代码与本机运行中的 iOS Web 界面。

补充范围：第 7–14 节为数据质量、成绩预测、VO₂max 和 CA/TA 跑力准确性专项。它们细化并扩展第 4 节的步骤 10，包含实际代码发现、模型改动、实验顺序、数据采集、验收门槛和新增工期。

## 1. 优先修复的问题

以下 P0 表示个人云端版本上线前必须解决；P1 表示日常使用可靠性问题；P2 表示体验及持续优化。排序不是漏洞评级。

### P0-1：过期或缺失恢复证据，仍可能建议质量课

- 证据：[mobile-coach.ts](../apps/api/src/mobile-coach.ts#L175) 的 `stale` 只在末尾追加文案；绿色分支不要求睡眠、HRV、静息心率证据有效。[Home.tsx](../apps/web/src/ios/Home.tsx#L208) 继续提供锁定按钮；[server.ts](../apps/api/src/server.ts#L680) 锁定接口未校验新鲜度。
- 实际复现：沿用现有测试中允许质量课的输入，仅把数据日期改为 2026-08-01，得到 `green + tempo`；将睡眠、HRV、静息心率和 recoveryEvidence 全部设为 null，仍得到 `green + tempo`。
- 影响：页面说“先同步”，却仍可生成、锁定一堂强度训练，行为与提示冲突。
- 处理：在后端建立证据门槛，再生成建议和接受锁定。未知状态不能等价于恢复良好；允许查看历史，但不给缺乏证据支持的质量课许可。具体门槛需要结合个人历史验证。

### P0-2：健康数据云端上传与授权文案冲突

- 证据：[Info.plist](../apps/ios/RAI/Info.plist#L17) 明确写“不会上传云端”；[ServerSession.swift](../apps/ios/RAI/ServerSession.swift) 支持任意 HTTP/HTTPS 服务地址，实际导出会上传到所配置服务。
- 影响：直接把地址换成云端，会违背当前向用户说明的数据处理方式。
- 处理：区分本地和云端构建配置，云端版本在授权前说明数据种类、处理地点、保留与删除方式；生产使用可信 HTTPS；调试网络例外仅留在 Debug。

### P0-3：WebView 凭证注入缺少目标来源限制

- 证据：[AppWebView.swift](../apps/ios/RAI/AppWebView.swift#L418) 给所有 fetch/XHR 自动附加 Token，没有限制为可信 origin 的 `/v1/`；导航允许同 host 的不同协议/端口；消息入口未检查主框架和发送来源。
- 影响：页面引入跨域请求、同主机其他服务或不可信嵌入内容时，可能扩大凭证暴露和原生操作调用范围。代码审查发现风险，未执行实际外传攻击。
- 处理：校验完整 origin（scheme、host、port）及 API 路径；拒绝生产 HTTP 降级；原生桥检查主框架和 securityOrigin；令牌按服务保存，生产端增加设备撤销能力。

### P1-1：HealthKit 增量同步丢弃删除事件

- 证据：[HealthKitExport.swift](../apps/ios/RAI/HealthKitExport.swift#L687) 的 anchored query 回调把 deletedObjects 参数用 `_` 忽略，结果只返回新增训练与下一锚点。
- 影响：在 Apple 健康删除错误训练后，本系统可能长期保留它并继续计算跑量、负荷和能力。全量重导不能默认当作删除对账，因为“没读到”也可能是权限或范围变化。
- 处理：引入来源 UUID 映射和明确删除事件，重建受影响的 canonical session 及衍生数据。多来源同一训练中只删除对应来源，不应误删其他来源的有效记录。

### P1-2：切换本地到云端后，旧同步锚点仍被复用

- 证据：[HealthKitSync.swift](../apps/ios/RAI/HealthKitSync.swift#L29) 用全局 UserDefaults 键保存锚点、导出时间和失败文件；不区分 server、账户或服务端数据集。
- 影响：手机已经同步到本地，改成空白云服务后仍只导出增量，云端缺失历史；失败 ZIP 也可能被重试到新服务。
- 处理：同步状态按 `serverId + athleteId + deviceId + sampleType + datasetEpoch` 隔离。换服务或恢复数据集后握手确认同步范围；不自动发送旧服务的待处理文件。

### P1-3：把“最近跑步日期”当成“数据同步新鲜度”

- 证据：[data.ts](../apps/api/src/data.ts#L225) 使用 `MAX(local_date)` from active_workout_training_loads；[mobile-read.ts](../apps/api/src/mobile-read.ts#L124) 今日没有睡眠时回退到前一天，却仍进入昨夜恢复展示。
- 影响：今天刚同步但没跑步，仍被认定数据过期；昨天的睡眠可能被标作昨夜。休息日和晨跑前尤其明显。
- 处理：拆开“最近训练”“最近同步”“各类样本覆盖截至时间”“模型数据版本”；每条恢复事实携带所属日期，过期事实不补到今日字段。

### P1-4：首次没有跑步时不能先同步恢复数据；同步恢复状态不完整

- 证据：[HealthKitExport.swift](../apps/ios/RAI/HealthKitExport.swift#L98) 首次没有训练就抛错，尚未读取全局恢复数据；恢复记录窗口复用跑步时间水位；[HealthKitSync.swift](../apps/ios/RAI/HealthKitSync.swift) 只持久保存失败 ZIP，没有持久化当前 sourceId、jobId 与待提交锚点。
- 影响：新用户即使有睡眠数据也无法进入有效恢复视图；长期不跑时可能反复读取增长的恢复时间段；App 在服务器导入中退出后不能直接恢复观察原任务。
- 处理：各样本类型独立游标；允许零训练、非零恢复记录导入；将整个同步任务落盘，先查既有服务端任务再决定重传。
- 额外风险：首次先普通查询 workouts、再 anchored query 获取锚点，两次查询间的新训练可能未进入导出却被游标越过，应改成一次锚定查询取得数据和锚点。

### P1-5：目标、周计划与锁课数据在 SQLite 之外

- 证据：[mobile-goals.ts](../apps/api/src/mobile-goals.ts#L86) 直接覆盖 JSON，读取损坏时静默返回默认值。数据库已有大量版本化分析表，但这些用户决策没有同等事务和历史保障。
- 影响：中断写入可能丢失目标或锁课；仅恢复主数据库不能保证还原用户计划。当前单进程同步写不等于已经出现并发冲突，主要风险是持久化与恢复一致性。
- 处理：迁到独立的用户控制数据表；加入 revision 和审计历史；特别注意导入流程会发布数据库副本，不能让发布动作覆盖导入期间的用户编辑。

### P1-6：训练列表分页可能混入旧筛选结果

- 证据：[Workouts.tsx](../apps/web/src/ios/Workouts.tsx#L76) `loadMore()` 完成后无条件追加；切换筛选虽然清空 extra，但没有取消旧请求或检查筛选版本。同步刷新首屏也没有同时使 extra 失效。
- 影响：弱网下“加载更多”后切筛选可能出现不属于当前筛选的训练；刷新后可能重复或漏项。
- 处理：请求取消、查询版本校验、按 ID 去重；刷新时重新获取整段分页，或迁移到包含数据版本的稳定游标分页。

### P2：iOS 界面存在明确可用性与语义问题

- 首页：“先同步”、能力大卡、今日裁决、恢复、处方依次堆叠；关键动作在首屏以下，信息状态互相冲突。
- 配速：本机实际显示 `6'28"–--`，应把单边区间显示为“6'28"/km 或更慢”等与区间含义一致的文案，未知值则显示“暂不可用”。
- 训练：列表前常驻四排筛选；CA、资格等专业信息与距离、配速抢占空间。
- [Physiology.tsx](../apps/web/src/ios/Physiology.tsx#L150) 把最近训练平均配速称为“有氧配速”。虽然正文有解释，但标题仍易产生错误理解。
- [ios-pixel.css](../apps/web/src/ios-pixel.css#L100) 头像按钮为 36×36；多处说明字号 10px。缩小信息层级不能依靠把字缩到难读。
- 锁定/重新锁定缺少 pending、错误反馈；设置仍有“数据在 Mac”“手机不能离线使用”等调试语言。

## 2. 当前架构与功能判断

### 应继续保留的基础

1. SwiftUI/WKWebView + HealthKit 只读同步，分析在 Node/TypeScript 后端完成。适合个人云端版本，暂不需要重写整个原生 App。
2. 数据层已有原始记录、跨来源归组、training_sessions、特征运行、能力评估、日快照、负荷、分区、睡眠/HRV canonical 事实及模型验证门槛；不需要推倒重建。
3. 数据库有迁移账本、外键校验、导入批次、模型版本与发布机制。需要把新增同步和用户计划纳入这些边界。
4. 模型训练已有时间可用性约束、公式基线、留出验证与发布门槛。不能把“没有严谨验证”作为已有事实，也不能用测试通过证明生理预测准确。
5. iOS 已有首页、训练列表和详情、统计、趋势、身体指标、周视图、目标、课型/RPE/测试协议/排除修改。优化重点是完善闭环，不是重复开发这些入口。
6. 已有 Nginx、systemd、Token 校验和 SQLite 一致性备份设施。部署工作以完善、演练为主。

### 建议的产品边界

首版定位为“个人跑步记录、恢复参考、训练复盘和成绩区间预测”。跑步实时录制继续使用 Apple Watch/健康生态；本次不增加 GPS 录制、HealthKit 写入、持续后台监听或社交功能。

先完成个人单账户云部署，保留 SQLite 单写者架构。未来开放多人注册时，再系统性补齐租户隔离并评估 PostgreSQL。当前 `profile.id = 1` 和全局 active model 指针说明不能直接共享一个数据库给多个账户。

## 3. 数据模型的目标结构

下表为拟新增或扩展的逻辑模型，并非全部都必须新建实体表。实施前与现有 import_batches、runtime jobs、overrides 合并复用。

| 模型 | 关键字段 | 约束与用途 |
|---|---|---|
| athlete_profile | id、timezone、单位偏好、创建时间 | 个人版单个 athlete；不把鉴权设备等同于运动者 |
| device_credentials | device_id、token_hash、scope、revoked_at | 可单设备撤销；Token 明文只在签发时展示/下发 |
| sync_checkpoints | server_id、athlete_id、device_id、sample_type、dataset_epoch、committed_revision | HealthKit anchor 保留设备端；服务端只保存确认的批次与版本 |
| sync_batches | idempotency_key、payload_hash、source_id、job_id、status、counts、committed_at | 同键同内容返回原结果；同键不同内容报冲突 |
| source_entity_links | source_scope、sample_uuid、entity_type、entity_id、deleted_at | 来源 UUID 唯一；显式 tombstone，不根据空查询推断删除 |
| freshness / coverage | sample_type、checked_at、latest_sample_at、coverage_start/end、state | 无新样本也可成功同步；state 区分未知、无可用数据、有效、过期 |
| athlete_goals | athlete_id、weekly_distance、race_target、effective_from、revision | 从现有 goals JSON 迁入；变更可追溯 |
| session_plans | date、kind、目标区间、status、revision | 草案/确认/完成/跳过；保留历史，不仅保存“今天锁定” |
| recommendation_snapshots | evidence_as_of、data_revision、model_version、policy_version、reason_codes | 能回答“当时为什么建议这堂课” |
| workout_feedback | session_id、rpe、状态、submitted_at、score_seen_at | 复用 override 字段；新增时间语义，识别看分数后反馈偏差 |
| prediction evidence | as_of、样本数、来源、区间定义、验证状态 | 扩展现有预测快照，避免重复建第二套预测系统 |

时间统一存 UTC 时间点，另保留来源偏移、用户 IANA 时区和派生 local_date。睡眠归属日明确为醒来日。把 `Asia/Shanghai` 从多处硬编码集中到 profile 默认值；旅行时区处理需有一致规则，历史日期不随手机当前时区任意漂移。

单位在采集边界标准化：距离 m、时长 s、配速 s/km、心率 bpm、HRV SDNN ms。缺失值保留 null 和 missingReason；不填 0、不把 HRV SDNN 与 RMSSD 混用。

保持四层：原始事实 → 去重后的实际训练 → 可重复计算的特征/模型输出 → 可解释的产品建议。用户反馈与计划属于持久控制数据，不应因重算或训练模型被覆盖。

## 4. 详细实施顺序

### 第 1 步：建立验收基线与环境边界（0.5–1 人日）

1. 固定当前提交、数据库迁移版本及模型配置；通过现有一致性备份创建测试副本，不在真实健康库上做破坏性场景。
2. 明确 local、staging、production 三个配置：域名、API、runtime 根目录、数据集 epoch、客户端版本。
3. 列出 Debug 和 Release 差异：地址输入、Bonjour、HTTP 例外、日志、Token 保存方式。
4. 保存五个主页面与详情的基线；明确本任务的 iOS 专用界面在范围内，桌面和其他窄屏兼容区不做顺带改版。

交付：环境表、可恢复测试数据、验收案例清单。验收：测试环境写入不会影响真实库。

### 第 2 步：先封堵错误训练建议（1–2 人日）

1. 在 API contracts 中加入统一 freshness 与 evidence 状态，兼容保留旧 latestDataDate 字段。
2. 为“无当天恢复”“过期模型”“数据未校准”等生成明确 reason code；后端先判断可用性，再进入课型选择。
3. 修改 mobile-coach：未知或过期恢复不生成绿色质量课；保留保守休息/轻松参考并说明依据不足。
4. 修改 `/v1/mobile/lock`：校验建议 revision 和当前证据，过期返回可恢复的 409；前端重新拉取并提示。
5. 修改首页：need_sync 只提供同步和历史摘要，去掉可执行的旧处方；锁定操作加入 pending、禁重入、错误和重试。
6. 增加回归：旧日期、三种恢复全缺、单项缺失、恢复恶化、休息日、跨午夜、重复点击。

涉及：mobile-coach.ts、mobile-read.ts、data.ts、server.ts、api-contracts、ios/Home.tsx。验收：已复现的两个 green+tempo 案例不再允许质量课；不能绕过 UI 直接锁定过期处方。

### 第 3 步：迁移目标与计划，建立同步身份（2–3 人日）

1. 评估主库副本发布和 runtime 库边界；建议用户目标/计划放在稳定控制库，主分析库继续可替换发布。
2. 添加 athlete、设备凭证、同步批次、计划 revision 等迁移；复用已存在的导入任务状态。
3. 一次性读取并校验 mobile-goals.json，迁入控制库；保留原文件备份和迁移标识，不长期双写。
4. 损坏 JSON 报明确迁移错误，不能静默恢复为默认目标。
5. 新增服务握手返回 serverId、athleteId、datasetEpoch、支持的同步协议/API 版本。
6. 更新整体备份清单：主库、控制/运行库、模型工件和配置清单应能对应同一恢复点。

验收：导入发布/恢复/服务重启不会覆盖用户计划；旧 JSON 迁移可重跑且不重复；新服务被识别为新同步目标。

### 第 4 步：完善 HealthKit 增量同步（3–5 人日）

1. Swift 查询返回 added、deleted 和 newAnchor；首次也使用同一次 anchored query 取得训练和游标，解决两次查询的竞态。
2. 为 workout、睡眠、HRV、RHR 等类型分别保存游标；保留权限有限、无样本的合法状态。Apple 不提供可靠的逐项“已拒绝读取”判断，UI 不得从空结果直接断言拒权。
3. 继续复用 ZIP/XML 导入；增加版本化 manifest，包含源 UUID、删除清单、设备、样本范围和幂等键。解析器忽略未知扩展需有版本协商，不能直接破坏旧 ZIP 兼容性。
4. 后端以 UUID 映射完成 upsert/tombstone；删除导致最早受影响日期回算；多个源属于同一训练时重新选 canonical 来源。
5. 新增恢复记录但无训练时仍提交批次；首次无跑步也能同步睡眠。对迟到路线/心率增加明确补查窗口或独立来源变化查询，不能只依靠 workout added。
6. 只有服务器确认导入并发布后提交本地锚点。幂等重试必须返回同批次结果；部分失败保留待提交游标。
7. 验证全量 XML 与 HealthKit 同一训练的去重，避免云迁移后重复计数。

验收：新增/修改/删除/无变化/部分权限/迟到路线/切服务各自有自动化协议测试；真机跑完至少一轮。仅健康记录为空不触发远程删除。

### 第 5 步：实现可恢复的同步任务（2–3 人日）

1. 本地任务保存 phase、sourceId、jobId、payloadHash、目标服务、pendingAnchors 和重试时间；替代只有一个 upload.zip 的状态。
2. 使用 idle → collecting → uploading → importing → recomputing → succeeded/failed 状态机；错误能指出失败阶段。
3. 重启或回到前台先恢复已有 job 查询，服务器已成功则补提交游标；响应丢失不重新创建逻辑任务。
4. 区分 401（重新认证）、409（状态冲突）、429/5xx（退避）、断网（等待恢复），避免用户看到“请运行 Mac 开发服务器”。
5. 先支持前台同步与返回前台续接；当前有限后台执行时间不能当作可靠后台同步承诺。HealthKit 持续后台 delivery 留待单独立项。
6. ZIP 设置文件保护、排除系统备份、按期限清理；成功任务删除临时敏感文件，失败保留可恢复任务和必要文件。

验收：上传后杀 App、服务器计算中杀 App、短时断网、服务重启后续接不重复训练、不跳过游标。

### 第 6 步：云端鉴权与网络加固（2–3 人日）

1. Release 固定可信 HTTPS 地址；服务切换入口收进高级设置。开发发现和 HTTP 例外使用独立 Debug 配置。
2. 短期桥接只给可信 origin 的 `/v1/` 请求附加凭证；保留 Request 自带的 headers、method、body 和 signal 语义。
3. 校验导航和 message.frameInfo 的主框架与来源；拒绝不支持协议及跨来源桥调用。

## 7. 准确性专项：先明确要预测什么

### 7.1 四个不同目标

| 目标 | 正确定义 | 可用验证参照 | 不应采用的验证方式 |
|---|---|---|---|
| 数据准确性 | 同一次真实训练的身份、距离、时间、时区、样本关联和删除状态正确 | 已确认记录、官方结果、明确构造的数据夹具 | 只看导入成功或总条数一致 |
| 成绩预测 | 指定日期、距离、场景下的完赛用时分布 | 独立的官方净计时或有协议的实测成绩 | 用普通慢跑时间判断比赛预测偏快 |
| VO₂max | 单位体重的最大摄氧量估计，mL/kg/min | 有测试协议与质控记录的气体代谢测试；未达到最大努力时保留 VO₂peak 标记 | 把 Apple Watch 估计或 VDOT 当实验室真值 |
| 跑力 | CA：当次可比表现；TA：缓慢变化的长期跑步表现能力估计 | 未参与估计的标准化表现、固定强度下的速度变化及未来成绩 | 与本模型自己的分数相关就宣称准确 |

普通轻松跑不是一次能力上限测试。其表现应提供“某种负荷下完成了这样的输出”的证据，不应直接把慢配速解释成能力下降。跑力分数是产品定义的指数，没有天然医学真值；应先验证它能否解释或预测可观察表现。

目标按两层管理：先做到定义正确、无数据泄漏、可重复计算；再证明样本外误差优于现有基线。任何“误差达到 X%”都必须附样本数、独立事件数、时间区间、距离与测试场景。

### 7.2 当前代码对准确性的具体限制

1. **VO₂max 与 VDOT 在实现中仍混合。** `packages/physiology/src/index.ts` 的 `performanceEvidence()` 直接把 `vdotFromPerformance()` 放入 `valueMlKgMin`；`packages/application/src/prediction-report.ts` 的 `buildFormulaPredictionBase()` 把 directEvidence 与 labeledPerformance 合并送入 VO₂max 集成。命名和文档已经区分两个指标，但计算链尚未完全分离。
2. **同一次表现可能通过两条路径增加证据。** 表现先影响 VO₂max，再作为独立 performance evidence 和 VO₂max prior 影响有效 VDOT。应追踪共同的 sourceEventId，不能把派生证据当独立测量。
3. **VDOT 受设备 VO₂max 的固定先验和硬上限约束。** `estimatePerformanceVdot()` 使用 VO₂max−1.5 的先验，并把结果限制在 VO₂max 区间上界+0.5。跑步经济性不同会造成 VDOT 与实测 VO₂max 不同，不能把该常数当普遍生理定律。
4. **比赛标签采用了训练活动时间。** `prediction-data.ts` 的 performanceRows 使用 `activeDurationSecondsSql()`，loadLabeledRaceOutcomes 将其作为 actualSeconds。自动暂停或手动暂停时，这不一定是比赛完整计时；应单独建成绩标签而不是修改所有训练的时长口径。
5. **CA 仍主要依赖整次平均信号。** `packages/features/src/index.ts` 的 efficiencyRaw 是 speed / averageHeartRate，paceRaw 是平均速度。心率储备虽已计算，但不等于已用于可比强度下的效率建模；整次热身、间歇、坡度与暂停差异仍可能混入能力。
6. **CA/TA 是相对初始个人样本的指数。** `packages/scoring/src/model.ts` 用中位数/MAD 建基线，再按 50+10z 映射到 0–100；权重为效率 0.375、配速 0.3125、稳定性 0.1875、恢复 0.125。Cardio 已因代理无效降为 0，应保留此纪律。当前数字不应与 VDOT 混用，也不适合直接跨人比较。
7. **TA 更新和停跑衰减依赖人工系数。** learning rate、正向增长阻力、负向方向系数、14/30/60 日后的衰减都是可解释规则，但仍需独立回放验证。恢复同时进入 CA 和负向更新门控，需要检查重复影响。
8. **区间与置信度目前主要是规则构造。** VO₂max 的来源误差常数、120 天衰减、截断范围，以及成绩的乐观/保守范围并不自动对应 80% 或 95% 的统计覆盖率。必须在界面区分“证据评分”与“预测概率”。

以上是静态代码发现，不代表已测得这些机制在当前个人数据上造成了多少误差。新增实验应分别量化，避免一次更换全部模块后无法归因。

## 8. 数据底座：先提高输入和标签的准确性

### A1：建立数据覆盖与误差预算（1–2 人日）

1. 从一致性副本生成 quality-report，统计实际训练数、独立来源、重复率、缺失率、迟到样本、暂停占比、有效心率/速度覆盖、恢复覆盖和各距离真实标签数。
2. 对每次训练保留质量分项而非只有总分：identity、distance、timing、heartRate、route、context、label；低质量理由用稳定代码记录。
3. 抽取已知问题事件核对原始记录和 canonical 结果：同一跑步多来源、5/10km 边界、跨午夜、暂停、室内跑、GPS 漂移、补传路线、删除训练。
4. 输出“输入误差 → 特征变化 → VO₂/VDOT/CA/TA/成绩变化”的敏感性报告。例如距离 ±1%、计时 ±30s、心率 ±5bpm 分别扰动，而非直接认为模型误差都来自公式。
5. 冻结初版数据集 manifest：记录数据哈希、抽样规则、排除原因、标签版本、训练事件分组和时间切分；以后每轮都能复现。

涉及：health-export-parser、storage-sqlite、features、application 的分析 CLI。验收：每个被排除/降权的事件可解释；明确当前最主要误差来源，避免盲目调参。

### A2：补齐成绩、生理测量和证据血缘（2–3 人日）

| 新增/扩展对象 | 必需字段 | 实施原则 |
|---|---|---|
| performance_observations | training_session_id、event_id、official_distance_m、official_elapsed_s、timing_basis、protocol、effort、verified_at、available_at | 使用已有测试协议/override 建关联，独立保存成绩，不覆盖 workout 原值 |
| physiological_measurements | metric、value、unit、method、observed_at、available_at、body_mass_kg、protocol、quality、source_document_ref | method 区分 lab_vo2max、lab_vo2peak、device_estimate；无真实检测不创建虚拟检测值 |
| evidence_lineage | evidence_id、source_event_id、parent_evidence_ids、source_device、algorithm_version、available_at | 同一事件的多个派生值去重计权，保留修订历史 |
| analysis_segments | session_id、start/end、active_seconds、coverage、稳定性、坡度、强度、质量原因、extractor_version | 可重算派生结果，不复制原始时间序列 |
| prediction_ledger | issued_at、target_date、target_distance、horizon、scenario、input_revision、model_version、point、bounds、interval_level、status | 发出预测后不可覆盖，之后独立关联实测结果 |

实施顺序：先迁移与契约 → 读取服务 → 用户确认入口 → 特征/预测消费 → 旧数据回填报告。旧历史缺少标签录入时间时标记 unknown，不能伪造早于比赛的 available_at。

成绩计时优先级：有证据的官方净计时 → 完整计时的标准测试 → 经用户确认的训练总经过时间。活动时间继续用于训练统计；暂停比例不明、赛道距离不明的记录只作为弱表现证据。官方 5km 不能因手表记录 5.08km 就按更长距离“校正”成更快成绩。

### A3：建立可比片段与来源质量控制（2–4 人日）

1. 先去除明确无效 GPS 点、时间倒序和重复点；不要跨长缺口插值。原始样本保留，过滤器版本化。
2. 使用采样时长计算覆盖率，不能只用点数。心率异常检测结合连续性、重复平台和与步频接近的持续锁定；疑似异常先降权，不因“看起来高”直接删除。
3. 切分 warmup、steady、interval、cooldown、pause；先提供保守的 steady segment 提取器，设置有限候选窗口（例如 8/12/20 分钟）并在开发集选择规则。
4. 同时核对速度与心率是否属于同一时间窗；心率滞后校正仅在开发集检验有收益时启用，不能为每段单独寻找最优滞后来抬高拟合。
5. 用可信高程评估坡度，区分平路、起伏、明显上下坡；只有累计爬升时保留有限修正和不确定性，不视为精确坡度还原。
6. 气象分为 observed 和 forecast，分别存发生时间与获取时间；没有数据就保留未知，不自动补 15°C 并当作真实标准环境。
7. 室内/户外、手表/胸带按来源分组评估。室内记录继续计负荷，除非有独立距离校准证据，不为提高样本量直接放开能力更新资格。

验收：构造的暂停、漂移和缺口不产生虚假的高能力片段；同一训练多来源没有变成多份独立训练样本；输出片段可在详情图中定位。

## 9. 最大摄氧量准确性专项

### V1：完全分离生理测量与跑步表现（1–2 人日）

1. 修改 Vo2MaxEvidence 来源与 schema：生理测量、设备估计、表现代理不再共享一个没有语义区分的 valueMlKgMin。
2. `performanceEvidence()` 生成的比赛 VDOT 只进入表现通道；调整 prediction-report 的 evidence 合并方式。
3. 只有 Apple 数据时输出“设备 VO₂max 估计”；有真实气体代谢测试时提供实测历史和校准估计。仅有比赛时，VO₂max 显示证据不足，VDOT 和成绩预测仍可独立运行。
4. 删除 VDOT 必须小于 VO₂max+固定常数的强制关系；保留可解释的弱先验作为候选，并与完全不使用该先验的版本对比。
5. 同一赛事推导出的多个指标共用 sourceEventId，不重复提升 evidenceCount 或 confidence。

验收：输入只有一次比赛时不会产生伪装为生理测量的 VO₂max；同一事件重复导入不会让估计更“自信”；可信表现不因设备低估被硬截断。

### V2：改进设备估计的融合与个体校准（2–3 人日）

1. 按设备/算法版本和相近采样时段聚合，不把同一设备连续高度相关的记录当独立测量；报告独立观测日和来源数。
2. 比较当前稳健融合、按日稳健中位数、简单一维状态空间滤波三种候选。先保持模型小，估计慢变水平与观测噪声，避免复杂黑箱。
3. 把来源误差、时间衰减和突变处理改为版本化参数；在开发时间窗比较少量半衰期候选。设备更换或体重变化作为已知上下文，不自动当作生理改善。
4. 有实验室记录时，用明确时间窗口匹配同阶段设备估计；记录期间训练变化、体重和测试方式。优先拟合稳健偏移，不以少量配对同时拟合斜率、年龄、天气等大量参数。
5. 单次实验室检测只提供一个锚点，不能一边用其校准一边用它证明准确。后续独立检测才可检验外推；没有检测则只评估稳定性和设备一致性。
6. 输出分层不确定性：设备系统偏差、日内波动、跨天变化与数据过期。更多相关记录不能把系统误差缩到零。

验收：异常单点不会造成不合理跃迁，真实持续变化也不会被无限平滑；重复样本不缩窄区间；展示 method、最近测量日期、是否有独立验证。

### V3：VO₂max 的准确性评价

- 对独立气体代谢测试计算偏差、MAE、RMSE，并在配对数量足够时报告 Bland–Altman 一致性界限；这是 VO₂max 验证，与成绩预测误差分开。
- 少量单人检测只报告每次误差与范围，不报告具有普遍意义的人群准确率。重复测量应按人和时间依赖处理。
- 暂不承诺“±2 mL/kg/min”之类绝对误差。先测现有基线，再预先登记候选的改善目标；无法取得独立参照时状态保持“设备估计，生理准确性未独立验证”。
- 外部实验室检测不是云端版本上线依赖，也不要求用户为了软件验证频繁做极限测试；可利用已有合格检查及后续自然获得的结果。

## 10. 成绩预测准确性专项

### R1：修正标签与预测时间口径（1–2 人日）

1. 让 loadLabeledRaceOutcomes 消费 A2 的独立成绩标签；普通训练、间歇拼接、未完成测试和计时不完整记录不能混入高可信目标。
2. 区分“按当前状态现在参赛”与“预测目标赛事日期”。现有 asOf 用于历史分析，不等于已实现未来训练适应预测；赛事日期较远时先给当前能力参考和计划场景。
3. 保存 prediction_ledger；每次预测记录当时实际可用输入，而非比赛结束后重算再称为赛前预测。
4. 为回放实现双时间边界：observed_at 是发生时间，available_at 是系统可知时间。赛后补填 RPE、修订路线和实际天气不得出现在此前已发出的预测中。
5. 比赛实际天气可以用于赛后误差解释；提前预测只能使用当时已取得的预报或明确假设，并保存预报版本。

验收：比赛成绩或赛后标签变化不改变已发出预测；同一场比赛的多距离中间分段同组，不能跨训练/验证集。

### R2：先校准简单基线，再测试机器学习（2–3 人日）

按顺序比较，不把所有方法叠加：

| 版本 | 具体改动 | 适用情形 |
|---|---|---|
| B0 | 冻结当前生产公式和预测输出 | 所有后续候选的参照 |
| B1 | 修复标签/VDOT 语义，保留 Daniels 成绩换算 | 先排除数据与定义错误 |
| B2 | 增加近期真实赛事换算基线，采用收缩的距离耐力参数 | 有可比比赛或标准测试；单一距离不足以拟合个人跨距离指数 |
| B3 | 按距离估计 log(actual/predicted) 的稳健偏移，向整体/零偏移收缩 | 少量标签；不允许一次发挥差永久重标所有距离 |
| B4 | 复用现有 ridge 或 CatBoost 预测剩余误差 | 独立标签达到发布门槛且样本外优于 B1/B3 |

1. 保留当前 5km、10km、半马范围；不同距离的专项耐力分别计算，半马不得只由 5km 速度外推。
2. 对训练上包络增加来源质量与时效约束；选最大值容易放大噪声，不把偶然最快 GPS 片段作为最强证据。比较按独立训练聚合的稳健高分位候选。
3. 日常跑可作为弱下界或固定强度效率信息；证据不足时扩大范围，不把“未尽力”隐含解释为能力不足。
4. 准备度、疲劳、天气和爬升逐项消融。若同一负荷信息已在表现估计和残差模型中使用，验证是否被重复惩罚。
5. 先保留可解释的温湿度/爬升小幅修正；新引入风、海拔、赛道起伏或专项训练特征必须有可靠来源和独立收益。

验收：输出每项修正秒数与原因；B4 没有收益时采用更简单版本。现有 ridge 与 CatBoost 的选择路径要明确，不把两者残差默认连续叠加。

### R3：把“乐观/保守”升级为可验证预测区间（1–2 人日）

1. 明确目标区间，例如标称 80% prediction interval；区间描述的是单次未来成绩，不是平均成绩的置信区间。
2. 留独立时间校准段，使用过去样本外 log residual 的分位数校准上下界；按距离样本少时采用收缩/合并并说明限制。
3. 可试验时间分块的 conformal 校准，但单人训练序列并非可交换，不能宣称无条件保证覆盖率；仍需做滚动样本外验证。
4. 同时报区间覆盖率、宽度和 interval score，防止靠无限放宽区间获得高覆盖。
5. 标注数据过期、未知天气、远期预测和距离外推，降低证据等级；缺证据不能只保留漂亮单点。

验收：每个区间都有 intervalLevel、method、calibrationThroughAt 和有效样本数；校准样本不可再用于最终测试。

## 11. 跑力准确性专项

### P1：拆分表现、长期能力和恢复（1–2 人日）

1. 文档和契约明确 CA 是当次可比表现指数，TA 是长期表现能力估计，recovery 是恢复证据；三者保持独立字段和日期。
2. 保留现有 CA/TA v1 作基线；候选 v2 不再把恢复分数直接当作长期能力证据，而是用于解释当次发挥、观测噪声或更新权重。
3. 对效率、速度、稳定性的重叠做消融。speed 和 speed/HR 高度相关，不能假设是两份独立能力证据；间歇波动不是应被直接扣除的跑力缺陷。
4. 保留 Cardio 权重为 0，直到存在经验证的新有氧信号。更换名称或引入新代理不能替代验证。
5. 固定公开分数映射的版本；升级后通过历史并行曲线解释变化，不能重新归一化后把基线变化展示为用户退步。

验收：单独改变恢复输入不会伪造长期能力的即时跃迁；相同个人能力但不同课型不会仅因整次慢配速系统性扣分。

### P2：从整次均值转向固定强度下的可比表现（2–3 人日）

1. 使用 A3 的稳态片段，选择个人确实覆盖的心率储备范围；最高心率先剔除孤立异常并使用可靠个人证据，不简单用样本 MAX 或年龄公式冒充实测。
2. 在历史已知的 HRR、坡度、温度和时长条件下，拟合简单稳健的“强度 → 速度”关系；只在数据支持的范围内估计参考强度速度。
3. 不直接把 speed/HR 改成 speed/HRR 就认定提高准确性。比较原始基线、按课型归组的稳健基线、标准强度速度候选的样本外结果。
4. 缺少可信最大心率时可比较同设备绝对心率区间，保留低置信；没有重叠强度证据时不给精确可比 CA。
5. 高可信赛事/测试提供能力上限证据，轻松跑只提供有氧效率证据；通过 sourceEventId 防止同一事件在多个通道重复影响 TA。
6. 每次展示 CA 贡献片段、主要条件差异、误差范围，以及是否进入 TA 更新；有效训练数按独立训练而非片段数量计算。

验收：在相似条件下的重复轻松跑表现更稳定；质量跑的能力信号不被热身/冷身稀释；不能用加入数据后更高的分数作为验收。

### P3：验证 TA 平滑、适应与停跑行为（2–3 人日）

1. 比较现有 TA、简单时间加权 EWMA、单一潜在能力的一维状态空间模型。状态模型只是候选，不能预设优于已有规则。
2. 先只估计慢变能力和观测噪声；少量个人数据不同时拟合 fitness/fatigue 多状态、多时间常数和天气适应。
3. 将观测质量决定更新幅度，按真实时间间隔推进状态；强证据允许合理响应，弱证据扩大不确定性。
4. 对正向增长阻力和负向折减分别做消融，测试长期是否造成乐观偏差或改善响应滞后。
5. 区分“已确认没跑”和“最近没有同步”。只有数据覆盖支持时才考虑停跑衰减；未知活动主要扩大不确定性，不能自动宣布身体退步。
6. 停跑衰减按历史恢复训练表现评估；样本不足保留有界先验并标“模型推估”，不输出看似实测的精确掉分。
7. 保持老模型与候选并行读，不直接替换 active model。分析 TA 波动、持续改善的响应时间、恢复差日的影响，以及未来标准化表现误差。

验收：单个 GPS/心率异常不使 TA 大跳；持续有效改善能响应；同步缺口不被当作确认停跑；重算同一版本可复现。

## 12. 准确性实验与发布门槛

### 12.1 实验顺序

1. 冻结当前基线、标签规范和最终测试时间段；先登记主要指标、允许退化范围和停止条件。
2. 修复数据与语义，回放 B1；把“纠正错误数据后的变化”与“模型学习能力提高”分别报告。
3. 在开发时间窗中逐项试验：分离 VO₂/VDOT → 片段质量 → 个人偏移 → 专项耐力 → 环境 → CA 观测 → TA 更新。每轮只改变一类机制。
4. 用 walk-forward 在每个预测时点拟合，预处理和标准化也只用此前数据；赛事、设备重复和同一训练片段保持同组。
5. 参数选定后锁定模型，在最终留出集一次性评估。反复看测试集再调参数，该段就已变成开发集，需要新的未来留出数据。
6. 启用仅观察、不影响页面主结果的候选预测；先验证工程稳定性，随后等待独立新赛事/测试事件验证准确性。经过几周但没有新标签，不等于验证完成。

### 12.2 指标与判定

| 对象 | 必报指标 | 初始判定规则 |
|---|---|---|
| 数据 | 重复、漏项、标签有效性、时间/单位错误、来源覆盖 | 已知夹具中重复/删除/跨日处理正确；真实异常队列逐项可解释 |
| 成绩单点 | MAE 秒、MdAPE、偏差、按距离误差、独立事件数 | 沿用现有 CatBoost 规则：整体 MAE 相对改善至少 5%，单距离相对退化不超过 5%；这些是模型版本对比门槛，不是绝对成绩误差保证 |
| 成绩区间 | 标称覆盖、实际覆盖、宽度、interval score、样本数 | 对比原模型，沿用覆盖率下降不超过 5 个百分点的门槛，并检查绝对覆盖及区间宽度；样本少不能声称已校准 |
| VO₂max | 对独立实验室参照的 bias/MAE/RMSE、配对误差 | 不在自身校准样本上评功；数据不足时不授予“已验证准确”状态 |
| CA | 同条件重复差异、对独立标准表现的关联与误差 | 课型/天气不同要分层；相关性与范围限制需一起报告，不能只给相关系数 |
| TA | 下一次标准表现误差、单次变化 P50/P95、改善响应滞后 | 同时优于或不劣于现有 TA 和简单 EWMA；不能只选最平滑曲线 |
| 工程 | 可重复性、输入时间约束、迁移恢复、跨运行时一致性 | 同输入/配置/数据版本确定性；未来数据泄漏测试为零违规 |

5% 等门槛来自仓库现有训练配置的版本发布规则，并非证明运动科学准确性的通用标准。候选还应沿用已有分块 bootstrap 检查；有相关性的同一人多次记录不能按独立样本随意计算狭窄置信范围。

现有 CatBoost 配置包括 minimum_labels=50、minimum_release_holdout=24、每距离最低 holdout=6、minimum_training_labels=24、每距离最低 training=4，以及时间分块和其他门槛。这些约束必须同时满足，50 条记录并非充分条件。个人数据难以满足时继续用公式/简单校准，不制造标签、不把同场分段拆成独立比赛、不降低门槛强行激活。

### 12.3 必须补的回归案例

- 只有比赛无设备 VO₂：VDOT 可用，VO₂max 不冒充实测。
- 同一设备/同一事件重复证据：不改变中心结果、不增加虚假置信。
- 10km 带暂停与官方用时：成绩标签采用确认的完整计时，训练统计仍保留活动时长。
- 赛后补填标签或导入旧路线：赛前 prediction ledger 不被改写，严格历史回放不能读到未来修订。
- 今日恢复缺失：无绿色质量课；预测疲劳未知不当作“完全恢复”的证据。
- 轻松跑与节奏跑：不同努力程度不会未经归一化直接比较能力。
- 同一训练 12 个片段：训练样本数仍是一次，不能跨训练/测试集合。
- 数据同步暂停：TA 不把未知活动状态等同确认停跑。
- 新旧模型切换：UI 能显示版本变更，历史分数不产生无法解释的断层。

## 13. iOS 配合准确性提升的最小功能

1. 跑后反馈直接复用详情页已有 RPE/课型入口，补充“普通训练/测试/正式比赛”、是否尽力及计时异常；可跳过，不强迫每跑必填。
2. 正式比赛标签页录入官方距离、净计时和结果来源；保存前展示与手表活动时间的差异，避免用户不知情地把暂停后时长作为比赛成绩。
3. 预测页展示“预测生成时间、目标距离/日期、数据截至、区间、证据数量”，允许查看历次预测与实际结果；模型证据分数不加百分号伪装概率。
4. VO₂ 页面分为设备估计历史、独立检测（有则显示）、校准状态；明确单位、来源与日期。没有检测不要显示“已校准”的徽标。
5. 跑力详情展示“当次可比表现/长期估计/恢复”三个不同含义，支持查看为什么本次不参与长期更新。
6. 数据质量页只列可操作问题，例如“本次计时含暂停，尚未确认为比赛标签”；让用户能确认或排除，避免把内部模型调参选项暴露为日常设置。
7. 可选的重复观察优先利用用户原有训练：相近路线、相近强度、同一设备与一致计时。标准测试和赛事只在用户既有训练安排中确认，不为了凑机器学习样本建议频繁全力测试。

专项合计约 20–34 人日，其中与原方案步骤 8/10 有约 3–5 人日重合；合并原基础方案后的总工作量粗估约 38–67 人日。若只先交付“修正指标定义、标签、同步和简单公式校准”，可先完成前六项中的必要部分，复杂 TA 候选和机器学习留后续；外部检测及独立赛事标签等待不计入工程人日。

建议拆成三个版本发布：

1. **可信数据版**：解决原 P0、同步完整性、成绩计时、VO₂/VDOT 混用、新鲜度和预测账本。即使暂时减少可显示的数字，也先保证含义正确。
2. **个人校准版**：片段质量、设备稳健融合、按距离简单残差、可验证区间、跑后标签入口，完成与原基线的独立比较。
3. **验证驱动升级版**：CA/TA 候选、专项耐力改进及达到门槛后的 ML；仅在样本外证据支持时切换主模型，否则保留成熟基线。

每次发布附三份结果：数据质量差异、模型样本外评估、用户指标变化解释。评价优先级是“真实有效的证据 → 正确的标签与指标定义 → 小模型校准 → 更复杂模型”，不能把数值更平滑、评分更高或界面小数更多当作准确性提高。
