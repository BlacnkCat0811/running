# 架构与数据计算模型审查及实施方案

审查基线：2026-09-07，`18b3298`；初始工作区干净。范围：桌面 Web、API、共享包。
实施：Luna / high；独立验收：Astra / medium。未授权修改的原生客户端与冻结响应式区域遵守 AGENTS.md。

## 1. 发现与优先级

### P1：停跑衰减可以反向提高跑力

- 定位：`packages/scoring/src/index.ts`，`trueAbilityAfterInactivity`。
- 当前 `Math.max(20, trueAbilityAtLastEvent - inactivityDecay(...))` 将低于 20 的有效跑力提高到 20。
- 已在基线执行公开函数复现：输入 0、10、19，停跑 0 天和 60 天均返回 20。
- 正常训练更新允许跑力低于 20，因此不是纯粹的无效输入情形；重算和每日快照均调用此函数。
- 修复：衰减结果不得超过输入；保留原有对大于等于 20 分的衰减下限语义；验证非有限输入。
- 验收：0/10/19/20/50 分与 0/14/15/60/长时间停跑的组合，结果有限且单调不增。

### P1：预测恢复度的事实来源和时效不一致

- 定位：`packages/application/src/prediction-data.ts`，`loadRecoveryReadiness`。
- HRV 使用 `health_records` 原始值中位数，绕过已有 `canonical_hrv_days` 的来源选择与夜间聚合。
- 睡眠仅限制 `wake_at < asOf`，没有近期下界；多周以前的睡眠仍可作为当前恢复证据。
- 睡眠查询的无条件 `catch` 同时隐藏缺表兼容和真正的查询/数据库故障。
- 函数还计算训练量及 `acuteRatio`，但最终返回值从未使用它们，产生无效查询且容易误导维护者。
- 修复：将这一组读取放到独立 storage repository；canonical 表存在时以 canonical 为准，显式区分旧库缺表；约束完成时间、近期窗口和时区；删除未使用的负荷查询。
- 保留现有预测恢复度的聚合公式。特征评分恢复权重与预测恢复度是不同模型，不能无验证地把 35/25/25/15 权重搬入预测公式。
- 验收：canonical 与原始 HRV 冲突、过期睡眠、未来才完成的样本、旧库缺表、真实 SQL 错误分别覆盖。

### P2：评分公开边界允许非有限信号进入计算

- 定位：`packages/scoring/src/model.ts`，`scoreRawSignal`、`scoreFeature`。
- 基线创建过滤非有限样本，但评分阶段只检查 null，NaN 可以传播到加权函数并中断整个重算；Infinity 会被截为满分。
- 修复：非有限原始信号按不可用证据处理；校验必要的基线尺度与配置，保证错误明确且不持久化 NaN。
- 验收：NaN、正负 Infinity、零/负尺度及正常有效输入；有效输入保留既有结果。

### P2：纯评分的时间排序隐含 UTC 字符串前提

- 定位：`packages/scoring/src/model.ts`，校准排序；`services/recompute-pipeline.ts`，回放排序。
- `localeCompare` 不代表跨偏移量 ISO 时间的先后顺序，同时间也没有显式 ID 次序。
- Apple 导入会规范化为 UTC，预测报告入口也会规范化，因此不将此问题描述为全部存量数据的已知故障。
- 修复：纯函数按实际时间排序，等时按稳定训练身份排序，无效日期明确失败；重算采用一致顺序。特征 ID 包含运行批次，不能作为跨批次稳定排序的首个平局键。
- 验收：混合偏移量、相同时刻不同表示、输入乱序、无效日期；模型版本隔离旧 checkpoint。

### P2：存储迁移有进展，但重算职责仍集中

- `storage-sqlite` 已拥有数据库实现、读 repository、任务和模型 repository；`service.ts` 已成为较薄门面。
- `services/recompute-pipeline.ts` 仍约 2,085 个非空行，涵盖特征、训练负荷、分区、评分回放、checkpoint、快照等职责。
- `prediction-data.ts` 仍约 800 个非空行，混合 SQL、行映射和生理证据转换。
- `docs/ARCHITECTURE_DEBT_MIGRATION.md` 的部分未完成清单已不反映当前代码，不能直接照历史清单重复搬迁。
- 本轮抽取预测恢复查询作为可验证的局部改进；其余拆分列入后续阶段。

## 2. 架构与模型判断

当前链路为 Apple Health 解析与 canonicalization → SQLite 事实 → Feature Run → 训练指标与评分 Model Run → active 指针 → API/桌面 Web。
预测链路复用历史事实与特征，使用生理公式及可选残差模型，并以版本和能力基线 hash 约束模型兼容性。

应保留的设计：纯 TypeScript 领域包、SQLite 唯一存储实现、不可变 Run、增量与完整回放对照、模型激活 gate、写任务互斥。
纯领域包的当前 import 未发现对 Node/SQLite 的直接依赖；`tsconfig.pure.json` 继续作为检查入口。

评分模型是个人基线的相对指标，维度稳健标准化后结合置信度更新长期跑力；它不是跨人群绝对竞技水平或医学结论。
Cardio 代理目前近似距离，配置已将其权重设为零，不能为了凑齐维度恢复其权重。
本轮没有真实比赛标签的新统计评估，不声称调整后比赛预测精度提高，也不重新拟合权重或自动激活生产模型。

## 3. 本轮实施步骤

1. 为已确认边界添加回归用例，保持有效输入原有语义。
2. 修复衰减与评分有限值处理，统一校准/回放排序。
3. 抽取预测恢复事实读取；在应用层保留聚合公式与调用接口。
4. 更新评分配置版本和预测公式基线版本，验证旧 checkpoint / 残差模型不被静默复用。
5. 运行类型检查、全仓测试及 Web 构建；涉及浏览器行为时执行桌面 E2E。
6. Astra medium 独立阅读最终差异、核查新旧边界与测试结果；问题交回 Luna high 修复，再复验。

实施结果见 `ARCHITECTURE_MODEL_IMPLEMENTATION_2026-09-07.md`，独立验收另行记录。
不修改实际健康数据库，不自动重算或切换已有 active 模型，不推送或部署。
