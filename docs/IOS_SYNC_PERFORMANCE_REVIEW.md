## 1. 目标、边界与必须保留的约束

### 1.1 本次优化的目标

1. 同步成本随**新增、更正、显式删除及待续数据量**增长，而不是随整个历史库增长。
2. 计算复用已验证的历史特征、指标和状态，只计算受影响的后缀。
3. 同步和计算并行推进时，不丢记录、不混用事实版本、不把旧结果显示为最新。
4. 保留“原始事实已保存”和“分析已发布”两个独立结论，不让计算失败迫使手机重传已保存数据。

### 1.2 明确不做

- 不把全量同步、重置 anchor、定时重读全部历史作为优化或故障恢复手段。
- 不创建整库备份、候选主库副本，不复制生产数据库做性能测试，不通过文件换库发布分析。
- 不在普通同步中执行全库 `quick_check`、`integrity_check`、外键巡检或全表 canonical 重建。
- 不用放大 `busy_timeout`、关闭事务、降低持久化等级、跳过身份或提交前校验来换速度。
- 不把评分核心搬到 iOS，不改变评分公式、时间语义、缺失值语义或来源优先级。
- 不修改冻结的窄屏 Web 区域，不增加其他原生产品。

**允许保留的最小可靠性数据**：游标、待续 UUID、删除待办、持久回执、未完成上传的小批临时载荷。
这些是断点续传状态，不是整库备份；批次确认后的产物按既有规则清理，不另建长期备份目录。
基准测试只使用程序生成的合成数据，禁止复制真实健康库或把健康明细写入日志。

首次安装、权限扩大或游标损坏，也不能静默转为全历史重扫。没有可信起点时明确提示并停止该路径；
首次初始化的时间范围需要单独确定，不能由本方案擅自解释为“从零读取所有历史”。

### 1.3 不能因优化破坏的不变式

沿用 [ADR-004](adr/ADR-004-healthkit-sync-invariants.md) 和 [直接增量同步设计](SQLITE_DIRECT_SYNC_DESIGN.md)：

- 游标只确认已交付的数据；阻塞、锁屏、权限不可判定不能冒充空结果。
- 事实、变更账本、必要的分析任务及回执同事务提交；客户端水位与任务结算同事务提交。
- 提交前回读断言保留，不能挪到提交后或降级为日志。
- `preserveAbsent: true` 保持增量语义；只有明确删除才能删除事实。
- 路线超配额保留待办，不以 `invalid` 清掉已发布轨迹；不发布半条路线。
- 保留动态批次 `payloadHash` 与持久任务恢复规则，不把它“优化”为另一种幂等语义。
- 产物清理、提交顺序沿用 ADR；本方案不顺手改动这条已有决策。

## 3. iOS 读取、分批与续传的具体实施方法

### O01：让训练查询页、载荷页和 anchor 一致

**定位**：`HealthKitExport.runningWorkouts` 逐页查到空页后返回最终 anchor；
`exportArchive` 又在训练 XML 页边界停止，却仍返回该最终 anchor。

**改动范围**：
[HealthKitExport.swift](../apps/ios/RAI/HealthKitExport.swift)、
[SyncTaskState.swift](../apps/ios/RAI/SyncTaskState.swift)、
[SyncTaskStore.swift](../apps/ios/RAI/SyncTaskStore.swift)、
[DirectSyncBatchBudget.swift](../apps/ios/RAI/DirectSyncBatchBudget.swift)。

**实施步骤**

1. 拆开“正式 anchored 训练流”和“近期／待办路线发现”，不再把两者合成一个无界训练数组。
2. 引入纯逻辑训练页处理器，页结构携带 `anchorBefore`、`anchorAfter`、新增及删除。
   `anchorBefore` 为已确认起点，`anchorAfter` 在该页完整处理之前只是候选值。
3. 一次查询一页，先渲染训练元数据并预留路线引用与 XML 结束标签开销。
   最终以实际序列化字节校验；不能用记录数估算替代最终字节上限。
4. 整页放不下时不写该页，不推进 anchor；缩小查询 `limit` 后从同一 `anchorBefore` 重查。
   不允许把一个查询页切成几个渲染页后，共享查询末尾 anchor。
5. 一条训练仍超出满额批次时，记录可见的阻塞原因并保留起点；不能无限重导，也不能跳过该条。
6. 只有“该页新增全部进入载荷，删除已发送或进入持久待办”时，才生成 `anchorAfter` 候选。
   候选随任务落盘，在 durable committed receipt 后由既有 `commitSuccess` 原子提交。
7. 训练页确认后，未交付的路线由 O02 的独立队列负责，不能依赖重读所有训练。

**回归／验收**

- 用纯查询替身生成超过两页训练，强制第二页字节拒绝；第一批提交的 anchor 只能到已交付页。
- 中途退出并恢复后，训练 UUID 并集与输入一致，无遗漏、无重复计入。
- 删除-only 页不是 EOF；页拒绝时删除事件不能提前丢弃。
- 在“读取第一页／拒绝下一页／任务落盘／服务端确认／本地提交”各点注入退出。
- `runningWorkouts` 不再先积累全部新增训练；峰值输入缓存受页预算约束。

### O02：把未查询路线变成明确的持久待办

**定位**：预算拒绝路径不写 `routeDecisions`，
但 `RouteSyncStateMachine.rediscoveryCandidates` 只遍历已有路线状态。

**改动范围**：O01 的 iOS 文件，以及
[RouteSyncStateMachine.swift](../apps/ios/RAI/RouteSyncStateMachine.swift)。

**实施步骤**

1. 在本地同步 SQLite 增加 `sync_pending_routes`，以 `(scope, workout_uuid)` 唯一标识，
   保存待办原因、重试时间及必要的公平轮转字段；这是 UUID 队列，不存另一份轨迹备份。
2. 导出遇到路线预算不足时，把未查 UUID 纳入本批候选待办，不能只设置 `routeFile` 布尔标记。
3. 将候选待办变更保存在 `SyncTaskState` 的可选字段中，并接入显式 `init(from:)`。
   服务端确认后，在 `commitSuccess` 同事务里更新队列和训练 anchor。
4. 下一批优先从队列取有限数量 UUID，经 `knownRunningWorkouts` 定点查询。
   保留既有近期发现机制作为补充，不增加全历史扫描。
5. 仅在整条路线交付成功后移除待办。查询不可达、权限不足或锁屏时不伪造“已无路线”；
   明确删除的训练可以移除对应待办。
6. “整条路线超过满额批次预算”保存为需要处理／延后重试的状态并显示原因。
   若只剩这种阻塞项，不得持续触发无进展的即时补跑。
7. 不把“预算不足所以没查”写成 `lastCheckedAt`、稳定性或 settled 证据。

**回归／验收**

- 从未有路线状态、发生在近期窗口之外的训练，被预算挡住后，重启仍能定点继续。
- 两条路线分两批交付，旧路线在新路线完整发布前仍可用。
- 超大单条路线不会造成无限前台补跑，其他可交付路线仍能继续。

### O03：删除队列守恒，恢复时明确区分“缺省”和“清空”

**定位**：`exportArchive` 只回传 `allocation.overflow` 与本批新训练删除溢出，
没有合并旧队列未取出的尾部；`HealthKitSync` 的部分 `markSuccess` 调用遗漏余量。

**实施步骤**

1. 抽出可执行的纯函数 `partitionPendingDeletions`，统一完成去重、限额分配及余量结算。
   记录身份使用 `(type, lowercasedUUID)`，训练身份使用规范化 UUID。
2. 维持已确定的优先顺序：旧待办先于本批新增待办；输出顺序确定且稳定。
   额度只扣实际发送的唯一删除引用，不能按重复事件重复扣减。
3. 输出余量必须包含“旧记录尾部＋旧训练尾部＋本批新增溢出”，不能只保留本批 overflow。
4. 新版本任务即使余量为空，也编码一个明确的空对象。只有老任务缺键才表示“未记录，不更新”。
   有字段但解码失败应保留任务并报错，不能 `try?` 后当空队列推进 anchor。
5. 抽出统一的 `SyncCommitCandidate` 装配方法，让 `waitJob`、`inspect`、
   `upload`、`unchanged`、新导出等所有收尾入口复用，避免逐个调用点手写遗漏。
6. `commitSuccess` 原子更新删除待办、anchor、记录游标、待续标记和任务删除；
   延续提交前回读断言，失败则全部回滚。

核心守恒关系，按唯一身份集合计算：

```text
旧待办 ∪ 本批确认消费的新增删除
    = 本批实际发送 ∪ 下批持久待办

本批实际发送 ∩ 下批持久待办 = ∅
```

**回归／验收**

- 10,000 条旧删除分为 4,500／4,500／1,000 条，最终全部交付。
- 混合 record、workout、重复事件、删除-only 页，仍满足守恒。
- 老任务缺键、新任务显式空、新任务损坏字段分别测试，不得合并语义。
- 每个恢复分支都验证“非空余量保留、显式空清旧槽、失败不提交”。
- 不仅测试分配器，还需测试真实 `SyncTaskStore` 与生产收尾装配路径。

### O05：限制近期窗口，让正式增量保证前进

**定位**：`writeGlobalRecords` 的近期窗口遍历所有类型，
使用与 anchored drain 相同的字节及记录总预算，没有独立限额。

**实施步骤**

1. 正常已有游标且没有历史积压时，只读取正式 anchored 变更流，不每批重复补读近期窗口。
2. 确有初始化／积压、需要近期优先时启用窗口 pass，但不以此触发历史重扫。
3. 初始建议：窗口最多使用总字节和记录预算的 20%，正式增量至少保留 80%；
   这是待基准校准的参数，不是已测最优值。窗口剩余额度不能借走正式增量的保留份额。
4. 近期 pass 的类型也需公平调度；优先满足产品必需的睡眠、HRV、静息心率、训练相关记录，
   不能让固定排序前几个高频类型长期占满预算。
5. 窗口数据与正式流在本批内按 `(type, UUID)` 去重。正式页已被本批窗口完整覆盖时，
   可不重复写 XML，但仍须正确消费该正式页删除事件，并等待同一批回执后才推进页游标。
6. 查询命中 `recentWindowLimit` 时只能认为“窗口可能截断”，不能把 `recentWindowReadAt`
   标记为整窗完整。继续补读须有稳定边界，或明确交由正式流补齐。
7. 持久化“为什么还需下一批”：实际未读页、删除待办、路线待办分开记录。
   只剩已经发过的重叠窗口不能成为无限续批依据。

**回归／验收**

- 三个类型各有 1,500 条近期记录时，正式流仍能处理至少一条可装入的记录，或报告确定性阻塞。
- 连续多批后，各类型均获得处理机会；“窗口写了数据但正式游标一直不动”必须报警。
- 同一固定输入连续同步最终收敛到无待办，不再重复上传整个重叠窗口。

## 4. 服务端解析、计算一致性与调度的具体实施方法

### O04：统一生成真正覆盖依赖的脏范围

**定位**：
[`dirtyFromAt`](../apps/api/src/direct-sync-ingest.ts) 只取账本事件时间；
`extractFeatures` 按 `workoutStartAt >= dirtyFromAt` 选择训练。
旧候选路径中的 [health-change-plan](../apps/api/src/health-change-plan.ts)
已有相交训练回退思路，但依赖 `previous` 附加库，不能原样搬进直连热路径。

**实施步骤**

1. 抽出不依赖候选数据库的 `planIncrementalAnalysisDirtyRange`，
   输入为本批账本、当前事实、`previous_effective_at`／`previous_end_at`／`previous_type` 和 canonical 变更。
2. 对每条更正或删除，保留新、旧区间的并集；删除后当前行不存在时使用账本 before 信息。
3. 对心率、速度等训练内输入，查询与新旧区间相交的训练：
   `workout.start_at <= changedEnd AND workout.end_at >= changedStart`。
   将这些训练的最早起点纳入 feature 脏边界，不能仅比较记录开始时间。
4. 将原始记录、训练、路线、canonical 恢复事实按影响域分类，分别给出
   feature、Fitness、负荷、分区、readiness 的最早受影响边界。
   路线-only 更正也要纳入，不能只依赖 workout 账本变化。
5. 只有配置、版本、override、来源归属及依赖范围都匹配时复用前缀。
   时间或依赖无法确定时拒绝不安全复用，并说明原因；不能自动要求手机全量同步。
6. 长期累积模型从脏边界之前的兼容 checkpoint 续算到当前截止点，
   不能以“最近 30 天足够”为由截断历史影响。

**回归／验收**

- 将本次“训练第 10 分钟心率更正”的合成夹具加入
  [前缀与 checkpoint 回归](../packages/application/test/import-idempotency-and-checkpoint.test.ts)：
  增量计算与从头计算的对照结果一致，受影响训练不得复用旧特征。
- 覆盖跨训练起点区间、跨夜、删除、记录时间前后移动、路线-only 更正。
- 验证更正前的安全前缀保持一致，且不能为修复一条记录重读全部原始健康数据。

### O06：固定计算输入，并让代次、发布与任务合并真正连通

**定位**：接收器登记目标 raw／dependency 代次，
`runDirectSyncAnalysis` 却直接调用现有 `runFullRecompute`，从可变事实表读取输入。

**实施步骤 A：先补一致性，不新增整库快照**

1. 定义 `AnalysisInputBinding`：scope、实际 raw 代次、dependency 代次、
   incumbent、配置／时区／override 摘要、截止时间及输入摘要。
2. 在独立只读连接的同一个读事务内读取 binding 及本次需要的事实。
   读取范围由 O04 的脏区间和兼容 checkpoint 决定；历史前缀读已发布派生结果，不复制主库。
   若当前依赖代次已超过任务登记代次，**不能沿用该任务单批 dirty 去算当前数据**：
   必须读取“当前已发布实际依赖代次之后、捕获代次之前”的全部未覆盖账本，
   合并 dirty、批次及删除／来源证据后生成实际执行计划；账本缺口时不允许安全前缀复用。
3. 将事实读取从 `pipeline.database` 拆到 `AnalysisInputReader`，
   候选结果写入仍走独立的 `AnalysisStore`。逐项覆盖训练、记录、路线、
   canonical、profile、override、分区设置及成绩证据，不能只冻结心率表。
4. 小任务在有界范围内物化必要输入后关闭读事务，再执行 CPU 计算。
   大任务按阶段设置输入内存／读取时长上限：预算不够时转为兼容 checkpoint 分段，
   不能关闭旧快照后无校验地读取“最新一段”再拼接。
5. 每个续算分段必须验证依赖绑定未变；变化则保留旧发布结果，
   合并新增 dirty 范围后重排。不能用长写事务把事实库锁住来制造一致性。
6. 用新增迁移为每个候选 run 保存实际 binding、摘要及被覆盖的 import batch／job 关联。
   例如新增 `analysis_run_input_bindings` 和 `analysis_job_coverage`；
   它们记录计算证据，不复制健康事实，也不另造一个随意递增的版本计数器。
   不能直接把任务登记时的旧代次写成候选实际输入代次。
7. 在发布短事务中核验绑定、当前依赖版本、override／设置摘要及 expected incumbent，
   然后原子完成发布指针和任务结算；任一变化不激活候选。
8. 新鲜度读取**当前 active release 绑定的实际覆盖代次**，不能用任意历史成功 job 的最大代次
   替代当前发布证据；没有新绑定的旧 release 继续走显式兼容分支。
   后续任务若已被当前发布完整覆盖，可校验覆盖证明后完成，不再重复计算。

这份最小覆盖证明属于一致性修复，随阶段 S2 一起交付，不能拖到性能合并阶段。
若涉及历史固定截止点的计算，保持其独立任务与原 `asOf`，不能以“当前数据更新了”偷换请求语义。

**现有发布保护的兼容方法**

- 首批仍保留 `verifyAndPoint` 的严格数据集版本检查，即使非评分批次使候选重排，也先保证正确。
- 确认类型分类和输入绑定覆盖完整后，再为**新绑定合同**增加 dependency 级发布判据，
  允许已证明不影响分析的 raw-only 批次通过；旧任务仍走原有严格判据。
- 不能全局删掉 dataset／incumbent／override 校验，也不能把 lineage 的原始 datasetVersion
  改成发布时“最新版本”来让校验通过。
- 当前 `FactsReader` 及稀疏历史不能被假定为已经覆盖所有事实与删除。
  本方案优先使用上述必要输入读快照，不引入整库备份或全量历史版本回填。

**实施步骤 B：再合并连续批次的重复计算**

1. 只合并同 scope、同配置／时区／override 绑定的尚未执行任务；已运行任务不能直接偷换输入。
   合并对象限于更新“最新分析”的直连任务，历史固定截止点任务不参加。
2. 统一生成覆盖任务：目标为可一致读取的最新依赖代次，dirty 边界取所有成员的最早值，
   `importBatchIds` 和删除／来源更正证据取并集，供现有业务 gate 使用。
3. 用新增迁移建立“原任务 → 覆盖任务”的关联。原回执、原 `analysisJobId` 保留不变；
   查询旧任务时沿关联报告覆盖进度，不能删掉旧 job 或把它谎报为 `not_required`。
4. 不直接增加 `superseded` 状态破坏现有 CHECK／iOS 枚举。
   覆盖任务真正发布后才结算被覆盖任务；失败和重排也必须保留真实含义。
5. 同批更新服务端任务查询、新鲜度派生及 iOS 对账。
   只有持久覆盖关系证明“这个发布包含该任务 dirty 范围”时，才能将原任务视为已覆盖。
6. 防止持续同步饿死分析：按任务年龄／合并次数设置上限，提供分析的最小调度份额；
   不能因为最新代次不停变化而无限创建、废弃候选。

**回归／验收**

- 在特征、负荷、时间线及发布前分别注入下一批导入；要么同绑定发布，要么安全重排。
- 配置或 override 改变必须拒绝旧候选；没有任何旧候选覆盖较新 incumbent。
- 10 个兼容排队批次只执行一份覆盖计算，全部原 `analysisJobId` 都能查询真实结果。
- 分析失败后原始回执仍为 committed，客户端不重传已确认载荷。

### O07：应用写许可必须覆盖完整的短事务

**定位**：
[`withWriteGate`](../apps/api/src/write-lease.ts) 分别包装 `exec` 和 `run`；
[`RecomputeJobRepository`](../packages/storage-sqlite/src/recompute-job-repository.ts)
的 `BEGIN IMMEDIATE`、后续写语句及 `COMMIT` 因而可能处于不同许可窗口。

**实施步骤**

1. 增加明确的 `withWriteTransaction(gate, database, operation)` 边界：

   ```ts
   // 结构示意，非现有可调用 API；异常清理不得覆盖原始错误。
   gate.scope(() => {
     database.exec("BEGIN IMMEDIATE");
     try {
       operation(); // 只有短 SQL 工作，不包含网络、HealthKit 或长 CPU 计算
       database.exec("COMMIT");
     } catch (error) {
       rollbackWithoutReplacingOriginalError(database);
       throw error;
     }
   });
   ```

2. 枚举并改造 claim、complete、fail、recover、分块候选落地、发布及清理的所有事务点。
   SAVEPOINT 嵌套复用外层许可，不能另取一把。
3. 记录事务深度；事务未结束时，`yieldIfStale` 不能释放许可。
   长循环的让路点移到“提交当前分块之后、开始下一块之前”。
4. 分块先以不超过 100 行／约 50ms 的目标校准，实际事务耗时必须记录；
   对单条耗时 SQL 单独治理，不能认为“100 行”自动等于短事务。
5. 将写操作的 `RETURNING`／`get`／`all` 等路径纳入显式写接口，
   不能仅凭调用名是 `run` 才认为它是写。
6. 租约超时不得无许可继续写；改为可重试调度失败，撤回请求并释放／撤销等待队列。
   这是现有失败开放策略的行为变更，必须同批修改回归，不能悄悄更改。
7. Worker 崩溃时先关闭连接释放 SQLite 锁，再完整释放应用调度状态；
   错误处理中的任务结算也不能绕过写许可。

**回归／验收**

- 分析事务持有期间，导入不能获得应用写许可；提交后导入可以获得。
- 在每条事务语句间强制安排另一个执行者，不能形成应用许可与数据库锁互等。
- 取消、回滚、租约超时、Worker 崩溃后，两类锁均可恢复，不遗留永久 busy。

### O08：消除租约握手的固定等待放大

**定位**：授权或释放后仍返回 `pending`，主循环据此固定等待 5ms；
多个语句窗口重复支付等待。另须核查进入 `waitAsync` 前的状态重读是否可能错过请求。

**实施步骤**

1. 将服务器状态机分为 `progressed`、`blocked`、`idle`：
   已完成授权或释放属于 progressed，立即继续处理，不走固定延时。
2. 只有确实被其他 owner 占用时才进入 blocked 等待。
   可先保留有界竞争退避，再接入 admission 状态变化通知；不能空转轮询。
3. `waitAsync` 使用**本轮已处理的观测值**作为 expected value。
   请求在检查与等待之间变化时必须立即重判，不能等待一个已到达但尚未处理的新请求。
4. 保留 request／grant 序号协议、退出唤醒和重复释放保护，不能改回单一布尔标志位。
5. 接入 O07 的短事务分块，减少窗口数量；CPU 工作仍不持写许可。
6. 输出 windows、waitMs、yields、timeouts 及 owner 等待分布，不记录健康数据。

**回归／验收**

- 将“200 个空窗口”探针改为调用生产实现的仓库基准，不能拿旧演示轮询脚本冒充生产测量。
- 覆盖请求刚好发生在准备休眠之前、取消时尚未授权、退出时尚有等待者等竞态。
- 性能目标见第 6 节；必须先通过互斥正确性，再比较耗时。

## 5. 计算、查询和轨迹写入的具体提速方法

### O09：把增量复用扩展到负荷、分区与日级结果

**定位**：
[`replayTrainingMetrics`／`buildAndPersistZoneProfiles`](../packages/application/src/services/recompute-pipeline.ts)
仍遍历整个 feature／日期范围；
[`loadDailyPhysEvidence`](../packages/application/src/training-load-data.ts)
逐日调用恢复事实装配，重复查询重叠历史窗口。

**实施步骤**

1. 由 O04 分别生成各计算域的 dirty 边界，不把所有健康变化一律扩大成 Fitness 全历史重算。
2. 为负荷、分区及 readiness 增加带版本的 checkpoint／复用证明，记录算法、
   配置、时区、override、输入绑定和滚动窗口状态。
   模型版本或状态缺失时不复用，不把默认零值当作有效历史状态。
3. 将安全前缀的逐训练负荷、分区、日指标用集合 SQL 复用到新 run；
   重映射 feature／profile／run 外键，不能让新 run 引用已淘汰 run 的临时行。
4. 从 dirty 边界前最近的兼容 checkpoint 恢复滚动状态，再计算到 `evaluatedAt`。
   90／180 天证据窗口保存必要队列；指数平滑、累积能力等状态不能靠固定天数截尾。
5. 从一个输入快照批量读取所需日期区间的恢复事实，按日索引或双指针维护基线窗口；
   保留 `observedAt`、`availableAt`、`asOf` 区分，不能用未来证据解释过去。
6. 一次装配后复用训练的心率／速度区间、路线质量／高程聚合，避免特征、最大心率证据、
   分区、负荷阶段重复扫描同一记录。缓存按输入 binding 和参数标识，并设置条数／字节上限。
7. 发布前保留完整的模型、覆盖与恢复隔离 gate；历史前缀证明失败不能假装已复用成功。

**回归／验收**

- 对新增、训练内更正、删除、override、配置变化，增量结果与合成数据的离线从头计算一致。
- 单次近期变更只重算受影响后缀；复用前缀中的业务数值不变。
- 保留浮点误差规范、分类／missing reason 精确比较，不能只比总行数。
- 输出每域 reused／recomputed 数、查询次数、扫描行数、CPU 及落地耗时。

### O10：让“局部重建”从读取阶段就局部化

**定位**：
[`canonicalizeNightsForWindow`](../packages/health-export-parser/src/canonicalize-nights.ts)
调用无窗口的 `loadSegments`、`loadHrv`，随后才在 JavaScript 中过滤。

**实施步骤**

1. 为两个加载器增加可选范围参数；直连窗口路径传范围，旧离线完整计算入口保留原语义。
2. 睡眠 SQL 在 `GROUP BY` 前加入 `end_at > rangeStart AND start_at < rangeEnd`；
   HRV 加入 `start_at >= rangeStart AND start_at < rangeEnd`。
   `rangeStart`／`rangeEnd` 沿用现有本地夜间边界换算，不能直接按 UTC 午夜代替。
   字符串比较前须证明该读取路径的存储时间已规范化为同口径 ISO 时间；
   不能把兼容的混合时区／格式数据直接按字符串排序而改变原有日期含义。
3. 保留重复记录折叠、区间并集、来源排序及 `computed_at` 还原规则。
4. 本批变更跨多个不相邻时期时，构造并合并实际受影响夜窗口，
   避免简单取全局 min／max 后重建中间几年未受影响的夜。
5. 在合成库上执行 `EXPLAIN QUERY PLAN`，评估现有
   `(type, start_at, end_at)` 索引；仅按实测选择是否增加类型＋结束时间等索引。
   普通 B-tree 不保证同时高效利用两个范围条件，不能仅凭列顺序宣称已解决。
6. 新索引用新增迁移创建，禁止修改历史迁移和冻结 checksum。
   大索引构建是受控一次性维护，不混入每次同步，不生成整库备份。

**回归／验收**

- 扩展 [窗口回归](../packages/health-export-parser/test/canonicalize-nights-window.test.ts)，
  覆盖窗口前开始但窗口内结束的睡眠、跨时区日期边界、相同内容的可得时间保留。
- 窗口外 canonical 行含时间字段逐字节不变。
- 历史数据量增加 10 倍、近期窗口相同时，输入装配行数主要随该窗口而不是全历史增长。

### O11：读端迁移完成后，消除轨迹点重复复制

**定位**：
[`publishRouteVersion`](../packages/storage-sqlite/src/database.ts)
从暂存版本分别复制到 `route_points` 和 published 版本点表，随后清理暂存。
当前 published 槽位还会复用，不能把它误描述为已经具有任意历史版本保留能力。

**实施步骤**

1. 枚举所有 `route_points` 读者，包括 API 轨迹、训练质量、高程、缓存／指纹校验和离线工具。
   统一通过一个 route point reader 按已发布、complete 的版本读取。
2. 在双读对照期比较点序、点数、坐标、海拔、速度、缺失值及删除语义；
   证明所有热路径已接入后，再退役旧表双写，不能先删旧表让旧读者读空。
3. 旧路线没有版本指针时，保留显式 legacy 读分支。
   当该路线下一次真实更正到达时逐条转换，不全库复制／回填轨迹。
4. 新路线的 staging 使用每次唯一版本 ID。解析时点只写进这一版本；
   校验点数、连续序列及摘要后，将**同一行**从 pending 提升为 complete，再原子更新指针。
   下一次 staging 必须使用新 ID，不能擦写当前已发布槽位。
5. 摘要命中同一完整版本时丢弃新暂存并复用，不能再复制一遍点。
   错误或超配额只拒绝新暂存，不改变当前可读版本。
6. 只保留当前版本及实际被保留发布结果引用的版本；无引用的暂存／过期版本分块回收。
   若尚未具备完整引用证明，先不删除被引用版本，不能用无限保留版本代替正确的生命周期。
7. 这一步需要与 O06 的路线输入绑定一致：候选计算使用捕获的路线内容，
   不能 CPU 阶段读取一份、发布前又解析成另一份。

**回归／验收**

- 在解析中断、数据库写入失败、超配额时，旧路线仍可读，新路线不可半发布。
- legacy 路线仍能读取，单路线更新后无需全量迁移。
- 新路线点不再同时落入两个完整点表，记录点表写入行数和 WAL 字节下降量。

### O12：复用 Worker，同时保持车道安全与故障恢复

**定位**：
[`ImportWorker.databaseTask`](../apps/api/src/import-worker.ts) 每次创建 Worker；
record-only 拒收后，通用车道再次创建 Worker；
[`RecomputeWorker`](../apps/api/src/recompute-worker.ts) 逐任务创建线程。

**实施步骤**

1. 第一阶段先将两条导入车道移入**同一个任务 Worker**：
   保持 record-only 严格资格判定，确认无写入／完整回滚后，再调用通用接收器。
   不能为了减少线程而取消白名单、表写守卫或 payload 身份复核。
2. 用经过同批身份复核的不可变输入传递预检结果。
   未证明上传目录不可变之前，不以 mtime／文件大小缓存取代内容摘要校验。
3. 第二阶段才建立一个常驻 ingest Worker、一个受控 analysis Worker，
   与现有 admission 共用单写者纪律；不要直接按 CPU 核数并行写 SQLite。
4. 每次任务重新检查 scope、数据库身份／schema 及当前版本。
   migration、恢复、目标切换后重建连接，不能把旧连接和 prepared statement 带到新库。
5. Worker 错误以 task ID 对应当前任务，崩溃后替换线程。
   导入是否成功仍从持久回执恢复，不能在回复丢失时重新导出或建立新批次。
6. 清空任务大数组、关闭文件句柄、保留有界缓存，监测多批 RSS 是否持续增长。
7. 将启动／加载、等待许可、解析和事务分开计时，验证节省的是实际启动成本。

**回归／验收**

- 20 个连续小批中没有每批重复启动两个导入 Worker。
- 各任务 scope 和回执隔离；上一任务异常不污染下一任务。
- CPU 计算期间不占写许可；线程复用不绕过 O06／O07 的一致性保护。

## 6. 性能验收：先定义工况，再承诺速度

本次没有真机／目标服务器端到端测速，**不宣称已经保证某个同步秒数**。
以下数字均为待执行的工程目标，测量设备、网络及数据规模必须随结果记录。

### 6.1 基准工况

| 工况 | 合成输入与条件 | 重点观察 |
|---|---|---|
| 无变更 | 已有有效游标，正式流读到空页 | 不重读历史；不反复补读窗口；不登记无意义分析任务 |
| 一次普通跑步 | 1 次训练、2,000 条心率、1,000 条速度、3,600 个轨迹点 | 导出、传输、解析、提交与分析分段耗时 |
| 历史训练内更正 | 更正一条训练中段心率，其他数据不变 | 正确命中训练；仅计算受影响后缀 |
| 删除积压 | 10,000 条记录删除，混合训练删除及重复事件 | 跨批守恒、有限步完成、无重复计费 |
| 路线预算不足 | 多条总量超预算、单条均可装入；另测单条不可装入 | UUID 待办、重启恢复、公平调度及阻塞可见性 |
| 连续同步 | 20 个小批；分析阶段注入新批次 | 不混代、锁等待、任务合并、旧回执可查询 |
| 历史量放大 | 程序分别生成 1 倍与 10 倍历史，相同近期变更及 checkpoint 条件 | 局部读取规模、前缀复用率，不把历史更正后缀误作固定成本 |

同一硬件／运行版本下先预热，再对每个工况至少执行 30 次，记录 p50／p95／最大值。
冷启动单独统计，不混进热路径分位数。iOS 系统后台派发等待独立记录，不归因于服务端计算。

### 6.2 结构性硬门槛与初始目标

| 项目 | 验收要求 |
|---|---|
| 全量／备份禁令 | 普通同步无 anchor 重置、整库备份、候选库复制、文件换库、全库检查 |
| 数据完整性 | 新增、更正、删除、路线待办无遗漏；相同批次幂等，不因失败重复计入 |
| 计算正确性 | 与同一合成输入、配置、截止点的离线参考一致；所有现有发布 gate 保留 |
| 分批前进性 | 有可装入待办时每轮有实际进展；不可装入时明确阻塞，不无限空转 |
| 锁纪律 | 写许可覆盖完整事务；CPU 不持写许可；租约超时不无锁写入 |
| 租约微基准 | 同机 200 空窗口目标小于 100ms；先消除约 2.17s 的固定延时放大，再评估目标可达性 |
| 写窗口 | 初始目标 p95 不超过 50ms；超时 SQL 必须可定位，不用增加超时掩盖 |
| 查询扩展性 | 固定近期窗口在 10 倍历史下不出现 10 倍原始记录装配；记录实际扫描行数与计划 |
| 增量收益 | 正确性一致后，近期小变更的分析 CPU／原始查询行数以较正确基线降低至少 50% 为初始目标 |
| 端到端时延 | 在目标手机／服务器测完后确定“事实保存”和“分析发布”各自的 p95 预算；未测不填达标 |

不能把“修复前错误地复用全部旧特征所以非常快”当作正确性能基线。
先建立正确的参考输出，再比较优化前后的同语义实现。

### 6.3 建议新增的观测项

- iOS：各类型查询页数、窗口／正式流条数及去重数、字节数、anchor 实际前进、
  各类待办数量、导出／打包／上传耗时。
- API：队列等待、Worker 启动、预检／摘要、解析、canonical、路线写入、事务与回执耗时。
- 分析：捕获的输入绑定、各域复用／重算量、SQL 次数／行数、CPU、落地及发布耗时。
- 调度：许可窗口、持有／等待、超时、重排原因、覆盖任务数量、RSS 及 WAL 增长量。
- 日志只写批次标识、计数及耗时，不写健康样本值、UUID 清单、GPX 内容或访问令牌。

### 7.4 失败回退和既往数据缺口

- 性能优化的回退只回退到**正确的增量实现**，不能回退已知会漏数据的分页实现，
  也不能回退整库备份／候选库／全量同步链路。
- 发布失败继续显示上次已发布分析及其过期状态，保留原始 committed 回执。
- 对已被旧缺陷跳过的训练或丢失的删除，不承诺仅改代码就能自动恢复。
  有可信 UUID／删除清单时可以定点补偿；没有证据时明确标为无法确认，
  不能猜测删除、自动重置游标或擅自全量重扫。
- 任何需要新的同步范围、破坏性迁移或超出已授权后台机制的动作，另行提交用户确认。

## 8. 总结

优先解决“批次交付边界、待办守恒、正确 dirty、固定输入和事务许可”，
再减少租约交接、历史重复计算、范围外读取、轨迹复制和 Worker 启动。
这些改造都可以在**仅增量、不备份、不换主库、不重写评分核心**的约束下实施。

是否真正变快，以同一合成输入的正确输出、目标设备的分段 p50／p95 和禁止操作为零共同验收，
不以“代码看起来更快”或单个总耗时数字代替。
